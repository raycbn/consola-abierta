Windows Server under pressure: advanced CPU, memory, storage and network diagnostics

A slow server is not a diagnosis. Investigation starts by correlating service impact, workload, topology and subsystem signals. This guide develops a capture and analysis method to distinguish actual saturation, contention, latency and secondary symptoms.

Operating principle

Do not declare a bottleneck from a single counter. A metric describes one aspect of system behaviour; causality requires temporal correlation, a falsifiable hypothesis and evidence of workload impact. The question is not “which resource is high?” but “what is the service waiting for, for how long, under what workload, and at which layer is that wait introduced?”

1. Diagnose the service, not the chart

The initial report usually sounds like “the server is slow”, “the application takes longer” or “CPU is spiking”. None of those statements defines a performance problem. Before opening PerfMon, identify the degraded behaviour and the interval in which it occurs.

At a minimum, establish:

  • Impact: p50/p95/p99 latency, throughput, errors, timeouts, job duration or a missed operational window. Choose a service-level metric that represents the actual problem.
  • Scope: one host, a node set, an application instance, a storage path, a VLAN or a region. Compare against a healthy peer when a meaningful equivalent exists.
  • Time window: when it started, periodicity, duration and overlap with backups, antivirus, snapshots, batch jobs, deployments, scheduled tasks or configuration changes.
  • Topology: OS version and build, sockets, NUMA, vCPU, assigned memory, storage type, teaming, vSwitch, hypervisor and upstream/downstream dependencies.
  • Baseline: known behaviour under comparable load. A metric only gains meaning when compared with its history, a peer node or an expectation derived from the design.

State a hypothesis and identify the observation that would disprove it. If CPU saturation is suspected, finding a process consuming cycles is not enough: determine whether available CPU time constrains request latency and whether the runnable queue grows during the same interval. If the service degrades while CPU remains idle, the hypothesis needs to change.

1.1 Separate saturation, contention and latency

ConceptMeaningWhat to look for
SaturationUsable capacity of a resource is occupied during the relevant period.Sustained utilisation, growing queue, constrained throughput and correlated degradation.
ContentionWorkloads compete for a resource or a critical section.Waits, queues, context switches, locks, throttling or noisy neighbours.
LatencyOperation response time increases even when aggregate utilisation is not high.Per-operation time, latency distribution, waits and end-to-end traces.
Insufficient capacityThe design has insufficient headroom for normal or forecast demand.Repeatable degradation as load increases, without a transient anomaly explaining the result.

A host can show 25% aggregate CPU while a critical thread is constrained to one logical processor; it can report low available memory without effective commit pressure; or a VM can observe storage latency whose cause is outside the guest OS. Metric aggregation level matters as much as the value itself.

2. Capture: build a timeline that supports investigation

A point-in-time capture is a snapshot. Intermittent incidents require a time series covering the state before degradation, during the event and after recovery. PerfMon and data collector sets are suitable for longer-running counter telemetry. Microsoft documents logman as an interface for creating, querying, starting and stopping these collectors.

2.1 Discover counters using the host's actual locale

Counter names are localised. The examples below use the English names shown in documentation; do not copy them blindly to a Windows Server installation in another language. Enumerate the sets and exact paths available on the target host:

# Run elevated if the relevant counter set is protected by ACLs
Get-Counter -ListSet * |
  Sort-Object CounterSetName |
  Select-Object CounterSetName, Paths

Get-Counter is available on Windows in PowerShell 7. Microsoft explicitly notes the localisation of counter names and recommends enumerating sets. Also verify that instances exist on the target: roles, drivers and devices do not expose identical counter sets on every machine.

2.2 A reference collector with logman

The following set is an investigation baseline, not a universal template. It captures CPU, memory, process, disk and NIC signals every 15 seconds. Tune counters to the question being investigated; adding every instance of every object without a hypothesis increases volume and makes analysis harder.

New-Item -Path 'C:\PerfLogs' -ItemType Directory -Force | Out-Null

$counterPaths = @(
  '\Processor Information(*)\% Processor Time',
  '\Processor Information(*)\% Privileged Time',
  '\Processor Information(*)\% DPC Time',
  '\Processor Information(*)\% Interrupt Time',
  '\System\Processor Queue Length',
  '\System\Context Switches/sec',
  '\Memory\Available MBytes',
  '\Memory\Committed Bytes',
  '\Memory\% Committed Bytes In Use',
  '\Memory\Pages Input/sec',
  '\Process(*)\ID Process',
  '\Process(*)\% Processor Time',
  '\Process(*)\Private Bytes',
  '\Process(*)\Working Set - Private',
  '\LogicalDisk(*)\Avg. Disk sec/Read',
  '\LogicalDisk(*)\Avg. Disk sec/Write',
  '\PhysicalDisk(*)\Avg. Disk sec/Read',
  '\PhysicalDisk(*)\Avg. Disk sec/Write',
  '\PhysicalDisk(*)\Disk Reads/sec',
  '\PhysicalDisk(*)\Disk Writes/sec',
  '\Network Interface(*)\Bytes Total/sec',
  '\Network Interface(*)\Packets Received Errors',
  '\Network Interface(*)\Packets Outbound Errors'
)

logman create counter WS-Perf-Baseline -o 'C:\PerfLogs\WS-Perf-Baseline.blg' -f bincirc -v mmddhhmm -max 1024 -si 00:00:15 -c $counterPaths
logman start WS-Perf-Baseline

# Reproduce or observe the incident...

logman stop WS-Perf-Baseline

Check that a collector with that name does not already exist and that the destination volume has approved capacity and retention. Circular logging limits the configured size; it does not replace an evidence-retention policy. Protect BLG files as operational evidence: they can disclose process names, activity and internal topology. Creating and controlling collectors requires appropriate privileges.

Fifteen seconds is a starting point for trends and longer windows. For a spike lasting only a few seconds, reduce the interval only for a bounded capture and assess instrumentation overhead. Do not confuse the sampling interval with the true temporal resolution of every metric. PerfMon may also condense points when the number of samples exceeds what a graph can display faithfully; inspect sample counts and the underlying data before interpreting a peak or a minimum.

2.3 Short sampling with Get-Counter

For a bounded check, Get-Counter can sample a small set. This example observes one minute at five-second intervals:

Get-Counter -Counter '\Processor(_Total)\% Processor Time', '\Memory\Available MBytes', '\System\Processor Queue Length' -SampleInterval 5 -MaxSamples 12

This can test a specific hypothesis; it does not replace a persistent collector or capture a problem that occurs outside that window. For trends, record or export data reproducibly and keep timestamps aligned with application, hypervisor and storage logs.

3. CPU: aggregate utilisation, hot threads and kernel cost

Start with Processor Information(*)\% Processor Time—or the equivalent counter available—and preserve per-logical-processor visibility as well as the aggregate. A total can conceal an uneven distribution: a serial thread can saturate one logical processor while the others remain idle. Aggregate utilisation then appears to have headroom, but the application's critical path cannot progress faster.

3.1 Interpret process and system values on the same scale

Process(*)\% Processor Time can exceed 100% because it expresses process consumption relative to one logical processor. On a machine with 16 logical processors, a process fully occupying four of them can approach 400%. To compare it with host-wide percentage, normalise by the number of logical processors and check how the tool handles processor groups.

Include Process(*)\ID Process in the capture. Process instances can acquire suffixes such as #1 when multiple processes share a name; that suffix is not a stable identity. Correlate instance name, PID and lifetime, and discard instances that exited or were recreated during the analysed window.

3.2 The CPU queue is not a magic threshold

System\Processor Queue Length helps observe runnable work waiting for CPU, but it does not represent every application wait. Interpret it with logical-processor count, per-CPU utilisation, queue duration and service latency. A momentary queue can be normal; a sustained queue coinciding with busy CPUs and degraded latency is a much stronger signal.

If kernel, DPC or interrupt time rises, investigate drivers, storage and security filters, NICs, virtualisation and devices. The System process can concentrate kernel activity that cannot be cleanly attributed to a user process. Do not conclude “bad driver” simply because System appears at the top: confirm with a trace and determine which module, stack or event type consumes the cycles.

Inside a VM, guest CPU counters do not describe the execution capacity granted by the hypervisor. Correlate the time series with ready/co-stop or the platform's equivalent metrics, CPU limits, reservations, overcommit and host contention. A guest with low visible utilisation can still experience external scheduling latency.

4. Memory: available RAM, commit and actual pressure

Separate physical memory, committed memory and kernel memory. Memory\Available MBytes is a physical headroom signal; Memory\Committed Bytes and Memory\% Committed Bytes In Use describe commitment relative to the commit limit. These are not interchangeable. High commit does not automatically mean all committed memory is resident in RAM; low available memory alone does not prove harmful paging.

4.1 Correlate pressure with processes

  • Private Bytes: private committed memory attributable to a process. Useful for detecting growth, but not equivalent to resident RAM.
  • Working Set - Private: the resident private portion of the working set. It can change because of trimming, memory pressure or normal memory-manager behaviour.
  • Available MBytes: physical memory available to the system and workloads.
  • Committed Bytes / Commit Limit: system-wide commitment against the limit, which depends on RAM and the page file.
  • Pool Paged / Pool Nonpaged: kernel allocations. Sustained abnormal growth can point towards a driver, but PerfMon alone does not identify the responsible pool tag.

Memory\Pages Input/sec is more useful than treating Pages/sec as a synonym for “the page file is saturated”. Pages read in can come from mapped files and other backing stores, not only the page file. Page faults can be resolved from memory without disk reads. Correlate page inputs, disk reads, storage latency and process behaviour before declaring excessive paging.

4.2 Investigate trends, not snapshots

Look for Private Bytes growth without release, persistently declining Available MBytes, rising commit, trimmed working sets and sustained hard faults. If kernel memory is suspected, first establish which pool is growing; then escalate to tools that can attribute allocations by tag and driver. Nonpaged pool cannot be evicted to the page file in the same way as paged pool.

In virtualised environments, include dynamic memory policy, ballooning or hypervisor reclamation where applicable. The memory assigned in VM configuration does not prove the guest always has the same effective headroom during host contention.

5. Storage: separate volume, device and I/O path

When an application blocks waiting for I/O, CPU utilisation may fall. Separate the logical volume used by the workload from the physical or virtual device backing it. Observe reads and writes independently:

  • Avg. Disk sec/Read and Avg. Disk sec/Write: average completion latency per operation over the interval.
  • Disk Reads/sec and Disk Writes/sec: operation rate, not I/O size or individual latency.
  • Disk Bytes/sec: throughput; interpret it with I/O size and workload.
  • Avg. Disk Queue Length / Current Disk Queue Length: pending work; meaning depends on device, parallelism and measurement layer.
  • Process(*)\IO Read Operations/sec and IO Write Operations/sec: process-level I/O activity attribution, not a direct measurement of the latency experienced by that process.

Do not turn indicative values into a universal SLA. Microsoft's guidance provides latency references for general scenarios, but the actual criterion depends on storage type, queue depth, I/O profile, service tier and that workload's baseline. A short spike is not equivalent to sustained latency throughout a critical window.

When latency rises, ask what changed: IOPS, throughput, block size, random/sequential pattern, read/write mix, flushes, snapshots, backup, antivirus, deduplication, multipath or array contention. In a VM, guest counters may not expose datastore queueing, vSAN/SAN latency or host-side waits. Correlate with hypervisor, array and multipath telemetry, respecting the boundaries of each support domain.

DiskSpd is a storage workload generator maintained by Microsoft's engineering teams. Use it to characterise a design or reproduce a pattern in a controlled environment, not as a first response against an active production volume: a poorly sized test can compete with live work and contaminate the evidence under investigation.

6. Network: throughput is not connection health

Network Interface(*)\Bytes Total/sec estimates traffic processed by a NIC. Compare it with effective capacity rather than only the advertised link speed, and distinguish sent from received traffic. An interface far from saturation can still experience drops, retransmissions, incorrect MTU, queueing, offload issues or loss in a virtual or physical component.

Collect interface statistics before and after reproducing the symptom:

Get-NetAdapterStatistics |
  Format-Table Name, ReceivedBytes, SentBytes,
    ReceivedPacketErrors, OutboundPacketErrors,
    ReceivedDiscardedPackets, OutboundDiscardedPackets -AutoSize

These are cumulative counters. The delta between two readings over a known window is more informative than a single value. Check whether driver, firmware, teaming, vSwitch, VLAN and the peer show the same pattern. If the application reports timeouts, include TCP retransmissions, resets, DNS, connection-establishment latency and measurements from the other endpoint; do not assume every timeout is local to the server.

6.1 Pktmon for locating drops within the stack

Pktmon, included in Windows Server 2019, 2022 and 2025, can capture traffic and observe packet loss at multiple points in the networking stack. Its differentiator in virtualised environments is visibility into the component where a packet is observed or dropped. Start with specific filters, reproduce the flow and keep the capture window bounded:

# Inspect filter syntax and current state
pktmon filter add help
pktmon list

# Example: filter a specific port (adjust to the flow under investigation)
pktmon filter add -p 443
pktmon start -c

# Reproduce the issue and inspect counters
pktmon counters

# Stop capture and convert ETL to text
pktmon stop
pktmon etl2txt PktMon.etl

Available syntax varies by version; check pktmon help and the documentation for the target build before running commands. Do not capture all traffic unnecessarily: filter by IP, port, protocol or component. Captures may contain sensitive metadata and must be handled as restricted evidence. Converting to PCAPNG helps with Wireshark analysis, but may lose component-specific drop reasons and capture-point detail; retain the original ETL.

7. When PerfMon is not enough: ETW, WPR and WPA

PerfMon describes trends through aggregate counters. By itself, it does not explain kernel-level activity, call stacks, thread scheduling or the exact sequence of events. When the question is which thread ran which code, which module generated the cost or why an operation waited, escalate to Event Tracing for Windows (ETW).

Windows Performance Recorder (WPR) collects ETW traces through profiles; Windows Performance Analyzer (WPA) opens the ETL and supports analysis of events, CPU, disk activity and other subsystems. WPR/WPA are part of the Windows Performance Toolkit, distributed with the Windows ADK. This is not a capture to leave running indefinitely: choose a profile that answers the hypothesis, define duration and storage mode, and bound the output volume.

# Review profiles available on the host
wpr -profiles

# Example CPU capture in memory mode
wpr -start CPU

# Reproduce the symptom during a bounded window
wpr -status

# Save the ETL and describe the scenario
wpr -stop C:\PerfLogs\cpu-investigation.etl "CPU contention during request latency"

Check the available profile and memory/disk headroom first; the command is illustrative. Unbounded file mode can fill a volume. In production, coordinate the capture, set a maximum size and duration, assess its impact and define who will hold the ETL. WPA requires a compatible Windows Performance Toolkit installation.

Use PerfMon to answer “when and which resource changed”; use WPR/WPA to answer “which event, thread, module or stack produced the cost”. Do not start with a verbose trace before defining a hypothesis: it creates large files and makes analysis harder.

8. Diagnostic patterns: signals that belong together

High disk latency, idle CPUWorkload is waiting for I/O; cause may be outside the guest.Read/write latency, queue, IOPS, throughput, snapshots, hypervisor and array.

These patterns are not closed diagnoses. They are starting points for experiments that can confirm or disprove the hypothesis. If evidence points across layers, broaden the capture instead of forcing an explanation inside the operating system.

9. Lab results: baseline, CPU, memory and storage

This section reports measurements collected in an isolated lab on 12 November 2026. They are not universal reference values: they describe a Windows Server 2025 Standard Evaluation VM (build 26100) with 2 vCPU, 4 GiB RAM and a 40 GiB virtual NVMe data disk (D:) on VMware Workstation 26.0.1. Networking remained on VMnet1 Host-only. DiskSpd 2.3 ran against a 4 GiB test file, never against a raw device.

9.1 Idle baseline

The PerfMon capture lasted 10 min 43.95 s, at a 5-second interval, with 130 samples. Mean total CPU was 3.79% (P95: 4.98%); mean available memory was 2,797 MB; mean committed memory was 18.68%. The D: disk queue remained at zero, with mean write latency of 0.4 ms (P95: 1.7 ms). This is the idle reference for this VM, not a threshold for other servers.

Interpreting sequential-read throughput

The observed 8.3 GiB/s is a measurement of the VM/Workstation/VMDK stack. It does not demonstrate that the physical NVMe can sustain that speed: virtualisation and host caching layers may affect the result. Do not extrapolate this figure to bare metal or use it as a physical-device specification.

9.7 Scope and evidence limitations

  • The main CPU, memory and storage suite completed 15 runs without failures and has a separate PerfMon capture of 366 samples at five-second intervals.
  • CPU, memory and storage figures belong to one specific Windows Server 2025 VM (2 vCPU and 4 GiB); the network test also used an Ubuntu 24.04.1 VM with 1 vCPU and 1 GiB.
  • The instrumented TCP repeat delivered exactly 768 MiB. Its network PerfMon series contains 90 five-second samples and must not be interpreted as per-transfer resolution.
  • The two TCP series are separate executions and are reported separately. Ubuntu sender and Windows receiver times use different timing boundaries.
  • The network was VMnet1 Host-only. NAT and Bridged were not enabled, and the host was not used as a sender. No physical NIC, bare-metal or production SLA capacity test was performed.
  • Results depend on build, language, drivers, hypervisor, cache and lab configuration; they are not universal reference values.

BLG/CSV, DiskSpd logs, ETL, xperf correlation, all three transfer results and PerfMon screenshots were preserved. ETW confirms the write-latency tail but does not determine whether it originates in the driver, virtualisation layer, host cache, VMDK or physical device. The root cause of the I/O anomaly remains unconfirmed.

10. Operational investigation runbook

  1. Record impact: affected service, latency/error metrics, scope, start time and workload conditions.
  2. Freeze context: recent changes, concurrent tasks, system/application events, topology, OS version/build, VM and storage configuration.
  3. Capture baseline: collect the minimum relevant counters over a sufficient window, including before, during and after the symptom.
  4. Correlate: align PerfMon, application logs, events, hypervisor, storage and network timestamps; normalise against capacity and workload.
  5. Form a hypothesis: state expected evidence, what would disprove it and the lowest-cost next measurement.
  6. Escalate deliberately: use WPR/WPA, Pktmon or hypervisor/array tools only when counters cannot answer the question.
  7. Validate the fix: compare the same service and subsystem metrics before and after under comparable load.
  8. Preserve evidence: retain BLG/ETL, commands, interval, time zone, build, changes and conclusion under controlled access and retention.
What a technical conclusion should contain

A useful conclusion states the measured symptom, time window, correlated evidence, responsible layer, causal mechanism, relevant exclusions, mitigation and quantified outcome. “High CPU” or “slow disk” are observations, not root causes.

10.1 Exit criteria

Do not close the investigation merely because the server is responsive again. Close it when the service metric returns to the agreed level, subsystem metrics return to a range consistent with baseline, the cause is reasonably demonstrated and the bottleneck has not moved to another layer. If the issue disappeared without sufficient evidence, record the cause as unconfirmed and define the capture needed to resolve a recurrence.
