LLM Inference: Prefill, Decode and KV Cache

Training is complete. A request arrives, and the model must answer. Understanding the real cost of that operation means separating two phases: processing the prompt and generating its continuation. At the centre is a memory structure that avoids repeating part of the work: the Key/Value Cache.

The central question

When we send a prompt, why does the model process all its tokens together but then generate one token at a time? Which calculations can be reused, which cannot, and how does that reusable state translate into GPU memory? We will follow the tensors and validate the mechanism with a small implementation.

1. From training to inference

In the previous chapter, we studied how a decoder-only Transformer adjusts its parameters to increase the probability of the next token. During training, sequences are processed with teacher forcing: each position receives the correct corpus prefix, and a causal mask prevents access to future positions. The loss and backpropagation update the weights.

During inference, the weights are fixed. We receive an input sequence — the prompt — and want to produce a continuation. There is no backward pass and no parameter update. We run a forward pass, obtain logits for the next token, select a token and repeat until a stopping condition is reached.

The distinction sounds simple, but it changes the compute pattern. The prompt may contain hundreds or thousands of tokens that are known before generation begins. Those positions can be processed in parallel while preserving causality. The next output token, however, depends on the token just selected: generation is sequential over time.

LLM serving commonly separates this operation into two conceptual phases:

  • Prefill: process the complete prompt and prepare the attention state needed by later iterations.
  • Decode: incorporate generated tokens, usually one per iteration, while reusing the previous state.

2. The autoregressive loop, step by step

Assume the prompt contains P tokens. The model computes a distribution for the next position and we select the first generated token. That token is appended to the context. The next forward pass uses the previous state and the new token to produce the distribution for the second generated token.

prompt = [x1, x2, ..., xP]

logits_1 = prefill(prompt)
token_1 = sample_or_select(logits_1)

logits_2 = decode(token_1, cache)
token_2 = sample_or_select(logits_2)

logits_3 = decode(token_2, cache)
token_3 = sample_or_select(logits_3)

One timing detail is easy to miss: Prefill already produces the logits used to select the first output token. We do not need to feed that token through the model to predict itself. The first Decode call consumes the token we have just selected to calculate the logits for the following token.

Selection may be greedy, sampling with temperature and top-p/top-k, or a more elaborate algorithm. This policy turns logits into a token, but it does not change the basic cache concept. Cache contents depend on the processed prefix and model, not on whether selection used greedy or sampling.

The loop ends when an EOS token is generated, an output limit is reached, the runtime triggers a stopping condition or the request is cancelled. In batch serving, requests can have different sequence lengths; coordinating those sequences is one of a serving engine's responsibilities, which we will study later.

3. Prefill: processing the known context

During Prefill, the model receives all P prompt tokens. Each layer computes Query, Key and Value projections from hidden representations. Each position may attend to previous positions and itself, never to future positions. A causal mask preserves this property while the framework computes many positions in parallel.

For one attention layer, the projection shapes are conceptually:

input:  X  [B, P, d_model]
Q:      [B, Hq, P, Dh]
K:      [B, Hkv, P, Dh]
V:      [B, Hkv, P, Dh]

B is batch size, P is prompt length, Hq is the number of query heads, Hkv is the number of Key/Value heads and Dh is the dimension per head. In conventional Multi-Head Attention, Hq and Hkv match. With Grouped-Query Attention or Multi-Query Attention, Hkv may be smaller.

The complete prompt passes through the layers. The last position produces the logits used to select the first output token. In addition, each layer retains its K and V tensors so they do not need to be calculated again in following iterations.

Prefill does not mean all operations are independent or that the causal mask disappears. Parallelism is across sequence positions: the attention matrix preserves allowed dependencies through the mask. The cost of dense attention depends on context length and the actual kernel implementation.

4. Decode: one new token, one new query

Once the first generated token is selected, the runtime adds it to the input of the next iteration. The layer computes its new Q, K and V projections. The Query is new and has one position; the available keys and values span the previous prefix plus the current token.

Q_new:       [B, Hq, 1, Dh]
K_all:       [B, Hkv, P + t, Dh]
V_all:       [B, Hkv, P + t, Dh]

scores = Q_new @ transpose(K_all) / sqrt(Dh)
weights = softmax(scores)
context = weights @ V_all

The block output produces logits for selecting the next token. The K and V for the newly processed position are appended to that layer's cache. This happens at every layer. The cache is therefore not one global matrix: it is a collection of K/V states, one for each attention block.

During Decode, the query has length 1, but its keys and values may cover thousands of positions. Each new token attends to a growing context. The cache avoids propagating the already-processed prefix through every layer again; it does not make attention constant-cost with respect to context length.

Why the order matters

If we already have past K and V, we do not need to calculate them again. But we do need a new Query for the current token and must calculate its attention against the accumulated keys. The KV Cache avoids recomputing previous states; it does not remove context reads.

5. What exactly does the KV Cache store?

At every self-attention layer, a hidden representation is projected into three spaces:

  • Query (Q): represents what information the current position is looking for.
  • Key (K): enables compatibility scores between the query and each available position.
  • Value (V): carries the information combined according to attention weights.

In simplified form, attention computes QKᵀ similarities, scales them, applies softmax and uses the result to weight V. Earlier positions' K and V do not change when a new token is appended in a standard causal Transformer with fixed weights: those positions could only depend on their own prefix, which is already known.

That is why they can be stored. In contrast:

  • The model weights are not copied once per token; the same weights are shared by every position.
  • Query is not stored for future reuse: queries belong to specific positions and the next position will produce a different query.
  • The cache is not simply a copy of the prompt text: it contains per-layer, per-head and per-position tensor projections.
  • The cache does not by itself contain every network activation or the full state of the generation process.

The cache is tied to the identity and configuration of the model, the token sequence that produced it and options such as RoPE/positional encoding, dtype, architecture and attention pattern. Reusing it with a different prefix, incompatible model or misaligned positions is invalid.

6. Why the cache avoids so much work

Consider a prompt of P tokens and D Decode inputs. Without a cache, a reference implementation may run the model over the entire prefix again for each new token. The number of positions processed through the model would be:

(P + 1) + (P + 2) + ... + (P + D)

With Prefill and incremental caching, the model processes the initial P positions once and then one position for every Decode input:

P + D

For P=32 and D=32, full-prefix recomputation processes 1,552 accumulated positions, compared with 64 on the incremental path. That is a 95.88% reduction in the structural count of positions. It does not mean an equivalent reduction in FLOPs or latency: each new query still compares against a growing K/V context, and attention cost, memory traffic and kernels depend on the architecture.

The cache opportunity is especially clear in token-by-token generation: without it, old-position projections are repeated at every step. With it, historical projections are retained and only the new position is incorporated.

7. How much space does it use? The memory formula

The trade-off is that storing K and V costs memory. For a homogeneous dense-attention architecture, storage can be estimated as:

KV_bytes =
  2 × L × B × T × Hkv × Dh × bytes_per_element

Where:

  • 2: Key and Value.
  • L: number of layers with attention cache.
  • B: batch size, or the number of sequences maintaining their own state.
  • T: cached context positions.
  • Hkv: number of Key/Value heads.
  • Dh: dimension per head.
  • bytes_per_element: numeric storage size (2 for FP16/BF16, 4 for FP32).

Illustrative example: 32 layers, batch 1, 8 KV heads, head_dim 128 and two bytes per element. Each token needs 128 KiB of K/V. At 16,384 tokens, storage totals 2 GiB, excluding weights, activations, temporary buffers, metadata and allocator fragmentation.

Size grows linearly with T and B. Doubling context or batch doubles cache storage, all else being equal. More layers, KV heads or head dimension increase it as well.

The formula is a sizing baseline, not a universal value. MQA/GQA reduce Hkv relative to Hq; sliding-window attention may limit T in selected layers; hybrid models can mix attention types; and a runtime may allocate blocks, padding or auxiliary structures. Check the actual architecture and storage format before reserving memory.

The cache usually resides in accelerator memory because Decode accesses it repeatedly. Some runtimes support CPU offload or other storage strategies: they reduce VRAM pressure but introduce transfers and latency/throughput trade-offs.

8. Compute-bound Prefill and memory-bound Decode

In many workloads, Prefill processes a substantial number of tokens simultaneously. More matrix work is available and the accelerator can use parallelism more effectively. It is therefore commonly described as the more compute-bound phase.

Decode processes very few new tokens per sequence and iterates through dependent steps. For every token, model weights participate in the forward pass and K/V states for a growing context must be read. At small batch sizes, the operation can be limited more by moving data from memory than by peak arithmetic capability: hence the term memory-bound.

This is a typical characterisation, not a universal law. Batch size, context length, concurrent requests, accelerator, kernels, quantisation, speculative decoding and prefix caching can change the bottleneck. A short prompt with a cached prefix may behave differently; speculative decoding can also change the amount of work per iteration.

The distinction helps explain why an attention-kernel improvement may benefit the phases differently, and why “tokens per second” alone does not explain user experience. First-token latency and inter-token latency are different dimensions.

9. Cache variants and engineering decisions

Dynamic Cache and Static Cache

A Dynamic Cache grows its tensors as tokens arrive. It is flexible for variable-length sequences, but dynamic growth can involve allocations and management overhead. A Static Cache reserves a known capacity ahead of time; it can make compilation and execution with stable shapes easier, but reserves space even while a sequence is short. The choice depends on the runtime, traffic pattern and memory constraints.

GQA and MQA

With Multi-Query Attention, several query heads share one K/V head pair. Grouped-Query Attention groups multiple query heads per KV head. Reducing Hkv lowers cache memory and the volume of K/V that must be stored and read. It is not a free optimisation: it changes the attention design and its representational/cost trade-off.

Sliding window and hybrid architectures

Some layers attend only to a local window. In those layers it may not be necessary to retain every old position: effective cache length can be bounded. Other models mix global and local layers, so memory cannot be estimated accurately by multiplying one homogeneous configuration without checking each layer's attention pattern.

Prefix caching is not the same as a request's cache

The ordinary KV Cache avoids recomputing the prefix within one generation. Prefix caching attempts to reuse states for a shared prefix across separate requests. For example, multiple requests may begin with the same system context or a common document. An engine can identify matching token blocks and share already-computed state, provided model identity, tokens and configuration allow reuse. This is an additional serving layer, not an automatic property of every per-request cache.

Offload, quantisation and paging

Offload moves part of the cache out of VRAM, trading memory for transfers. Quantisation reduces bytes per element but introduces scaling, precision and error decisions that require validation. Paged allocation manages KV blocks to reduce fragmentation and accommodate requests of different lengths. These are complementary techniques, not synonyms for KV Cache. We will go deeper into the engine and its scheduler in the vLLM chapter.

10. Measuring real inference

Before comparing engines or configurations, define which latency is being measured and under what load. Common metrics include:

  • TTFT (Time To First Token): time from request arrival until the system can emit the first token. End-to-end measurement may include queuing and Prefill, depending on instrumentation boundaries.
  • TPOT (Time Per Output Token): average time per generated token after the first, according to the measurement convention.
  • ITL (Inter-Token Latency): time between consecutive tokens, useful for studying smoothness and variability.
  • Throughput: tokens per second; specify whether it counts input tokens, output tokens or both and whether it is per request or aggregate.
  • Concurrency and percentiles: active requests, input/output length distributions, p50/p95/p99 and error rate.

A reproducible test should pin model and revision, tokenizer, hardware, dtype, input/output lengths, batch/concurrency, warm-up, duration, sampling policy and exact metric definitions. Queues and timeouts should also be reported; one isolated call does not represent service behaviour under load.

Chapter 08 will examine benchmarking in depth: TTFT, TPOT, throughput, percentiles, saturation and cost per request. For now, it is enough to distinguish that Prefill conditions the start and Decode the output cadence, although real workloads mix both phases across many requests.

11. Reproduced laboratory: incremental cache vs recomputation

I built a small decoder-only Transformer in PyTorch with three layers, four attention heads and a model dimension of 64. Its weights are random: the purpose is not to generate convincing language but to isolate tensor flow and verify that the incremental path is equivalent to recomputing the entire prefix.

13. Common Decode implementation mistakes

  • Recomputing the entire prefix: it works as a baseline but wastes projections and activations that were already computed.
  • Forgetting to append K/V: a cache that is not updated makes the model ignore recently generated tokens.
  • Misaligning positions: with RoPE or positional embeddings, the new token must receive its correct absolute or relative position; restarting every call at position zero changes the result.
  • Applying the wrong causal mask: for a query of length one and long K/V, a non-square mask can have unexpected alignment. The lab attends to every cache entry because they are all past or current, never future.
  • Confusing Hq and Hkv: GQA/MQA may have fewer KV heads than query heads. Cache shapes must not always assume they match.
  • Mixing incompatible requests: reusing cache with another model, tokenization, prefix or positional configuration can invalidate the state.
  • Sizing only for weights: in long contexts and high batch sizes, KV Cache may become a dominant part of serving memory.
  • Comparing non-equivalent metrics: TTFT, aggregate throughput and per-request latency are not interchangeable.

14. What the laboratory does and does not show

The experiment shows that, for this teaching model and within the specified numerical tolerance, Prefill and incremental Decode reproduce the logits obtained by recomputing each full prefix. It also validates cache shape and memory accounting.

It does not demonstrate GPU acceleration, lower latency in a real engine, generation quality, production throughput, scalability, GQA/MQA behaviour, quantised-cache accuracy or statistical advantages across architectures. The weights are random and the model has not been trained.

Verifiable conclusion

The KV Cache retains the keys and values computed by each layer for already-processed positions. Decode appends K/V for the new position and computes a new Query against the accumulated context. In the lab, this path matches full-prefix recomputation within 2 × 10⁻⁵ and avoids reprocessing old positions. The trade-off is memory proportional to context, batch, layers and number of KV heads.

15. What comes next
