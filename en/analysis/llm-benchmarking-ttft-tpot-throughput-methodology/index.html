LLM Benchmarking: TTFT, TPOT, Throughput and Reproducible Methodology

A server claims 180 tokens per second. Is that fast? The number does not answer the question. Are those input or output tokens? Per request or aggregated across the fleet? With which prompt, generation length, concurrency, cache policy, queue latency and error rate? Did we measure the user response or just a kernel? This chapter builds a methodology for benchmarking an LLM system as a system: from the first unit of work to the final token, under defined workloads, with statistical caveats and repeatable evidence.

The chapter thesis

There is no single number called “LLM performance”. Results depend on the model, hardware, runtime, prompt, output, arrival process, concurrency, caching policy, streaming behaviour, timing boundaries and success criteria. A valid benchmark publishes that configuration and retains per-request samples. Without a workload and clear measurement boundaries, an isolated tokens/s figure is incomplete telemetry, not an engineering comparison.

1. What question does an LLM benchmark answer?

A benchmark does not start by running a tool. It starts by defining the decision. Selecting a model for an interactive assistant differs from sizing a bulk-generation API, RAG service, structured-extraction endpoint or agent backend that chains multiple calls.

At least four questions need separate answers:

  • Experience: how long does a user wait for the first content, and what generation pace follows?
  • Capacity: how many requests, input tokens and output tokens can the system complete for a defined traffic mix?
  • Reliability: what fraction completes successfully and meets the latency SLO?
  • Economics: what does it cost to deliver useful work while meeting that SLO?

A testable question would be: “What is the highest arrival rate that keeps TTFT p95 below 800 ms, TPOT p95 below 60 ms, errors below 0.5%, and task quality acceptable on our evaluation set?” “Which model is faster?” does not specify a use case or measurement boundary.

Keep performance separate from quality. A server may emit tokens quickly while producing incorrect, incomplete or unsafe answers. Quality requires another evaluation set (accuracy, task success, groundedness, tool success) and should accompany performance measurements. Quantization, context limits and sampling changes can alter quality, so record them.

2. Three measurement planes: client, server and hardware

PlaneWhat it observesWhat it answersWhat it cannot prove alone
Client / black-boxSchedule, HTTP send, received stream, completion and errors.End-to-end experience of the API consumer.Which internal component caused the latency.
Server / runtimeQueue time, prefill, decode, scheduler, batches and KV Cache.What the engine does and where it waits.The exact latency perceived beyond the server.
Hardware / systemGPU utilisation, HBM, SM, PCIe/NVLink, NIC, CPU, memory and power.Which resource may be saturated or underused.Answer usefulness or user experience.

The primary service benchmark should be measured at the client. Runtime and hardware telemetry explain the result. Server-side TTFT can be good while client TTFT is worse because of load-generator queueing, serialization, gateway, transport, TLS, network or stream buffering.

Keep client measurements per request and, where possible, correlate them with internal traces through a request ID. Do not add overlapping components or values from unsynchronised clocks. Two metrics called “TTFT” may start and finish at different points.

3. TTFT, ITL, TPOT and E2E: put each clock in the right place

Time To First Token (TTFT)

For a client-side streaming benchmark, TTFT is the time from the actual request send until the first event containing generated content is received:

TTFT_client = first_content_received_at - request_sent_at

It includes transmission, gateway, server queue, tokenization/preparation, Prefill, first Decode step and return of the first chunk. It is not a kernel execution time or isolated Prefill duration.

Define “first token” precisely. APIs may send HTTP headers, status events, metadata, an assistant role or empty chunks first. Those are not necessarily visible content. Record the first non-empty content event and document the stream parser. With non-streaming responses, a client cannot reliably observe TTFT; it only knows full response time.

Inter-Token Latency (ITL)

ITL is the interval between consecutive content events in a stream:

ITL_i = content_event[i].received_at - content_event[i-1].received_at

When exactly one token is emitted per chunk, the interval approximates the gap between delivered tokens. A chunk may contain multiple tokens; speculative decoding, buffering or server-side coalescing changes the relation between an event and a token.

Time Per Output Token (TPOT)

In the vLLM serving-benchmark convention, TPOT is calculated per request:

TPOT_request = (E2E - TTFT) / (output_tokens - 1)

It is defined only when more than one token is generated. It is an amortised average of the interval after the first token, not the latency of each individual token. Calculate TPOT per request first, then summarise its distribution; do not subtract global averages and divide by an average output length.

Conceptual example: TTFT = 100 ms, E2E = 180 ms and output = 5 tokens. The period after the first token is 80 ms, so TPOT = 80/(5−1) = 20 ms. If the client sees two 40 ms gaps because the second event carries three tokens, event ITL is 40 ms and amortised TPOT is 20 ms. Both are correct; they answer different questions.

End-to-End latency (E2E)

In this chapter E2E is the time from actual send until the client considers the response complete:

E2E_client = response_completed_at - request_sent_at

Document whether completion means the last content chunk, terminal protocol event, stream close or full body completion. Do not mix logical completion with TCP closure without saying so.

Time To First Byte (TTFB), Time To First Output (TTFO), server TTFT and model execution time appear in different tools. Do not assume they are synonyms. Publish the formula and boundary. The vLLM Benchmark CLI distinguishes TTFT, ITL and TPOT and explains why ITL and TPOT diverge when a chunk carries multiple tokens.

4. Throughput: tokens/s is not one metric

Throughput measures completed work per unit time. LLM serving requires identifying which tokens and which interval are counted:

request_throughput = successful_requests / measurement_window_seconds
output_token_throughput = generated_output_tokens / measurement_window_seconds
input_token_throughput = accepted_input_tokens / measurement_window_seconds
total_token_throughput = (input_tokens + output_tokens) / measurement_window_seconds

Requests/s measures completed requests. Output tokens/s measures generated tokens across the entire system. Input tokens/s reflects Prefill work. Total tokens/s combines both, but can hide the Prefill/Decode split. State whether tokens from failed, cancelled or rejected requests are included. This lab counts tokens from successful requests for throughput and retains failures for error-rate calculation.

A user's generation pace is not the server's aggregate throughput. The inverse of ITL or TPOT approximates a per-sequence emission rate under specific conditions. Output tokens/s aggregates tokens across active sequences. A server can generate 2,000 output tokens/s while each user receives 25 tokens/s. There is no contradiction.

The measurement window must be explicit. A fixed-duration test may run from the measured phase start through the drain period (when admitted requests finish). This lab uses the earliest scheduled arrival until the final completion: it includes drain and excludes warmup. Other tools may use different windows.

The same output tokens/s can come from many short responses or a few long ones. Publish request/s, input tokens/s, output tokens/s and length distributions.

5. Latency decomposition: client queue, server queue, Prefill and Decode

planned arrival
  └─ client queue / rate limiter
      └─ actual HTTP send
          └─ network / gateway / ingress
              └─ server scheduler queue
                  └─ Prefill
                      └─ first Decode / first content
                          └─ incremental Decode + stream delivery
                              └─ terminal event / completion

The client may delay a send because it reached its concurrency limit. That is client queue, not server latency. The internal runtime queue begins after sending and before the sequence enters execution. Prefill processes the prompt; Decode produces subsequent tokens.

vLLM distinguishes benchmark-client queue time from server scheduler queue time. With per-request metrics enabled, server-side values help estimate which portion of TTFT belongs to the scheduler/runtime. Client TTFT still includes transport and additional overhead. Per-request instrumentation can add overhead; use it diagnostically and disclose it.

A decomposition is additive only when intervals are non-overlapping and clocks are comparable. If client TTFT already includes server queue and prefill, adding them again creates fictional latency. Client/server correlation requires synchronised clocks or correlated spans.

6. Workload design: distributions matter more than averages

A test with random 128-token prompts and 32-token outputs may compare a controlled micro-configuration, but does not automatically represent an assistant with history, RAG documents, system instructions, tool calls and long answers.

Document five dimensions:

  • Input: prompt-token distribution (p50/p90/p99), system prompt, history, retrieval context, long documents and repeated-prefix share.
  • Output: output-token distribution, stop sequences, max_tokens, short/long answers and truncation.
  • Request mix: chat, classification, JSON extraction, summarisation, RAG, tool calls, reasoning, multimodal and streaming, with declared proportions.
  • Model contract: exact checkpoint revision/commit, tokenizer, chat template, sampling and API version.
  • Cache contract: prefix caching, KV reuse, cold/warm state, prompt reuse and reset policy.

Context length is a structural variable. Long prompts increase Prefill work and KV Cache occupancy; many long active sequences can reduce effective concurrency due to memory pressure. Output length increases request occupancy. Build separate profiles: short chat, long-context RAG, long generation, mixed production traffic and stress tests.

Do not use one average as a substitute for a distribution. Two workloads can both average 1,000 input tokens while one clusters around 1,000 and the other mixes 100 with 10,000. Queueing, KV and tail latency will differ.

Random prompts isolate length, but may not preserve semantics, tokenization or shared prefixes. When using a dataset, record its origin, licence, hash, tokenizer, anonymisation, sensitive-data filtering and transformations.

7. Open-loop, closed-loop and coordinated omission

Closed-loop: concurrency-controlled

A closed-loop client sends a request, waits for completion and then sends the next one. If latency doubles, that client automatically lowers its arrival rate. The generator offers less load precisely when the system degrades. This is useful for modelling active users who wait for a response, but can hide what happens when external arrivals continue independently.

Open-loop: arrival-rate-controlled

In open-loop tests, arrivals are scheduled at a target rate independently of previous request completions. If the system cannot sustain it, queues, generator delays, rejections or timeouts grow. This is useful for APIs receiving independent external traffic.

Open-loop does not mean unlimited traffic or ignoring backpressure. Use a rate scheduler, resource limits and explicit overload policies. Record scheduled arrivals and actual sends: if the client cannot sustain the rate, the benchmark did not maintain offered load.

Coordinated omission

Coordinated omission occurs when a generator stops creating samples during a slow period. Measuring only requests it manages to send can omit the time when work would have accumulated. p99 then looks better because requests are missing. An arrival process independent of completion reduces this bias when the generator can sustain the schedule and reports its own queueing.

Common profiles:

  • Constant rate: deterministic spacing; easy to compare configurations.
  • Poisson-like: independent stochastic arrivals, useful for some aggregate traffic models.
  • Gamma / burstiness: controls arrival clustering and variability.
  • Bursts: deliberate spikes to test admission control, queueing, autoscaling and recovery.
  • Concurrency cap: maximum in-flight requests, which may create client-side wait.

A fixed rate of five requests per second is not the same as five concurrent clients: as requests take longer, closed-loop clients complete fewer requests per second. Record arrival rate, concurrency, temporal distribution and backpressure. vLLM and NVIDIA AIPerf expose controls for request rate, concurrency and arrival patterns; verify flags against the installed version.

8. Concurrency, saturation and goodput: find the operating region

At low load, increasing concurrency often improves throughput: more sequences fill batches and keep the GPU busy. Eventually resources saturate. Beyond that point, throughput may barely rise while queues and p95/p99 latency grow sharply. This change in slope is the saturation knee.

The output metric should not be “the highest observed tokens/s”, but the highest offered load the system sustains while meeting the SLO and error budget. This article uses an operational goodput definition:

goodput_requests_per_second =
  successful requests that satisfy all latency SLOs
  / measurement_window_seconds

A request is good only when it satisfies every declared condition, for example TTFT ≤ 800 ms, TPOT ≤ 60 ms and E2E ≤ 8 s. The error limit is calculated over received or scheduled requests according to a stated policy. These thresholds are examples, not universal recommendations.

Goodput can be defined per token or completed task, but the denominator and success criteria must be explicit. Goodput is not output tokens/s. A long response that violates TTFT may increase throughput while reducing operational usefulness.

Little's Law, L = λW, relates average requests in the system (L), average arrival rate (λ) and average time in system (W) under stable conditions. It helps reason about queues but does not replace percentile measurement, and should not be applied casually while the system changes regime or an unbounded queue grows.

9. Percentiles and statistics: p99 needs samples

The mean summarises the centre, not the tail. A pleasant p50 can coexist with a p99 that causes timeouts. Publish p50, p90, p95 and p99 for TTFT, ITL/TPOT and E2E, alongside errors, requests/s and output tokens/s. Maximum latency can help debugging but is sensitive to one outlier.

A sample p99 is not automatically an accurate estimate of the true percentile. With 100 requests, the slowest 1% is roughly one sample; with 1,000 it is roughly ten. Retain raw observations, sample size, interpolation method and repetitions. For rigorous decisions, add confidence intervals or bootstrap and document the method.

There is no universal magic request count for p99. Precision depends on variability, distance from the SLO and desired confidence. MLPerf demonstrates how formal tail estimates can require large sample sizes under its own statistical rules; those rules are not a universal minimum for every service.

Do not average p99 values across machines, workers or runs to produce a fleet p99: quantiles are not additive. With compatible histograms, aggregate buckets and calculate a quantile on the combined histogram, or collect per-request observations under the same definition. Prometheus documents histograms and histogram_quantile().

Repeat independent runs. Report variation between runs, not just a favourable execution. If the observed effect is smaller than system noise, it is not a robust basis for an architectural change.

10. Reproducible protocol: the benchmark needs a manifest

GroupFields to record
ModelName, revision/hash, tokenizer revision, chat template, quantization, dtype, context and limits.
HardwareGPU SKU/count, memory, topology, CPU, RAM, NIC, driver, firmware and power mode.
SoftwareOS/kernel, runtime, commit, Python, PyTorch, CUDA, NCCL, driver and libraries.
ServingTP/PP/DP, max model length, max sequences, scheduler, batching, prefix cache, KV dtype and chunked prefill.
RequestDataset/hash/licence, input/output length, stop, sampling, streaming, tool calls and traffic mix.
Load generatorVersion, request rate, arrival pattern, concurrency, timeout, retries, warmup and request count.
MeasurementTiming boundary, clock, percentile, aggregation, window, drain, errors and client/server metrics.
OperationsThermal state, co-tenancy, background load, network, cache state, date, time and run number.

Sequence:

  1. Freeze: pin model, runtime, hardware and dataset revisions; calculate hashes.
  2. Warm up: initialise kernels, graph capture, caches and connections. Keep warmup out of headline samples.
  3. Settle: allow the system to reach the intended state; record autoscaling and cache changes.
  4. Measure: generate the declared load and capture stream, errors and server metrics.
  5. Drain: finish admitted requests; count timeouts, rejections and incomplete work.
  6. Repeat: run independent repetitions and change one variable at a time.
  7. Publish: retain raw CSV/JSON, manifest, logs, scripts and limitations.

Warm and cold cache are valid scenarios, but must not be mixed. For prefix caching, design one test with shared prefixes and another without. vLLM warns that repeated benchmarks with similar inputs can increase prefix-cache hit ratio and artificially improve results; its docs describe cache resets and sweep runs that clear caches between repetitions. Cache policy is part of the workload.

A minimal JSON manifest:

{
  "model": "model-name",
  "model_revision": "commit-or-sha256",
  "runtime": "vllm-x.y.z",
  "hardware": ["gpu-sku x 4"],
  "precision": "bf16",
  "parallelism": {"tensor": 4, "pipeline": 1},
  "cache": {"prefix": false, "state": "cold-per-run"},
  "workload": {"dataset_sha256": "...", "arrival": "poisson", "request_rate": 5},
  "measurement": {"warmup_requests": 50, "measured_requests": 1000, "streaming": true}
}

The values are illustrative, not a recommended configuration. A real benchmark must complete the manifest with verifiable data.

11. Practical benchmarking with vLLM

vLLM provides separate commands for API serving and offline throughput. They are not equivalent: bench serve observes an endpoint from a benchmark client; bench throughput focuses on generation inside the process and does not by itself reproduce the network, gateway and API path seen by a user.

Start a server

vllm serve MODEL_ID --enable-per-request-metrics

Use a model you can access under terms that permit the test. Pin its revision and configuration. Per-request instrumentation helps diagnosis, but also run a headline measurement with minimal overhead.

Send load through the endpoint

vllm bench serve \
  --backend openai \
  --endpoint /v1/completions \
  --model MODEL_ID \
  --dataset-name random \
  --random-input-len 1024 \
  --random-output-len 256 \
  --num-prompts 200 \
  --request-rate 5 \
  --max-concurrency 32 \
  --save-result \
  --save-detailed \
  --result-dir ./results

The random dataset fixes lengths and is useful for controlled engine tests. It is not a real conversation workload: it does not model semantic distribution, shared prefixes or necessarily the application's tokenizer/template. Backend, endpoint and flags can change; run vllm bench serve --help for the installed version and retain that output.

To explore capacity, sweep request rates or concurrency limits without simultaneously changing the model and configuration. vLLM benchmark sweeps help explore the trade-off between load, throughput and SLO latency. See vLLM Benchmark Sweeps.

Save raw per-request results, token lengths, request IDs, TTFT/ITL/TPOT/E2E, request rate, max concurrency, client queue and completed request count. In a separate diagnostic run, enable server queue, prefill/decode and KV metrics.

An offline benchmark answers “how much throughput does the model generate under this backend?” It does not answer “what does a user experience through our API gateway under load?” For that, measure the actual client path.

12. AIPerf and MLPerf: tools versus a standard

NVIDIA AIPerf

AIPerf is NVIDIA's GenAI benchmarking tool. Its metric reference describes TTFT, ITL, output-token throughput and total-token throughput. It supports request-rate or concurrency-controlled load and patterns such as constant, Poisson/Gamma and bursts. It is useful for compatible endpoints; record the version because flags, output formats and profiles evolve.

MLPerf Inference

MLPerf Inference from MLCommons is a standardised benchmark with models, datasets, scenarios, execution rules and reporting policies. Scenarios include SingleStream, MultiStream, Offline and Server; Server models online arrivals under benchmark-defined latency constraints. Official comparisons follow specific rules, not arbitrary local runs.

MLPerf answers “how does a submission perform under a standard specification?” An internal benchmark answers “how does my service perform with my traffic and SLOs?” Both are valuable, but not interchangeable. Dataset, scenario, harness, rules and validation are part of the result.

13. Observability: client, server and GPU metrics

The headline table should be client-side. A diagnostic dashboard complements, rather than replaces, that view. vLLM documents, among others, these runtime metrics:

vllm:time_to_first_token_secondsServer-side distribution of time to first token.
vllm:inter_token_latency_secondsInter-token/stream intervals under runtime instrumentation.
vllm:request_time_per_output_token_secondsAmortised output-token time per request.
vllm:e2e_request_latency_secondsTotal request latency measured by the runtime.
vllm:request_queue_time_secondsTime waiting in the scheduler.
vllm:request_prefill_time_seconds / vllm:request_decode_time_secondsPrefill and Decode duration within that version's boundaries.

Names, labels and availability depend on version and mode. Review vLLM Metrics and validate the installed /metrics endpoint.

Correlate latency with GPU utilisation, SM activity, HBM bandwidth/usage, allocated memory, KV cache occupancy, clocks, thermal throttling, CPU, RAM, PCIe/NVLink and NIC. A GPU at 100% is not automatically the cause; correlate it with queues and phases. A GPU at 30% may indicate memory, CPU, synchronisation or small-batch limits.

Also record admission rejections, HTTP status, cancellations, timeouts, retries, context rejections, preemptions and cache hits/misses. If retries are enabled, count both the logical user request and each server attempt to avoid inflating throughput or hiding failures.

OpenTelemetry GenAI conventions include names for TTFT and output-token time. The reviewed documentation marks this set as development status; treat it as evolving and pin the adopted revision. Do not present it as a universally stable contract.

14. Prometheus histograms: aggregate percentiles correctly

For classic Prometheus histograms, a typical query to approximate end-to-end p99 across instances is:

histogram_quantile(
  0.99,
  sum by (le) (
    rate(vllm:e2e_request_latency_seconds_bucket[5m])
  )
)

Adapt the metric name, labels and window to the version. The correct operation aggregates compatible buckets before calculating the quantile. Calculating p99 per worker and averaging those p99 values does not produce fleet p99. Histograms retain resolution only at their bucket boundaries; choose buckets for the operating range and tail of interest.

Do not turn request IDs, prompt text, users or tokens into metric labels: they create high cardinality and can expose data. Use aggregated metrics for trends and sampled traces/logs for individual requests. Define retention and sensitive-data redaction.

The question is not only “which metric got worse?” but “at which boundary does the delay start?” A poor TTFT p99 may come from a minority of very long prompts; average input tokens will not reveal it. TPOT can change with batch composition, lengths, quantization or concurrency.

16. Long context, prefix cache and continuous batching

Increasing input length raises Prefill work and KV Cache occupancy. The ability to admit new sequences may fall even if a phase's token throughput rises. A prefix-cache hit can also benefit a long prompt much more than a short one.

Continuous batching admits new sequences as others finish; it is not the same experiment as a closed static batch. Record running/waiting requests, preemption, KV block pressure, prefix-cache hits and active sequence counts.

  • Cold cache: no reused prefixes, cache reset according to a declared method.
  • Warm prefix: repeated instructions/prefixes with caching enabled.
  • Long prompt: high input tokens and fixed output to isolate Prefill.
  • Long decode: fixed prompt and long output to study generation and occupancy.
  • Mixed: production-like distribution with variable lengths.

Specify max_model_len, max_num_seqs, KV dtype, block size, chunked prefill, speculative decoding and scheduler/cache settings that affect the result.

17. Cost per request and per million tokens

Performance and cost must be compared under the same workload contract. A simple direct compute-cost estimate is:

compute_cost =
  gpu_hour_rate × gpu_count × measured_runtime_seconds / 3600
cost_per_1M_output_tokens =
  compute_cost × 1,000,000 / successful_output_tokens

This is not total service cost. It excludes idle capacity, amortisation, electricity, CPU, RAM, storage, networking, load balancers, observability, licensing, support and operations. Autoscaling, granular billing or shared GPUs require additional attribution.

Separate cost per million output tokens from cost per million total tokens. Add cost per request and, preferably, cost per correct task within the SLO. A cheap system that returns invalid answers or misses latency targets may be worse than one with higher unit cost.

The lab accepts --gpu-hour-cost and --gpu-count as operator-supplied values; it does not query prices or account for hidden costs. Synthetic fixture output is not an LLM cost per token.

18. Reproduced lab: analyse your own traces with the Python standard library

This chapter takes a different approach from earlier labs: it does not simulate kernels or run a tiny LLM. It implements an analyser for client-observed traces. Learn with synthetic data, then feed the same program CSV exports from a real benchmark.

Scope and cost

Python standard library, CPU-only, no PyTorch, Transformers, vLLM, CUDA, GPU, external API, model download or paid service. Cost: €0. Default records are synthetic to validate formulas; they are not model, engine, GPU or network benchmarks.

Run the lab

Expand-Archive .\llm-benchmarking-08-lab.zip -DestinationPath .\llm-benchmarking-08
cd .\llm-benchmarking-08
.\run.ps1

Or run python .\src\run_lab.py directly.

The fixture uses a fixed seed and two arrival scenarios (steady and bursty), each with 48 synthetic requests. It includes deliberate failures, variable lengths and stream events that sometimes carry multiple tokens in one chunk.

Import your own CSV files

python .\src\run_lab.py --requests C:\bench\requests.csv --events C:\bench\token-events.csv --output .\reports-real --slo-ttft-ms 500 --slo-tpot-ms 80 --slo-e2e-ms 5000

The request CSV requires request_id, scenario, scheduled_ms, sent_ms, first_token_ms, completed_ms, prompt_tokens, output_tokens and status. Timestamps must share one monotonic clock and use milliseconds. first_token_ms may be blank for failures before first content. Optional server_queue_ms, server_prefill_ms and server_decode_ms remain separate from client-plane observations.

The stream-event CSV requires request_id, chunk_index, received_ms and tokens_in_chunk. Indexes must be contiguous; the first event must match first_token_ms; summed chunk tokens must equal output_tokens. ITL measures event gaps and does not invent timestamps inside multi-token chunks.

Outputs

  • request-metrics.csv: per-request latency and derived metrics.
  • itl-samples.csv: gaps between consecutive stream events.
  • metrics.json: overall and per-scenario metrics.
  • lab-report.md: readable summary and interpretation limits.
  • data/manifest.json: fixture provenance and seed.

The analyser computes TTFT, TPOT, ITL, E2E, client queue, optional server queue/prefill/decode fields, request throughput, input/output/total token throughput, maximum in-flight concurrency, error rate and goodput. Percentiles use R-7 linear interpolation. It does not produce confidence intervals for p99.

Verification fixture results

On Python 3.12.10, the run completed 20/20 PASS checks. The fixture contains 96 requests: 92 successful and 4 timeouts; its synthetic window is 32.953 seconds, calculated output throughput is 70.645 tokens/s and maximum observed concurrency is 11.

These figures validate the analyser, not LLM performance. They come from a locally generated trace; no model, inference server, GPU or API is involved. The practical value is that the import format and formulas can be used on real observations without changing the core program.

The optional cost output uses a GPU-hour rate supplied by the operator and calculates direct cost during the window; it does not include amortisation, infrastructure or idle capacity.

19. Runbook: before, during and after

Before

  1. Define the decision, quality gate, SLO and primary metric.
  2. Pin the model, tokenizer, chat template, runtime and hardware.
  3. Build a representative dataset and document privacy/licensing.
  4. Verify that the load generator can sustain the target rate without becoming the bottleneck.
  5. Define warmup, cache mode, request rate, concurrency, timeout and repetitions.

During

  1. Record actual schedule and send times, request ID and result.
  2. Measure client-side TTFT, ITL, TPOT and E2E.
  3. Collect versioned server and GPU metrics.
  4. Include errors, rejections, cancellations and timeouts.
  5. Record cache state, queues, batches and token-length distributions.

After

  1. Wait for drain and close the measurement window.
  2. Validate event, token and timestamp integrity.
  3. Calculate per-request percentiles; do not average worker percentiles.
  4. Repeat and compare variation.
  5. Report the saturation frontier and maximum SLO-compliant goodput.
  6. Publish raw data, manifest, scripts, results and limitations.

20. Conclusions and closing LLM Engineering

An LLM benchmark is meaningful only when workload, timing boundary and success criteria are defined. TTFT measures time to first content; ITL measures gaps between stream events; TPOT amortises generation time; E2E measures the complete request cycle. Requests/s, input tokens/s, output tokens/s and total tokens/s describe different capacities. Percentiles expose tails; goodput connects capacity to SLOs.

Open-loop and closed-loop represent different arrival models. Length distributions, prefix cache, continuous batching and long context change the workload. Server and GPU metrics explain symptoms, but primary user experience belongs at the client boundary. Cost is comparable only when divided by valid work and exclusions are declared.

A reproducible result retains versions, manifest, traces and code. A p99 without sample size, output TPS without a measurement window or a benchmark that omits failures should not size a service. Define the workload first, measure second, explain the evidence last.
