Distributed LLM Inference: Tensor Parallelism, Pipeline Parallelism and NCCL

One GPU runs out of room. The solution seems simple: add more. But a distributed LLM is not a model that magically gets faster when accelerators are connected. We must decide which dimension to partition, which tensors remain replicated, which data moves between ranks, which collectives synchronize each layer and which physical links carry those bytes. This chapter moves from the algebra of a Linear layer to the multi-node topology that determines whether eight GPUs collaborate or spend their time waiting for the network.

The central idea

Distributed inference is not about dividing the GPU count by the model size. It is about choosing a tensor layout and an execution topology. Tensor Parallelism divides computation inside layers; Pipeline Parallelism divides model depth; Data Parallelism replicates the model to distribute requests. Each strategy moves different data and has a different cost. Physical interconnect is part of the design, not an infrastructure detail to solve afterwards.

1. Why distribute: capacity, latency and throughput are different goals

In previous chapters we reduced weight precision through quantization and learned how vLLM manages KV memory and requests with Continuous Batching. Even so, a model may not fit on one GPU, may consume too much memory to retain enough KV Cache, or may fail to meet a throughput target. Distributed inference lets us split weights, operations or request load across accelerators.

Keep three goals separate:

  • Capacity: the model or its state does not fit on one GPU. The priority is to store a fraction of the model on each device and make inference possible.
  • Latency: we want to reduce one request's response time. Parallelism can accelerate matrix operations, but it introduces communication and synchronization. Not every strategy reduces end-to-end latency.
  • Throughput: we want to serve more tokens or requests per second. We can gain throughput by overlapping independent work, replicating models or keeping several pipeline stages busy.

A strategy can solve Capacity without improving Latency. Pipeline Parallelism, for example, can let a model that does not fit on one device run across several, but one sequence still has to traverse every stage. Throughput benefits appear when enough independent requests can occupy the pipeline.

The first criterion remains simple: if the model fits on one GPU and meets the SLO, do not add distributed execution just because more accelerators are available. Process management, networking, failure recovery and observability are operational costs too. The current vLLM guide recommends starting with one GPU when sufficient, using TP within a node when the model requires several GPUs, and combining TP/PP when scaling across nodes. vLLM — Parallelism and Scaling.

2. Parallelism axes: not every strategy splits the same thing

StrategyWhat it splitsWhat it replicatesPrimary goal
Tensor Parallelism (TP)Weight and operation dimensions inside a layer.Parts of activations or intermediate results, depending on layout.Distribute large matrices and weight memory.
Pipeline Parallelism (PP)Consecutive model layers across stages.Each stage's work across different microbatches.Distribute model depth and memory across devices.
Data Parallelism (DP)Batch or requests across replicas.The complete model on every replica.Scale the number of concurrent requests.
Context Parallelism (CP)Sequence/context dimension.Model and parts of state depending on implementation.Process long contexts across devices.
Expert Parallelism (EP)Expert networks in a Mixture-of-Experts model.Router and shared components according to architecture.Distribute dynamically activated experts.

For serving a dense LLM replica, TP and PP are the main axes for splitting one model. DP usually operates on another dimension: several independent replicas receive different requests. CP appears when context is so long that distributing the sequence becomes useful. EP matters for MoE models, where routing introduces All-to-All communication and traffic between experts.

Do not confuse Model Parallelism with Data Parallelism. With TP/PP, one inference needs ranks to collaborate to produce the next token. With DP, a request normally executes on one replica; it does not synchronize its weights with other replicas for every token.

3. Rank, local rank, world size and process groups

In distributed execution, each participating process receives a global identifier called a rank. The total number of participating processes is the world size. In multi-GPU systems, one process often controls one GPU, although exact mapping depends on the runtime. Local rank identifies its position within a node. It is not the same as a physical GPU index, and rank 0 must not be assumed to map to GPU 0.

A process group defines which ranks collaborate in an operation. This matters when TP, PP and DP are combined. In a 2D TP×PP mesh, each pipeline stage can contain a TP group. Layer collectives run inside the appropriate group, while activations move point-to-point to the next stage.

world_size = TP × PP × DP

global_rank = rank in the entire job
local_rank  = rank within a node
tp_group    = ranks that shard one layer
pp_group    = ranks that own consecutive model stages
dp_group    = independent model replicas

This formula is a simplification of a standard rectangular device mesh. Context Parallelism and Expert Parallelism add more dimensions and groups. In heterogeneous or non-uniform layouts, the mapping must be documented explicitly.

A common error is creating groups with a different order on different processes. Collectives must be called compatibly by all ranks in the participating group. NCCL specifies that count and datatype must match across participants; a mismatch can cause hangs, crashes or data corruption. NCCL — Collective Operations.

4. Linear layer mathematics: column-wise and row-wise sharding

Start with a linear layer:

Y = X W

X ∈ R[B,H]
W ∈ R[H,O]
Y ∈ R[B,O]

With TP=P, there are two main partitions. For simplicity, assume O and H can be divided evenly by P. Real models have additional constraints involving head count, head dimension, alignment and kernels.

Column-wise Parallel Linear

Split W by columns, along the output dimension:

W = concat(W₀, W₁, ..., Wₚ₋₁) along output dimension
Yᵢ = X Wᵢ

Y = concat(Y₀, Y₁, ..., Yₚ₋₁)

Each rank receives input X and computes a slice of output features. If the next operator can consume the sharded result, we can avoid reconstructing the full tensor immediately. When a replicated output is required, the shards must be gathered, for example with AllGather. Communication can be deferred until the layout actually requires it.

Row-wise Parallel Linear

Split W by rows along the input dimension. X is divided compatibly:

X = concat(X₀, X₁, ..., Xₚ₋₁) along hidden dimension
W = concat(W₀, W₁, ..., Wₚ₋₁) along input dimension

Yᵢ = Xᵢ Wᵢ
Y = sum(Y₀, Y₁, ..., Yₚ₋₁)

Each rank computes a partial contribution to the output. The contributions must then be reduced and combined. The common form is AllReduce when every rank needs the complete result; a ReduceScatter/AllGather combination may fit better when the next operator keeps a sharded layout.

PyTorch exposes primitives such as ColwiseParallel and RowwiseParallel through DTensor. The API declares input and output layouts and manages communication operations required to connect modules. PyTorch — Tensor Parallel.

5. Tensor Parallelism inside a Transformer

A dense Transformer block contains attention projections and a Feed Forward Network (FFN). Exact dimensions vary by architecture, but a common sharding pattern looks like this:

OperatorTypical shardingReasonFrequent communication
Q, K, V projectionsColumn-wiseDistribute heads or head groups across ranks.Sharded output can stay local until the next operator.
Attention output projectionRow-wiseCombine local head contributions.AllReduce or equivalent layout transition.
MLP gate / up projectionsColumn-wiseDistribute intermediate features.Sharded activations.
MLP down projectionRow-wiseSum contributions from intermediate dimensions.AllReduce or ReduceScatter.

In a gated MLP, gate and up projections can run in parallel on local shards; activation and element-wise multiplication are then applied before the down projection. PyTorch documents this pattern with w1/w3 column-wise and w2 row-wise, allowing the AllReduce to be placed after the combination rather than after every individual Linear operation.

Attention adds constraints. If there are Hq query heads and TP=P, the usual strategy distributes heads across ranks. Hq must be compatible with the parallel degree, or the runtime needs a specific strategy. Grouped Query Attention and Multi-Query Attention reduce KV head count; if KV heads do not divide evenly across ranks, some implementations replicate groups or restrict supported combinations. Do not assume TP=8 works with any checkpoint just because eight GPUs exist.

Weights are not the only tensors involved. Activations, heads, logits, embeddings and KV state are distributed too. Sharding must be designed end-to-end to avoid unnecessary Gather/Scatter operations between modules. PyTorch DTensor and Megatron Core document different layout conventions; not every runtime follows exactly the same path.

6. NCCL collectives: what data actually moves

NCCL is a GPU-optimized collective communication library for NVIDIA devices. It provides operations where several ranks exchange or reduce buffers. It is not an inference scheduler, node orchestrator or a replacement for the runtime that creates processes and assigns models. Frameworks such as PyTorch and engines such as vLLM use a runtime layer plus low-level collectives to coordinate devices.

CollectiveWhat it doesResult on each rankTypical use
AllReduceReduces buffers from all ranks (SUM, MAX, etc.).Every rank receives the complete result.Sum partial outputs from a row-wise operation.
AllGatherConcatenates shards from all ranks.Every rank receives the concatenated tensor.Rebuild features or sequences when a module needs the full tensor.
ReduceScatterReduces buffers and distributes equal result chunks.Each rank keeps one shard of the reduced result.Sharded layouts and Sequence Parallelism.
BroadcastOne root rank distributes the same buffer.Every rank receives a copy.Initialization or data/control distribution.
AlltoAllEach rank sends a different chunk to every destination.Each rank receives one chunk from every source.Expert Parallelism and token dispatch to experts.
Send / RecvPoint-to-point communication between ranks.Only the destination receives the buffer.Move activations between pipeline stages.

AllReduce can be conceptually decomposed into ReduceScatter followed by AllGather. This does not mean every implementation always executes two separate calls; NCCL can select a different implementation and algorithm. There is also a practical difference between input tensor size, output size and the bytes each rank transmits: do not use global tensor size as a synonym for bytes sent per rank.

7. Ring All-Reduce: volume and latency formulas

Ring AllReduce is a useful reference for estimating communication. For P ranks and a buffer of N elements, the classic algorithm has two phases:

  • ReduceScatter: P−1 steps. Each rank sends a chunk and accumulates the chunk it receives.
  • AllGather: P−1 steps. Reduced chunks circulate until every rank has the complete result.

In each phase, a rank transmits approximately (P−1)/P of the buffer. Total bytes sent per rank are:

bytes_sent_per_rank ≈ 2 × (P − 1) / P × N × element_bytes

ring_time ≈ 2 × (P − 1) × α + bytes_sent_per_rank / BW

α represents latency per step and BW is the effective bandwidth available to that communication. This is a simplified model, not an exact NCCL predictor. It does not include protocol, headers, multiple rails, congestion, topology, contention, kernel overhead, synchronization or compute overlap.

The model still reveals a trade-off. As P grows, each rank's transmitted payload approaches two buffers, but the number of steps and fixed latency cost also increase. A small AllReduce can be dominated by α and launch overhead; a large one can be bandwidth-bound.

Do not assume NCCL always uses Ring. Current documentation lists algorithms such as Ring, Tree, CollNetChain, CollNetDirect, NVLS, NVLSTree and PAT, with availability depending on version and platform. If no algorithm is forced, NCCL chooses automatically based on hardware, topology, collective function and message size. NCCL — Environment Variables.

Forcing NCCL_ALGO is not the first optimization step. Measure first, identify the algorithm and transport selected, and establish a baseline. An environment variable that improves one microbenchmark can make other message shapes or the real workload worse.

8. Sequence Parallelism: changing layouts to move fewer activations

Sequence Parallelism distributes the sequence dimension of selected activations and element-wise operations when used with TP. Instead of fully replicating an activation across ranks, the runtime keeps a sequence shard and uses operations such as ReduceScatter and AllGather to transition between layouts.

The distinction matters: Sequence Parallelism is not Context Parallelism, even though both split a token dimension. Sequence Parallelism typically aims to reduce activation memory and redundant operations within a TP mesh. Context Parallelism distributes context/sequence to scale attention over long contexts, with specific communication to obtain the information attention needs.

In training, Sequence Parallelism can reduce activation memory for LayerNorm and Dropout. In inference, the optimizations and layouts depend on the engine and model. Do not enable a sequence-parallel flag without confirming that runtime and checkpoint support the combination.

Avoid double-counting optimizations. If one path introduces AllGather before a layer and another triggers another AllGather for the next layer, the result may move more data than it saves. Follow tensor layout from the output of one operation to the input of the next.

9. Pipeline Parallelism: splitting model depth

PP splits layers into consecutive stages. If a model has 32 transformer blocks and PP=4, each stage may own eight blocks. A rank processes its segment and sends activations to the next stage. The last stage produces output or logits and the next token returns to the client or scheduler.

For one sequence, the flow is sequential: the token must pass through Stage 0, Stage 1, Stage 2 and Stage 3. First-result latency includes the work of all stages plus transfers between them. PP does not turn one request into four parallel requests.

The activation crossing a boundary is usually the previous stage's output. During Prefill it may have an approximate shape of [batch, sequence, hidden]; during Decode, when each active sequence produces one token, it is typically [active_sequences, hidden]. Pipeline communication volume therefore depends on active tokens, hidden size, dtype and layout. It is not equal to model weight size.

Stage balance is critical. A stage with more layers, a heavier embedding/LM head module or a less efficient kernel becomes the bottleneck. Other stages wait for that stage to release the next microbatch. Equal layer counts do not always imply equal work.

10. Pipeline bubble, microbatches and the latency/throughput difference

For an ideal pipeline with P balanced stages and M microbatches, utilization for a simple forward fill/drain schedule can be approximated by:

ideal_utilization ≈ M / (M + P − 1)
bubble_fraction ≈ (P − 1) / (M + P − 1)

The formula describes the penalty of filling and draining a pipeline with M independent jobs. Increasing M amortizes fill/drain, but is not free: microbatches can become too small, scheduling overhead increases and the system needs enough concurrent independent requests.

Training has schedules such as GPipe and 1F1B, which must manage forward activations and backward gradients. Their bubble formulas should not be copied blindly into an autoregressive server. In serving, sequences have different lengths, clients arrive at different times, Decode produces small iterations, and the scheduler can dynamically admit or retire requests. This chapter's simulation is FIFO, not a real serving engine.

The latency/throughput difference is essential:

  • Single-request latency: an isolated request must traverse the entire pipeline. More stages do not automatically reduce time to first token.
  • Steady-state throughput: with enough independent sequences, multiple stages can work simultaneously on different microbatches.
  • Tail latency: one slow stage, irregular microbatch or congested network can affect the whole queue.

For a streaming service, examine TTFT and TPOT per request, not only aggregate throughput averages.

11. Combining TP × PP × DP: an eight-GPU mesh

Suppose eight GPUs are distributed across two nodes with four GPUs each. Several layouts are possible:

LayoutTPPPInterpretation
TP8 × PP181One stage; the TP group spans all eight GPUs.
TP4 × PP242Two stages; each TP group stays within one node.
TP2 × PP424More stages with smaller TP groups.
TP1 × PP818No TP collectives; many pipeline boundaries.

All four layouts use eight GPUs, but they are not equivalent. TP8 introduces collectives across all eight devices. TP4×PP2 can keep frequent collectives within a node and transfer activations between nodes at pipeline boundaries. TP1×PP8 reduces intra-layer communication but adds seven stages and seven boundaries. The choice depends on the model, interconnect latency, activation size, stage balance, active request count and SLOs.

A common recommendation is to keep TP inside the fast-link domain within a node and use PP to scale across nodes. The vLLM guide gives the example of two eight-GPU nodes with TP=8 and PP=2. It also documents the edge case of GPUs without NVLink, such as the L40S example, where PP can be preferable to TP to reduce communication overhead. This is contextual guidance, not a universal rule for every GPU generation or model. vLLM — Multi-node parallelism.

DP adds another dimension. For example, four TP4 replicas can serve separate requests across four groups of four GPUs. This increases serving capacity when demand exists, but each replica needs its own complete set of weight shards. DP does not turn a four-GPU model into one model split across sixteen GPUs; it combines several replicas.

12. Physical topology: HBM, NVLink, PCIe and network fabric

Before discussing NCCL, draw the physical machine:

  • GPU HBM: each accelerator's local memory. The most efficient operation often avoids moving activations outside the GPU.
  • NVLink / NVSwitch: high-speed GPU interconnect in platforms that include it. Exact topology determines which pairs have direct access and which paths share resources.
  • PCIe: host-device bus and, when topology/driver permit, GPU-to-GPU P2P communication. Not every pair has the same route.
  • NIC + InfiniBand / RoCE: inter-node connectivity. GPUDirect RDMA can enable traffic from GPU memory to the network adapter without classic CPU-buffer staging, when hardware and software requirements are met.
  • CPU / NUMA: process, host memory and NIC affinity relative to CPU sockets. Poor placement can introduce cross-NUMA traffic.

NCCL favours P2P when CUDA reports direct access between GPUs, typically through NVLink or PCIe when topology and driver allow it. It is not enough that a system advertises NVLink: verify the links between the specific devices. NVIDIA documents commands such as nvidia-smi topo -m and nvidia-smi topo -p2p n to inspect the matrix. NCCL — GPU troubleshooting.

Topology also determines rank placement. If a TP group needs an AllReduce for every block, placing ranks of that group on GPUs connected within the same fast domain is generally preferable to accidentally spreading them across a multi-node network. A PP boundary may tolerate a less frequent P2P message, although total volume and latency still matter.

13. NCCL, PyTorch Distributed and the runtime: who does what?

Distributed execution involves several layers:

LayerResponsibilityExamples
Model partitioningDecide which weights, heads, layers or tokens belong to each rank.Megatron Core, PyTorch TP / DTensor, model code.
Distributed runtimeCreate processes, assign ranks, initialize groups, start workers and manage lifecycle.torchrun, multiprocessing, Ray, Slurm, Kubernetes.
Collective communicationExecute AllReduce, AllGather, ReduceScatter, AllToAll and P2P.NCCL on NVIDIA GPUs; other backends depending on platform.
Inference engineScheduler, batching, KV Cache, layer execution and serving API.vLLM, TensorRT-LLM and other runtimes.
Fabric / hardwareMove bytes and execute kernels.NVLink, PCIe, NIC, InfiniBand, RoCE, GPU.

NCCL does not create the logical mesh on its own. The framework initializes communicators and calls operations. Collectives must be executed in a compatible order across all ranks. A rank that does not arrive, arrives late or executes another operation can block the rest.

In PyTorch, torch.distributed exposes ProcessGroup and collective abstractions. The NCCL backend is common with NVIDIA GPUs; Gloo is often used for CPU and certain other cases. Backend, versions and transports depend on the environment. PyTorch documentation also shows how TP uses DTensor and layouts to automate communication.

14. Multi-GPU and multi-node serving with vLLM

For one replica distributed across several GPUs, vLLM exposes tensor_parallel_size and pipeline_parallel_size. The current CLI syntax includes:

One machine with four GPUs

vllm serve <model> \
  --tensor-parallel-size 4

The four ranks collaborate within the TP group. Before choosing this configuration, verify that model dimensions are compatible and the topology has suitable links.

Two nodes with eight GPUs each

vllm serve <model> \
  --tensor-parallel-size 8 \
  --pipeline-parallel-size 2 \
  --distributed-executor-backend ray

This arrangement typically places eight TP ranks per node and uses two pipeline stages. Ray is an optional runtime for multi-node; vLLM also documents a multiprocessing path. Processes must be able to access the same model or an equivalent location, and nodes need consistent private-network connectivity.

Pipeline-only within one node

vllm serve <model> \
  --tensor-parallel-size 1 \
  --pipeline-parallel-size 4

This may make sense when distributing layers without introducing TP collectives, or when GPU-to-GPU topology does not provide suitable links. Stage balance and microbatching must be validated with the actual workload.

vLLM's documented multi-node recommendation is to set TP to the number of GPUs per node and PP to the number of nodes; it also describes setting TP across all GPUs in the cluster. Runtime and strategy must be validated against the installed release. vLLM — Parallelism and Scaling.

Cluster security

vLLM documentation warns that Ray cluster communication/control traffic is not encrypted and that an actor with access to the endpoints can reach dangerous capabilities. Keep distributed traffic on a controlled private network. Do not expose internal Ray or worker ports to untrusted networks; the public model HTTP endpoint is not the same as the internal execution network.

15. Memory per rank: weights, KV Cache and buffers

As a first approximation, weight payload can be divided by TP×PP:

ideal_weight_bytes_per_gpu ≈ total_weight_bytes / (TP × PP)

This is a first-order estimate, not an exact allocator calculation. Some embeddings, norms, output heads, buffers, scales or tensors may remain replicated. Actual size also depends on checkpoint, quantization, alignment, workspace and runtime.

KV Cache needs a separate formula:

KV_bytes ≈
  2 × layers_local × active_sequences × context_tokens
    × local_kv_heads × head_dim × bytes_per_element

The factor 2 represents Key and Value. With PP, each stage stores KV for the layers it executes. With TP, KV heads may be distributed among ranks, but some GQA/MQA models may replicate heads or impose restrictions. The formula requires the actual layout; do not blindly divide by TP×PP.

In addition to weights and KV, each GPU needs memory for activations, workspaces, communication buffers, graph capture, temporary memory and allocator reservations. A configuration may fit at initialization and fail when max_model_len or max_num_seqs increases, because KV Cache and runtime buffers consume the remaining margin.

vLLM startup logs often report estimated GPU KV Cache size and approximate concurrency at a particular request length. That number is more useful than weight-only arithmetic for understanding how many active sequences really fit.

16. A performance model: compute, communication and synchronization

A distributed operation's latency can be modelled simply as:

T_operation ≈ T_compute + T_communication + T_launch + T_sync

T_communication ≈ latency_cost + payload_bytes / effective_bandwidth

But terms can overlap. If an implementation permits communication to overlap computation, total cost is not necessarily their full sum:

T_step ≈ max(T_compute, T_communication) + T_unhidden_overhead

Overlap depends on kernels, streams, data dependencies, scheduling and link capability. A row-parallel operation that needs its AllReduce before continuing creates a dependency; declaring an operation asynchronous is not enough to remove it.

During Prefill, token batches can be large and GEMMs often perform substantial work per communication. During Decode, each active sequence usually adds one token per iteration; for small batches the collective message can be relatively small and fixed launch/latency cost becomes more important. As active sequence count increases, activation size in collectives grows too. The same TP degree can therefore behave differently during Prefill and Decode.

A roofline-style analysis should separate:

  • Compute peak and real Tensor Core utilization.
  • Local HBM bandwidth and weight access.
  • GPU-to-GPU bandwidth and latency inside the node.
  • Inter-node bandwidth, NIC affinity and fabric contention.
  • Scheduler, batch composition, sequence length, KV Cache and CPU overhead.

The goal is not to maximize isolated theoretical bandwidth. It is to minimize unhidden communication and keep GPUs busy with a balanced workload.

17. How to measure real systems: NCCL Tests, nvbandwidth and serving benchmarks

Do not measure only with a ping between nodes. TP inference depends on GPU-to-GPU communication and collective operations. A useful benchmark needs to test the message types and sizes used by the engine in addition to model workload.

Topology discovery

nvidia-smi topo -m
nvidia-smi topo -p2p n
nvidia-smi topo -p2p p

The first command shows links between GPUs, CPUs, NICs and other components. P2P checks reveal whether pairs allow direct NVLink or PCIe access. An uneven route matrix can explain why the same TP degree performs differently when GPUs are remapped.

Bandwidth and collectives

NVIDIA documents nvbandwidth and nvloom for measuring GPU-to-GPU bandwidth across NVLink/PCIe and between nodes on supported systems. The official NCCL Tests repository includes programs such as all_reduce_perf and tests for other collectives. A size sweep example is documented in the project README:

mpirun -np 8 -N 8 ./build/all_reduce_perf \
  -b 8M -e 1G -f 2 -g 1

Adapt the command to GPUs per process, number of nodes and NCCL Tests build. Do not run it in production without reserving resources; tests can consume much of the interconnect.

Serving benchmark

Then benchmark vLLM or the final engine with representative prompts and outputs, defined concurrency and warmup. Keep:

  • TTFT, TPOT/inter-token latency and p50/p95/p99 percentiles.
  • Input/output tokens per second and requests per second.
  • Active concurrency, queue time, prompt length, output length and long-context distribution.
  • GPU memory, utilization, HBM, links, KV usage, queues and errors.
  • TP/PP degree, rank mapping, CUDA/driver/NCCL versions, backend, selected algorithm and transport.

Microbenchmarks help isolate transport problems. They do not replace end-to-end application measurement. NVIDIA NCCL Tests · NVIDIA nvbandwidth.

18. NCCL logs and observability: identify which path is being used

For a controlled investigation, NCCL can increase its logging level:

export NCCL_DEBUG=INFO
export NCCL_DEBUG_SUBSYS=INIT,GRAPH,ENV

Logs can help identify communicator initialization, detected topology, environment variables, transports and route selection. NVIDIA documentation shows INIT, GRAPH and ENV for inspecting affinity/topology together with nvidia-smi topo and lscpu.

An important practice: do not leave debugging or tuning variables in production scripts without a reason. NCCL documentation distinguishes system configuration variables from debugging variables; some should be removed after an issue is resolved because they can degrade performance or cause other problems. NCCL — Environment Variables.

When investigating algorithm selection, record the version and topology graph, message size and collective type. Do not attribute every improvement to NVLink if the actual change was an algorithm or number of messages.

20. Diagnostic runbook for a multi-GPU server

  1. Freeze the topology: record nodes, GPU models, driver, CUDA, NCCL, NICs, switch/fabric and cabling. Do not change software and topology simultaneously.
  2. Map ranks to devices: record global rank, local rank, GPU UUID, pipeline stage and TP group. Confirm that ranks in the same TP group have the expected physical route.
  3. Check P2P: run nvidia-smi topo -m and P2P matrices. Identify pairs using PCIe, NVLink or no direct access.
  4. Benchmark the fabric: run nccl-tests and nvbandwidth with representative sizes. Compare results per GPU pair, collective and message.
  5. Enable temporary NCCL logs: INFO + INIT/GRAPH/ENV to capture device discovery, transports and route selection.
  6. Validate process groups: same world size, valid ranks, compatible collective operation, count/dtype and call order.
  7. Run a tiny model: validate a small replica before loading the real checkpoint. Test forward, decode, stop, error and worker shutdown.
  8. Profile the real workload: Prefill and Decode separately; TTFT/TPOT, batch, queues, KV, memory, collectives and P2P stage transfers.
  9. Change one dimension: compare TP, PP or placement one variable at a time. Preserve baseline and rollback.
  10. Remove debug overrides: clean temporary variables; keep only settings justified by reproducible measurements.

When a collective hangs, start with the first error from the first rank. The last process to report a timeout is usually a victim, not necessarily the origin. A synchronization problem in an earlier layer can leave every other rank waiting indefinitely.

21. Reproduced laboratory: TP, PP, collectives and topology

The included lab builds a synthetic model with 32 layers, hidden size 4096 and FFN intermediate size 11008. It calculates ideal weight payload and models communication for one decode iteration with 16 active sequences. It downloads no weights and executes no GPU. The goal is to understand quantities, layouts and dependencies.

Lab scope

Python standard library, CPU-only, no PyTorch, CUDA, NCCL, Ray or vLLM. It does not create distributed processes or measure an interconnect. 23. Limits and conclusions

Distributed inference is a joint architecture and topology decision. TP splits matrices and needs frequent collective communication. PP splits layers and moves activations between stages. DP replicates the model and distributes requests; CP splits context; EP distributes experts. A real server can combine several of these dimensions.

More GPUs do not automatically mean more speed. A larger TP degree reduces weights per rank but increases coordination; PP reduces layers per stage but creates fill/drain and stage boundaries; DP increases replicas but each replica retains its model memory; CP and EP change communication patterns. Physical topology determines which traffic uses NVLink, PCIe or an inter-node network.

The right engineering sequence is to measure the bottleneck, draw the topology, choose a layout, test collectives, validate a small model, profile Prefill/Decode and change one variable per iteration. This chapter's lab teaches the mathematics and flow; it does not replace nccl-tests or a real serving benchmark.
