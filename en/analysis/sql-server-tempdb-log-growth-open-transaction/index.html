SQL Server tempdb: diagnosing log growth caused by an open transaction

A growing tempdb log is not fixed by blindly shrinking the file. First establish why SQL Server cannot reuse its log space. We reproduce the scenario, identify the transaction keeping log records active, and verify recovery with both SQLCMD and SQL Server Management Studio.

Main finding

The open transaction kept log records active and prevented their reuse. SQL Server reported ACTIVE_TRANSACTION; the log file grew from 8 MB to 216 MB and reached 99.16% utilisation. After rollback and CHECKPOINT, utilisation fell to 1.78% and the wait reason returned to NOTHING. The physical file remained 216 MB: space became reusable inside the file; it was not returned to the operating system.

1. What happened

The symptom under investigation is sustained growth of templog.ldf, the tempdb log file. File size and utilisation alone do not explain the cause. The key question is why the engine cannot reuse inactive log records.

In this lab, one session opened an explicit transaction, inserted rows into a dedicated table in tempdb, and held the transaction open for three minutes. A second session queried log usage and transaction DMVs during that interval. The observed reuse wait was ACTIVE_TRANSACTION.

This was not a production incident. It is a controlled reproduction of the mechanism. A long-running transaction is one possible reason for log retention, not a universal explanation for every tempdb growth event. Start from the actual log_reuse_wait_desc value.

The 8 MB growth increment was deliberately configured to make growth events visible during the test. It is not a production recommendation and should not be mistaken for a default on other installations. Size tempdb for the workload and observed peaks.

The table dbo.CA_TempdbLogGrowthLab exists only inside tempdb. Tempdb contents do not persist across Database Engine restarts: the database is recreated at startup and does not support backup/restore like a user database.

3. Capture a baseline

Before generating load, record file configuration, current log usage and the reuse wait reason. Run the following with the database context set to tempdb:

USE tempdb;
GO

SELECT name, type_desc, physical_name,
       CAST(size * 8.0 / 1024 AS decimal(12,2)) AS size_mb,
       CASE WHEN is_percent_growth = 1 THEN CONCAT(growth, '%')
            ELSE CONCAT(CAST(growth * 8.0 / 1024 AS decimal(12,2)), ' MB')
       END AS filegrowth
FROM sys.database_files
ORDER BY file_id;

SELECT total_log_size_in_bytes / 1048576.0 AS total_log_mb,
       used_log_space_in_bytes / 1048576.0 AS used_log_mb,
       used_log_space_in_percent
FROM sys.dm_db_log_space_usage;

SELECT name, state_desc, recovery_model_desc, log_reuse_wait_desc
FROM sys.databases
WHERE database_id = DB_ID(N'tempdb');

sys.dm_db_log_space_usage reports total log size and used space. On SQL Server 2022, the DMVs used in this article require VIEW SERVER PERFORMANCE STATE or a server role that includes it, such as sysadmin. Verify permissions for the target build and edition.

4. Reproduce an open transaction

The workload inserts 12,000 rows with a char(7000) column: 84,000,000 payload bytes before accounting for other structures and log records. The transaction remains open for three minutes so a second session can inspect it.

USE tempdb;
SET NOCOUNT ON;

IF OBJECT_ID(N'dbo.CA_TempdbLogGrowthLab', N'U') IS NOT NULL
    DROP TABLE dbo.CA_TempdbLogGrowthLab;

CREATE TABLE dbo.CA_TempdbLogGrowthLab
(
    id int IDENTITY(1,1) NOT NULL PRIMARY KEY,
    payload char(7000) NOT NULL
);

BEGIN TRANSACTION CA_TempdbLogGrowthLab;

;WITH n AS
(
    SELECT TOP (12000)
           ROW_NUMBER() OVER (ORDER BY (SELECT NULL)) AS n
    FROM sys.all_objects AS a
    CROSS JOIN sys.all_objects AS b
)
INSERT INTO dbo.CA_TempdbLogGrowthLab (payload)
SELECT REPLICATE('X', 7000)
FROM n;

SELECT @@SPID AS repro_session_id,
       COUNT_BIG(*) AS rows_inserted,
       SUM(DATALENGTH(payload)) AS payload_bytes
FROM dbo.CA_TempdbLogGrowthLab;

-- Keep the transaction open for diagnosis from a second session.
WAITFOR DELAY '00:03:00';

ROLLBACK TRANSACTION CA_TempdbLogGrowthLab;
DROP TABLE dbo.CA_TempdbLogGrowthLab;

Disposable lab use only. This workload inserts data and keeps a transaction open for three minutes. Do not run it in production or on a shared instance. The downloadable package includes the scripts and these warnings.

5. Diagnose while the transaction is active

First measure file size and utilisation. Then correlate the reuse wait with the transaction, session, login, host and client application:

USE tempdb;
SET NOCOUNT ON;

SELECT total_log_size_in_bytes / 1048576.0 AS total_log_mb,
       used_log_space_in_bytes / 1048576.0 AS used_log_mb,
       used_log_space_in_percent
FROM sys.dm_db_log_space_usage;

SELECT name, state_desc, log_reuse_wait_desc
FROM sys.databases
WHERE database_id = DB_ID(N'tempdb');

SELECT at.transaction_id, at.name AS transaction_name,
       at.transaction_begin_time,
       dt.database_transaction_log_bytes_used / 1048576.0 AS log_used_mb,
       st.session_id, s.login_name, s.host_name, s.program_name
FROM sys.dm_tran_database_transactions AS dt
JOIN sys.dm_tran_session_transactions AS st
  ON st.transaction_id = dt.transaction_id
JOIN sys.dm_tran_active_transactions AS at
  ON at.transaction_id = dt.transaction_id
JOIN sys.dm_exec_sessions AS s
  ON s.session_id = st.session_id
WHERE dt.database_id = DB_ID(N'tempdb')
ORDER BY at.transaction_begin_time;

Together, these queries show how much log is used, what prevents reuse, when the transaction began and which session/application needs investigation. Do not kill a SPID until you understand its work and identify the workload owner.

6. Count autogrowth events

The final file size does not show how many growth operations occurred. The default trace was available in this lab, so it was used to count historical events. Event IDs 93 and 92 correspond to Log File Auto Grow and Data File Auto Grow, respectively.

DECLARE @trace nvarchar(4000);
SELECT @trace = path
FROM sys.traces
WHERE is_default = 1;

SELECT EventClass,
       CASE EventClass WHEN 93 THEN 'Log File Auto Grow'
                       WHEN 92 THEN 'Data File Auto Grow' END AS event_name,
       COUNT_BIG(*) AS growth_events,
       SUM(IntegerData) * 8.0 / 1024 AS total_growth_mb,
       MIN(StartTime) AS first_event,
       MAX(StartTime) AS last_event
FROM sys.fn_trace_gettable(@trace, DEFAULT)
WHERE EventClass IN (92,93)
  AND DatabaseName = 'tempdb'
  AND StartTime >= '2026-11-13T20:00:00'
GROUP BY EventClass
ORDER BY EventClass;

The default trace may be disabled or may no longer retain events from the investigation window. Check availability before running the query. For new, persistent instrumentation, design an Extended Events session with appropriate filters and retention.

7. Resolve and validate: rollback and log reuse

The fix is not to shrink the file. Resolve the transaction holding the log active, taking account of the workload owner and service impact. In this reproduction, the session that opened the transaction issued ROLLBACK; then CHECKPOINT was run in tempdb.

USE tempdb;
CHECKPOINT;

SELECT total_log_size_in_bytes / 1048576.0 AS total_log_mb,
       used_log_space_in_bytes / 1048576.0 AS used_log_mb,
       used_log_space_in_percent
FROM sys.dm_db_log_space_usage;

SELECT name, state_desc, recovery_model_desc, log_reuse_wait_desc
FROM sys.databases
WHERE database_id = DB_ID(N'tempdb');

SELECT COUNT_BIG(*) AS active_tempdb_user_transactions
FROM sys.dm_tran_database_transactions AS dt
JOIN sys.dm_tran_session_transactions AS st
  ON st.transaction_id = dt.transaction_id
WHERE dt.database_id = DB_ID(N'tempdb');

SELECT CASE WHEN OBJECT_ID(N'dbo.CA_TempdbLogGrowthLab', N'U') IS NULL
            THEN 'REMOVED - PASS'
            ELSE 'STILL EXISTS - CHECK' END AS lab_table_status;

Log space reuse is not the same as file shrink. Logical truncation makes inactive VLFs available for reuse; shrinking attempts to return capacity to the file system. They are different operations. Do not automatically shrink the file in response to this symptom.

8. Production runbook

  1. Confirm impact and capacity: check free volume space, current file size, growth settings and utilisation trend. Establish whether the disk is at immediate risk.
  2. Read the reuse wait: query sys.databases.log_reuse_wait_desc. Do not assume every retention issue is caused by an open transaction.
  3. If ACTIVE_TRANSACTION appears: identify the transaction through sys.dm_tran_database_transactions, map it to a session using sys.dm_tran_session_transactions, and inspect login, host, program and start time.
  4. Understand before acting: coordinate with the workload owner. Decide whether the transaction should complete normally or be rolled back based on application semantics and service windows. KILL can start a lengthy rollback and prolong resource consumption.
  5. Validate recovery: measure log usage, log_reuse_wait_desc, active transactions and free volume space again. Record the evidence and recovery time.
  6. Prevent recurrence: size tempdb for normal workload and peaks, set sensible fixed growth increments and monitor capacity and autogrowth. Autogrowth is a safety net, not a capacity plan.

ACTIVE_TRANSACTION alone does not prove that a user temporary table is responsible. tempdb also contains internal objects, worktables, sort/hash structures and row versioning data. Correlate the wait reason and DMVs before attributing consumption to a specific operation.

9. What not to do

  • Do not shrink templog first. If the transaction remains active, shrink does not fix the cause. If the workload needs the space again, the file will grow again and add autogrowth overhead.
  • Do not kill an unidentified session. A SPID is not a root cause. Inspect its program, host, login, age and transaction owner.
  • Do not confuse size with utilisation. A 216 MB file may be only 1.78% used and have reusable capacity.
  • Do not copy the lab configuration into production. The 8 MB increment was selected to expose growth events; production sizing must reflect workload and storage capacity.
  • Do not generalise this fix to every reuse wait. Read the observed wait reason and follow the relevant diagnostic path. Not every log reuse issue is fixed by rolling back a transaction.
