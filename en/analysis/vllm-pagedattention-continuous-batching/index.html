Inside vLLM: PagedAttention, Continuous Batching and GPU Memory

A model can generate tokens correctly and still make a poor service. When dozens of requests arrive with different contexts and output lengths, the challenge is no longer just running the forward pass: the engine must allocate KV Cache, manage memory, admit requests, schedule every iteration and protect the latency of requests already generating. This is the engineering behind a serving engine such as vLLM.

The central idea

PagedAttention solves how to store and read a sequence's KV state without requiring one contiguous region per request. Continuous batching solves how to add and remove requests from the engine's work at every iteration. Prefix caching adds a third optimisation: reuse blocks belonging to an identical prefix. These are different mechanisms that complement one another; none replaces the others.

1. The serving problem is more than generating tokens

In chapter 04 we followed Prefill, Decode and KV Cache. An isolated request is easy to describe: process a prompt, generate a token, update the cache and repeat. In a real service, however, requests arrive at different times, carry prompts of different sizes and have different generation limits.

Imagine four concurrent requests. One has a 4,000-token prompt and wants 100 output tokens; another has 200 prompt tokens and wants 30 output tokens; a third shares the same system context as the first; and a fourth finishes while the others are still active. If we reserve a large contiguous region of memory for every request, we can pin space that is not yet used. If we wait for the whole batch to finish before admitting more work, GPU capacity may sit idle. And if a request exhausts the KV budget, the scheduler must decide what to do without causing a global failure.

A serving engine coordinates at least five responsibilities:

  • Execution: run model forward passes over active requests.
  • KV memory management: allocate, grow, share, release and reclaim blocks.
  • Scheduling: decide which tokens and requests enter each iteration.
  • Admission and backpressure: bound queued work when capacity cannot sustain demand.
  • Observability: expose latency, utilisation, queues, cache hits, preemption and errors.

vLLM combines these mechanisms in a high-throughput inference engine. PagedAttention was one of the original ideas behind its design: applying memory paging concepts to Transformer KV state.

2. Static batching vs continuous batching

Static batching: everyone leaves when the slowest finishes

In a static scheme, a set of sequences is grouped and executed as a batch. Because generation is autoregressive, each sequence can produce a different number of tokens. When one finishes, its place in the batch may become underutilised while the others continue. If the next group waits until the current group is complete, the slowest member controls when capacity can be reused.

Padding and variable sequence lengths may add work or gaps. This can make sense for offline workloads or when input and output shapes are known, but it is not the most useful abstraction for an interactive generation endpoint.

Continuous batching: the batch changes at every iteration

Continuous batching rebuilds the active work set at every engine iteration. Requests that are still generating remain active; completed requests release resources; waiting requests can enter the next step when sequence, token and memory budgets permit. The engine does not need to wait for an entire batch to finish.

The engine can keep useful work flowing even when requests have different durations. It does not mean all tokens are processed simultaneously or that individual latency always falls. A larger batch may improve aggregate throughput while worsening the wait or inter-token latency of a particular request.

The optimisation question is not simply “how many requests fit in a batch?” It is “what mix of Prefill and Decode can run, with what memory budget, while preserving TTFT and inter-token latency SLOs?”

3. PagedAttention: KV blocks instead of large contiguous regions

The KV Cache grows as each sequence's context grows. If a request needs T tokens and each block stores B positions, its minimum number of blocks is:

required_blocks = ceil(T / B)
allocated_slots = required_blocks × B
tail_waste = allocated_slots - T

Instead of asking for one contiguous region of T positions, the engine maintains a pool of fixed-size physical blocks. Each sequence has a table pointing to the blocks containing its state. Blocks belonging to one logical sequence do not have to be adjacent in physical memory.

The name PagedAttention describes both the paged organisation of KV state and the attention operation that reads those blocks. During Decode, the new query must read the relevant Keys and Values from the context. The attention implementation uses block metadata to locate the cache segments belonging to each sequence. This is not merely splitting a tensor into Python chunks: the kernel and physical layout participate in efficient memory access.

Current vLLM documentation describes fixed-size blocks, and the attention kernel receives K/V cache structures organised by block count, heads and positions within a block. Exact block size and layout depend on the architecture and backend; a teaching example with four or sixteen tokens is not a universal default.

4. Block tables: separate logical position from physical address

Assume a block size of four tokens. A ten-token sequence may be mapped as follows:

Logical token ranges       Physical block table
0..3                       [block 7]
4..7                       [block 2]
8..9                       [block 11]

Sequence → [7, 2, 11]

Block 7 may be in a different memory region from block 2. The sequence sees logical continuity, while the allocator manages independent physical pieces. To attend to a new Decode query, the kernel traverses the blocks specified by the table, calculates the contribution of the positions and composes the attention result.

A key advantage is that we do not need to reserve one contiguous region for every request's maximum length in advance. Blocks are allocated on demand as the prompt is processed and new tokens are generated. Memory is managed as a common pool, with a logical map per request.

This reduces external fragmentation associated with finding large contiguous holes for independently growing and shrinking sequences. It does not eliminate all waste: the final block of each sequence may be partially empty, and the pool itself needs metadata, buffers and spare capacity for bursts.

5. Fragmentation: what improves and what does not

For a sequence of T tokens and block size B, the last block wastes between zero and B−1 positions. Final-block occupancy depends on the actual length; across many requests this slack can matter, but it is usually much more bounded than reserving one fixed maximum length for every request.

Example: four contexts of 23, 77, 12 and 49 tokens. Reserving 128 positions for each reserves 512 slots. There are 161 live tokens, so 351 slots are unused. With blocks of 16, allocated capacity is 192 slots: partial-tail waste totals 31 positions.

Unused slots fall by 91.17% in this scenario. It does not mean vLLM uses 91.17% less VRAM in production. The example excludes model weights, activations, workspaces, alignment, buffers, allocator fragmentation and the actual number of blocks reserved by the engine. It illustrates the effect of on-demand allocation using uniform sizes.

Block size is also a trade-off. Small blocks bound final-block slack but increase block-table entries and management operations. Large blocks reduce metadata per token but may increase tail waste and change prefix-matching granularity. Real configuration must be read together with the implementation and model.

6. Automatic Prefix Caching: reusing work across requests

PagedAttention allows sequences to be represented by blocks. Automatic Prefix Caching uses that organisation to reuse KV state when a new request shares a complete prefix with an existing one. The new request can skip computation for the prefix that already has a cache hit and continue from the first non-matching block.

For example, two calls may share a system prompt and a context document. The first eight positions may be represented by two identical complete blocks. The first request creates those blocks; the second can reference the same IDs instead of storing another copy. Its block table shares the prefix and then points to private blocks for its own suffix.

This requires more than comparing visible text. A cache key is associated with token content and relevant model/configuration context. In vLLM V1, the KV cache manager maintains block objects, IDs, hashes, reference counters and a queue of reusable blocks. Blocks without active references may remain cached until space is needed.

A shared block must not be overwritten while another sequence uses it. Reference counting makes this property explicit: creating a new reference increments the counter; releasing a request decrements it; only when no references remain can the block be recycled, subject to its cache-index state.

This chapter's simulator simplifies hashing to consecutive complete blocks and one teaching model. The actual implementation has more details, including prefix hashing, duplicate blocks, free queues and hybrid-model behaviour. Do not turn the simulator into implementation documentation.

Prefix caching is not unlimited global memory

An entry may be evicted when the pool needs to reclaim space. Hits depend on the prefix arriving again, block retention, concurrency and block size. A hit reduces Prefill work; it does not eliminate Decode for the new suffix or guarantee an identical gain for every request.

7. V1 Scheduler: a token budget per iteration

An important precision from the current documented vLLM V1 architecture: the scheduler should not be understood as two rigid queues, one for Prefill and one for Decode, executed as independent phases. Its loop uses a token budget per iteration and requests in running or waiting states. Each sequence tracks how many tokens have already been computed; the scheduler assigns work to close that gap. The same loop can integrate chunked prefill, prefix caching and speculative decoding.

The key parameter is max_num_batched_tokens: the maximum number of tokens the scheduler can process in one iteration. There are also limits related to the number of sequences, active requests and queued requests. They are not interchangeable:

  • max_num_batched_tokens: token budget for one iteration.
  • max_num_seqs: maximum sequences processed in an iteration and a dimension for associated buffers.
  • max_num_active_seqs: cap on requests admitted to RUNNING in configurations that support it.
  • max_num_queued_reqs: control for total in-flight requests, waiting or running.
  • max_num_queued_tokens: control for the prompt-token backlog in Prefill.

The documented default scheduling policy is FCFS. A Priority policy is also available. When KV Cache cannot allocate new blocks, the scheduler can preempt running requests until capacity is recovered. In documented vLLM V1 behaviour, the default preemption mode is recompute; do not assume an automatic swap to CPU as older explanations sometimes imply.

When a preempted request is admitted again, the required progress is recomputed; some work may be recovered through prefix caching or compatible KV connectors. Preemption is a signal of memory pressure and a potential source of repeated work. It is not free.

8. Chunked Prefill: balancing prompts and generation

Prefill usually exposes more parallel matrix work; Decode is sequential per request and often more dependent on reading weights and KV state. If a request brings a very long prompt, allowing it to consume an entire iteration can delay output tokens for requests already generating.

Chunked Prefill divides a long prompt into segments that can enter different iterations. Current vLLM V1 documentation says that, when possible, this feature is enabled by default and the scheduler prioritises Decode work before spending the remaining iteration budget on Prefill. If a pending prompt does not fit into the token budget, it is chunked automatically.

The budget changes the trade-off:

  • A smaller budget can protect ITL because fewer Prefill tokens compete with Decode in each step.
  • A larger budget allows more prompt tokens to be processed and may improve TTFT for requests waiting for their first token.
  • Aggregate throughput requires a balance tested against the actual model, GPU, context distribution and concurrency.

Do not copy a number from a guide and make it a universal standard. The 2,048 or 8,192 token examples in the documentation are tuning guidance, not universal settings or guaranteed results. Choose through benchmarking with the workload the service will actually receive.

9. Admission control, preemption and backpressure

A server that accepts unbounded requests can turn a temporary overload into an ever-growing queue. Users see increasing TTFT, timeouts cause retries, and retries add more load. The system may remain busy without increasing useful completed work.

Admission control defines how much work is accepted. vLLM includes controls for queued requests and pending prompt tokens; when limits are reached, the API layer can reject new requests with HTTP 503 so the client can retry on another replica or later. A priority policy may also be used by service class.

A production design should combine:

  • End-to-end timeout and deadline propagation through gateway and client.
  • Concurrency and maximum prompt/output lengths per service class.
  • Bounded queue, explicit rejection, and retry with exponential backoff and jitter.
  • Cancellation of requests the client no longer needs.
  • Per-identity/tenant rate limits and burst protection.
  • Alerts for preemption, KV block saturation and queue growth.

HTTP 503 is not necessarily a model failure: it may be the deliberate signal that an instance has reached its admission budget. The client must distinguish transient overload, model error, timeout and authentication failure.

10. Operational architecture of vLLM

Current V1 documentation describes responsibilities separated across API Server, Engine Core, GPU Workers and, when scaling Data Parallel, a coordinator. The API Server handles HTTP and input processing; Engine Core contains the scheduler and KV Cache management; workers execute model forward passes. The process count depends on DP, TP and PP.

This separation helps reason about faults and saturation by layer. The API Server may be healthy while the scheduler queue is long; GPU Workers may be active but unable to admit more sequences because there are not enough KV blocks; and a network or tokenisation problem can degrade end-to-end time without the attention kernel being saturated.

That is why monitoring only GPU utilisation or total memory is insufficient. Queue state, active sequences, KV blocks, per-request timings and admission errors must be correlated.

11. Sizing: from bytes per token to available blocks

For homogeneous full attention, an approximation for K/V storage per block of B tokens is:

bytes_per_KV_block =
  2 × layers × B × KV_heads × head_dim × bytes_per_element

approx_num_blocks =
  KV_memory_budget / bytes_per_KV_block

The factor 2 represents Key and Value. The calculation depends on the number of layers that store KV, KV heads —not query heads—, head dimension and effective dtype. GQA/MQA reduce KV heads; hybrid or sliding-window architectures may change the retained length by group or layer.

The second expression is a planning approximation, not vLLM's exact allocator formula. The available KV budget must leave room for model weights, activations, temporary buffers, kernels, CUDA graphs, memory not used by the process and headroom for workload variation. A calculation consuming 100% of theoretical VRAM is not a safe operational capacity.

Block count determines how much context can be kept simultaneously. As average context grows, each request uses more blocks. Higher concurrency also increases demand. Prefix caching can reduce duplicate copies of shared prefixes, but its benefit depends on hit rate, retention and eviction policy.

Serving capacity should be expressed as a workload envelope: prompt/output token distribution, concurrency, arrival rate, shared-prefix ratio, TTFT/TPOT SLOs, request duration and preemption probability. “It fits 100 requests” without these variables is not reproducible sizing.

12. Metrics and observability: see the service from request and engine perspectives

vLLM exposes Prometheus-compatible metrics at /metrics. V1 documentation groups server metrics —gauges and counters— and request-level metrics —histograms. Together they help explain why a user SLO is degrading.

MetricWhat it helps answer
vllm:num_requests_runningHow many requests are active inside the engine.
vllm:kv_cache_usage_percWhat fraction of KV blocks is occupied.
vllm:num_requests_waitingQueue pressure, where exposed by the applicable version/configuration.
vllm:prefix_cache_queries / hitsPrefix cache query volume and hit effectiveness.
vllm:time_to_first_token_secondsLatency distribution until the first output token.
vllm:inter_token_latency_secondsTime between consecutive streamed output events.
vllm:request_time_per_output_token_secondsPer-request TPOT according to the engine's convention.
vllm:request_queue_time_secondsTime spent waiting in the scheduler.
vllm:request_prefill_time_seconds / decode_time_secondsTime attributable to generation phases.
vllm:admission_rejections_totalRequests rejected by admission limits.

ITL and TPOT are not necessarily equal. ITL measures gaps between streamed output events. TPOT is calculated per request, excluding the first token and amortising the remaining generation time over the other output tokens. With speculative decoding, one event can contain multiple tokens; aggregation weights also differ. Before comparing graphs, check the exact metric definitions used by the tool.

A useful dashboard should combine p50/p95/p99 for TTFT, ITL/TPOT and end-to-end latency with request rate, input/output tokens, queue wait, running/waiting, KV usage, prefix hits, preemption and HTTP 429/503/5xx. GPU memory without request context explains little.

13. Trying real vLLM: a startup template, not a lab result

This chapter's lab does not install vLLM or download a model. On a Linux machine compatible with the vLLM version and a supported accelerator, the documentation provides this general serving pattern:

# In an isolated environment with vLLM installed and a compatible GPU:
vllm serve <MODEL_ID> \
  --host 0.0.0.0 \
  --port 8000 \
  --enable-prefix-caching \
  --max-num-batched-tokens 8192

8192 is a tuning example, not a universal recommendation. Start conservatively, verify model/backend compatibility and memory, and increase load progressively. Do not expose the endpoint to the Internet without authentication, authorisation, rate limits, input limits and suitable network policy. Binding to 0.0.0.0 opens the service on all host interfaces; use it only when that exposure is intentional and protected.

After starting the service, validate health, generation endpoint, streaming format and /metrics. Run a controlled matrix of short/long prompts, short/long outputs, increasing concurrency and repeated prefixes. Change one variable per test and record the full configuration.

14. Reproduced laboratory: allocator and scheduler in Python

I built a simulator using the Python standard library. It does not reproduce CUDA kernels or vLLM's internal code. Its purpose is to make the invariants studied above verifiable without installing dependencies, downloading weights or using GPU resources.

Experiment A: block tables and reference counting

Two requests are created with an identical eight-token prefix. Each block contains four tokens. Their tables point to the same two physical prefix blocks; each shared block has two references. Suffixes are assigned to private blocks. When the first request is released, the shared-block reference count drops to one, so the second request retains valid access.

The second sequence is then extended until a third block is full. A third request with that complete prefix reuses the first three blocks. Partial final blocks remain separate. The CSV stores physical ID, logical position, tokens, capacity, ref_count and cached state.

Experiment B: continuous batching

Four requests arrive at steps 0, 1, 2 and 3. The scheduler admits at most three. In each iteration it first grants one token to every request in Decode; it uses the remaining budget to distribute Prefill tokens round-robin; when a request completes, it releases its slot so another request can enter. Each step schedules at most six tokens.

The simulator uses a simple one-token quantum to make the distribution visible. It does not claim to reproduce the exact vLLM implementation or measure milliseconds, throughput or fairness under a real workload.

16. Security and multi-tenancy

Prefix caching shares state derived from prompts. In a multi-tenant environment, review which data may share context and what isolation boundaries are required. Do not assume a cache hit is valid just because two requests look similar in visible text: model, revision, tokenisation, configuration and serialised content belong to the identity that the implementation must respect.

There is a risk beyond hash collisions: the Prefix Caching timing side-channel, documented by vLLM as CVE-2025-46570. A tenant sharing the same backend can measure TTFT differences to infer whether a guessed prefix matches content cached by another user. vLLM security documentation describes a mitigation using cache_salt: the value is mixed into the first KV block hash, so only requests carrying the same salt can share prefix blocks.

In a multi-tenant deployment, the gateway should assign a secret, random salt per tenant (or per user when stricter isolation is required), with sufficient entropy —the guide recommends an unpredictable 256-bit value— and apply it to every request in that scope. Do not use usernames, account IDs or predictable values. Sharing a salt across users in one organisation allows prefix sharing within that group; using one per user reduces sharing and cache hits further. The salt is not an isolation boundary: vLLM does not isolate tenants that share a process. For strong isolation requirements, use separate instances and an authorisation layer that controls which salt each client may use.

response = client.chat.completions.create(
    model=model_name,
    messages=messages,
    extra_body={"cache_salt": tenant_cache_secret},
)

This example assumes tenant_cache_secret is generated and controlled server-side by the gateway; do not accept an unvalidated value from the end user.

The inference endpoint should be treated as a high-compute-cost API: authenticate clients, authorise models, limit input/output tokens, bound concurrency, cancel orphaned work, account usage per tenant and protect metrics/logs against prompt or sensitive-data exposure.

17. Runbook: what to inspect when a vLLM service degrades

SymptomCorrelate firstHypothesis to validate
High TTFT and growing queueQueue time, prompt tokens, prefill time, token budgetPrefill backlog, excess concurrency, long prompts or poorly sized admission limits.
High ITL / TPOTDecode time, running requests, batch tokens, GPU utilisationPrefill contention, oversized batch, memory bandwidth or GPU contention.
KV usage near limitkv_cache_usage_perc, context length, preemptionToo many long sequences, insufficient KV budget or prefixes that cannot be reused.
Frequent preemptionPreemption events, free blocks, sequence lengthsOver-aggressive admission or optimistic memory sizing.
Few prefix cache hitsQueries, hits, common-prefix lengthVariable prefixes, partial blocks, low repetition ratio or frequent eviction.
HTTP 503Admission rejections, queued requests/tokens, healthy replicasIntentional backpressure or insufficient capacity; verify client retry policy.

Practical sequence:

  1. Determine whether degradation is in API, queue, Prefill, Decode, KV allocation or worker.
  2. Compare current prompt/output token distributions with baseline.
  3. Check p50/p95/p99, not averages alone.
  4. Correlate KV usage, running/waiting, prefix hits and preemption.
  5. Check recent changes to model, dtype, flags, hardware, concurrency and prompt size.
  6. Reduce load or apply backpressure before blindly raising limits.
  7. Validate with a reproducible workload and roll back configuration if SLOs worsen.

18. What this chapter does and does not show

This investigation documents the current vLLM V1 architecture and its main KV and scheduling mechanisms. The custom lab validates block allocation, complete-prefix reuse, reference lifecycle, block slack and a teaching token-budget scheduler using the Python standard library.

It does not run vLLM, call a real model, execute PagedAttention kernels, measure TTFT/TPOT, estimate tokens/s or demonstrate GPU scalability. It also does not replicate every detail of the scheduler, hashing implementation or hybrid-model handling. LAB VERIFIED applies only to the simulator and its assertions.

Conclusion

PagedAttention organises KV Cache into physical blocks and lets each sequence reference them through a logical table. Prefix caching can share complete blocks from a repeated prefix when identity and lifecycle constraints match. Continuous batching rebuilds the work set on every iteration and can admit a new request when another finishes. The operational challenge is balancing available blocks, token budget, TTFT, ITL/TPOT, queue depth and memory pressure with explicit backpressure.
