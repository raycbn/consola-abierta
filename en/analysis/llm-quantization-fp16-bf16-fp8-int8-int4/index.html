LLM Quantization: FP16, BF16, FP8, INT8 and INT4 from the inside

A seven-billion-parameter model can require tens of gigabytes just to store its weights in FP32. Quantization reduces that representation, but it is not a matter of replacing every number with a smaller one and calling the job done. We must decide what to quantize, how to scale it, which information to sacrifice, how to calibrate it, which kernel executes the operation and how much model quality survives. We will follow the subject from numeric representation all the way to serving.

The central idea

Quantization represents a tensor using a smaller set of values, together with parameters that explain that representation. The format (FP8, INT8, INT4, NF4), scale granularity (tensor, channel, group), target (weights, activations or KV Cache), algorithm (RTN, GPTQ, AWQ, SmoothQuant) and execution kernel are related but different decisions. A four-bit label alone does not answer any deployment question.

1. Why quantize: memory, bandwidth and serving capacity

In chapter 05 we saw how vLLM manages KV state through blocks and a continuous scheduler. Before the engine can take advantage of those blocks, it must load model weights and execute matrix operations. In many deployments, weights consume a substantial share of available VRAM. Reducing bits per parameter can let a model fit on a smaller GPU, free memory for KV Cache or reduce memory traffic.

There are three distinct motivations:

  • Memory footprint: fewer bits reduce checkpoint payload and, when the runtime keeps weights quantized, resident weight memory.
  • Memory bandwidth: moving fewer bytes can help bandwidth-bound operations. The benefit depends on the kernel, batch size and whether values must be unpacked or converted during computation.
  • Compute throughput: some accelerators provide instructions and Tensor Cores optimized for BF16, FP8 or INT8. A format only improves speed when architecture, matrix shape and backend use an efficient path.

Reducing checkpoint size does not guarantee that total VRAM falls by the same proportion. KV Cache, temporary activations, CUDA graphs, kernel workspaces, communication buffers, runtime memory and higher-precision modules all contribute. Nor does quantization guarantee faster execution: if another phase is the bottleneck, a smaller representation may save memory without improving latency.

2. Range, precision and error: two concepts you must not mix

A numeric format must solve two problems. Dynamic range defines which values can be represented before overflow or underflow. Precision determines the spacing between representable values within that range. In floating point, exponent and significand/mantissa bits share that budget. In integer quantization, the useful range depends on discrete codes and scale parameters.

A format with more range is not automatically more precise. BF16, for example, retains an eight-bit exponent like FP32 but reduces the mantissa. FP16 retains more significand bits but has a smaller exponent. BF16 can therefore tolerate larger magnitudes, while FP16 can distinguish more nearby values in some ranges.

Quantization can introduce several types of error:

  • Rounding error: the real value falls between two levels and is approximated by the nearest one.
  • Clipping / saturation: a value exceeds the chosen range and is forced to the minimum or maximum representable value.
  • Scale error: a poor scale wastes available levels or distorts part of the distribution.
  • Accumulation error: even when operands are quantized, accumulation may use another dtype and has its own numerical error.

3. FP16 vs BF16: same 16 bits, a different budget

Both formats use 16 bits per element, but encode those bits differently:

FormatSignExponentFractionPractical characteristic
FP321823Higher precision reference among these three.
FP16 / binary161510More significand precision than BF16, narrower dynamic range.
BF16187Exponent range similar to FP32; fewer significand bits.

FP16 can represent up to 65,504 as the largest finite binary16 value. A magnitude of 100,000 overflows that format. BF16 retains a wider exponent and can represent that value as a nearby finite number, albeit rounded. The lab reproduces exactly this difference: 100,000 converts to infinity in FP16 and to 99,840 in BF16.

This does not mean BF16 is always better. When values fall within FP16's range, its additional mantissa bits can represent smaller differences. BF16 is attractive in training and inference because it supports a broad range with a 16-bit format; FP16 remains useful when its range limits are acceptable and mantissa precision matters. Model, hardware and framework must be validated: some operations accumulate in FP32 even when inputs are stored in FP16/BF16.

Do not confuse storage dtype, activation dtype, accumulation dtype and output dtype. A layer can store weights in one format, convert them to another inside the kernel and accumulate the result in a third format.

4. FP8: E4M3, E5M2 and the role of scaling

FP8 is not one single format. Two common families are:

  • E4M3: one sign bit, four exponent bits and three fraction bits. It favours relative precision within a more limited range.
  • E5M2: one sign bit, five exponent bits and two fraction bits. It favours dynamic range at the cost of resolution.

FP8 training recipes often use different formats for different directions of computation. NVIDIA Transformer Engine documentation describes a hybrid recipe using E4M3 during forward and E5M2 during backward in a delayed-scaling configuration. The important detail is that a tensor is not simply converted to FP8 in isolation: the runtime needs to estimate and apply scales so values fit the representable range.

Current scaling, delayed scaling and block scaling

Current scaling calculates the scale from statistics of the current tensor. It is straightforward, but may require synchronization or become sensitive to abrupt distribution changes. Delayed scaling keeps a history of amax values and uses recent iterations to select future scales. That history can reduce sensitivity to a single instantaneous value, but adds state and a policy that must be configured.

Block scaling divides a tensor into groups and applies local scales. NVIDIA's documented MXFP8 uses blocks of 32 consecutive values, allowing E4M3 in more positions because each block has its own scale. This is a specific format/recipe architecture: do not assume every checkpoint labelled FP8 uses the same granularity.

In FP8 block-scaled formats, values may require per-block scales and, depending on the format, an additional tensor scale. NVIDIA also documents NVFP4 with blocks of 16 elements and block scales stored in FP8 E4M3 plus an outer FP32 scale. These implementation details explain why a real checkpoint size cannot be derived only by multiplying parameter count by four bits.

5. Integer quantization: scale, zero-point and the formula

In linear quantization, a floating-point value x is mapped to an integer code q. A general formulation is:

q = clamp(round(x / scale) + zero_point, qmin, qmax)
x_hat = scale * (q - zero_point)

scale defines the step between adjacent integer codes in the real domain. zero_point establishes which code represents real zero exactly. qmin/qmax define the available discrete set. When reconstructed, x_hat need not equal x: the difference is quantization error.

Symmetric quantization

For a signed symmetric integer, the zero-point is usually zero and the scale is calculated from the maximum absolute value:

qmax = 2^(bits - 1) - 1
scale = max(abs(x)) / qmax
zero_point = 0

q = clamp(round(x / scale), -qmax, qmax)
x_hat = q * scale

For INT8, a conceptual implementation may use −127 to 127 and leave −128 unused to maintain symmetry. For signed INT4, this laboratory uses −7 to 7 for the same reason. Other formats and serializations may use different integer ranges; read the checkpoint and backend rather than assuming every INT4 implementation reserves the same codes.

Asymmetric affine quantization

To represent a shifted distribution, observed minimum and maximum values can be mapped to the integer range:

scale = (xmax - xmin) / (qmax - qmin)
zero_point = round(qmin - xmin / scale)
q = clamp(round(x / scale) + zero_point, qmin, qmax)
x_hat = scale * (q - zero_point)

The exact zero-point calculation, rounding and clamping depend on dtype and implementation. It is important that real zero can be represented exactly, for example when padding with zeros. ONNX Runtime documents this representation with scale and zero-point and distinguishes symmetric from asymmetric forms.

In a weight-only scheme, weights are stored as low-precision integers and the runtime may unpack or dequantize them before computation. In W8A8, both weights and activations may be quantized and use an integer matrix multiplication path, provided a compatible kernel exists.

6. Per-tensor, per-channel and per-group: where each scale lives

Granularity determines how many values share one scale and, when applicable, one zero-point. This is one of the most important quantization trade-offs:

  • Per-tensor: one parameter set for the entire tensor. It consumes little metadata and is simple, but one outlier can dominate the shared scale.
  • Per-channel: one scale per channel, for example one per row of a weight matrix [out_features, in_features]. Each channel adapts its range independently.
  • Per-group: each channel is divided into groups of G values and gets a local scale per group. This can reduce reconstruction error but adds scales and packing/alignment requirements.
  • Per-block: a similar local-scaling idea, but block definition and layout are tied to the format and kernel. There is no single universal convention.

Metadata cost can be made explicit. Consider INT4 with one FP32 scale for every 64 weights and no zero-point: payload contributes 4 bits per weight and the scale contributes 32/64 = 0.5 average bits per weight. The idealized total becomes 4.5 bits per parameter, before padding and other metadata. With one scale every 16 weights, scale cost rises to 4 + 32/16 = 6 bits per weight. Finer granularity has a real cost.

The best granularity is not selected by MSE alone. Kernel availability, supported block sizes, matrix shapes and scale serialization also matter.

7. Outliers, clipping and saturation: the extreme value that controls the range

LLMs can produce distributions where channels or activations have very different magnitudes. If a per-tensor scale is based on the largest absolute value, most smaller values may use only a limited part of the available integer levels. Reducing the range with clipping improves resolution for common values, but some extremes saturate and lose magnitude.

Calibration can use absmax, percentiles, histograms, optimized clipping or other criteria. But “use the 99th percentile” is not a universal rule. When production contains rare but relevant events, discarding them during calibration may cause saturation precisely in the cases that matter.

There are also two activation quantization modes:

  • Dynamic quantization: statistics and scales are calculated during inference or over operational windows. It adapts to input data, but adds runtime work and is not equally supported by every kernel.
  • Static quantization: a scale is estimated offline using calibration data and reused during inference. Cost moves to model preparation, but the real distribution must resemble calibration data.

In the lab, INT8 absmax had an RMSE of 0.0293 on the synthetic set. p99 clipping reduced the quantization step but saturated 16 of 1,536 values and reached RMSE 0.4934, much worse because of those outliers' magnitude. The conclusion is not “absmax always wins”; it is that selecting a threshold without studying the distribution tail can badly damage reconstruction.

8. W4A16, W8A8, W4A8: read the complete precision policy

W/A notation indicates the precision used for Weights and Activations. The digits represent nominal bit widths for those representations, but do not by themselves describe scales, accumulation, exceptional weights or final output representation.

SchemeWeightsActivationsMeaningTypical goal
W4A16INT4 / FP4FP16 / BF16Low-precision weight-only; 16-bit activations.Reduce weight footprint while retaining a more conservative activation path.
W8A8INT8 or FP8INT8 or FP8Both weights and activations are quantized.Reduce traffic and use low-precision arithmetic where supported.
W4A8INT4INT8Four-bit weights and eight-bit activations.More aggressive compression with lower-precision activations.
W4A4 / NVFP4FP4FP4Both operands use 4-bit formats with specific scaling.Hardware paths designed for FP4 formats.

W4A16 does not mean the entire multiplication necessarily runs with four-bit operands. The kernel may unpack and dequantize weights to higher precision before multiplication. In other schemes, quantized operands can enter a specialized instruction and accumulate in higher precision. Only inspection of the checkpoint format, actual kernel path and runtime can tell you what happens.

9. Calibration datasets: teach the quantizer how the model behaves

Data-aware algorithms observe activations from representative samples to decide which channels are more sensitive, where outliers live or which scale preserves layer behaviour best. The full model does not necessarily need to be retrained, but calibration inputs must represent expected use.

A calibration process should control at least:

  • Domain alignment: conversation data for a chat model; code for a coding assistant; legal or technical text when those domains dominate traffic. A generic collection may not represent real prompts.
  • Chat template and tokenizer: the template changes token sequences, separators, role tokens and length distributions. Calibrating with a different template can invalidate part of the observation.
  • Sequence length: include representative lengths, not only short examples when the service accepts long contexts.
  • Distribution tails: capture rare examples with extreme magnitudes when they matter to the product's SLO or function.
  • Sampling and privacy: use data with appropriate provenance, permissions and protection; do not include confidential user prompts without a legitimate basis.

LLM Compressor guides mention WikiText/C4 for general text, UltraChat for instructions and domain-specific datasets for coding. As a starting point they mention 128–512 samples for many algorithms, but the final amount depends on model, sequence length and objective. It is an operational starting point, not a quality guarantee.

10. PTQ vs QAT: when should training change?

Post-Training Quantization (PTQ) quantizes an already trained model, usually keeping original weights frozen during the process. RTN can do this without calibration data; GPTQ, AWQ and SmoothQuant use statistics or transformations derived from calibration data. The attraction of PTQ is avoiding full retraining.

Quantization-Aware Training (QAT) introduces quantization effects during training or fine-tuning, for example with fake quantization in forward and approximate gradients during backward. The model can adapt to the reduced representation, but training, pipeline and validation costs are higher.

QAT is not the same as loading a model in 4-bit and training some LoRA adapters. QLoRA is a parameter-efficient fine-tuning recipe over frozen quantized base weights, with trainable adapters and dequantization/compute in higher precision. It is related, but should not be confused with a generic full-model QAT recipe.

11. RTN: the baseline worth measuring first

Round-to-Nearest (RTN) is direct quantization: select the scale, divide the value by it, round to the nearest code and clamp it to the integer range. It does not require a calibration dataset when the range is derived directly from weights. It is fast, easy to audit and a useful baseline for deciding whether a more complex algorithm justifies its cost.

The problem becomes more visible as bit width decreases. Independent rounding does not consider how much each weight contributes to layer output or how errors might be compensated by remaining weights. RTN is sufficient for some models and formats, but simple rounding should not be assumed to preserve every LLM at four bits.

12. GPTQ: quantize with second-order information

GPTQ (Frantar et al.) is a one-shot post-training, weight-only method that quantizes weight matrices using approximate second-order information. Its core intuition is that weights are not equally sensitive: the effect of changing one weight depends on the activations entering the layer and on the geometry of output error.

Conceptually, it estimates an approximation of the Hessian / second-order information from calibration activations, processes the matrix in an order, rounds weights and compensates for error across weights that have not yet been processed. The compensation seeks to minimize layer output error rather than only element-wise weight error. The original paper demonstrated 3–4 bit quantization on large models; published results depend on architecture, dataset, implementation and hardware.

GPTQ does not mean that every weight in every model is converted to one universal file. Checkpoints include configuration, group size, scales, zero-points and packing. The runtime must understand that metadata and provide a compatible kernel.

13. AWQ: protect channels that matter to activations

Activation-aware Weight Quantization (AWQ) starts from a practical observation: some activation channels are associated with more sensitive weights. The algorithm uses activation statistics from calibration samples to estimate saliency and apply equivalent channel scaling that reduces quantization error for important weights.

The goal is not to store a huge list of weights in FP16 while the rest are INT4. AWQ seeks to transform channels so low-bit weight quantization behaves better while remaining hardware-friendly. The paper highlights that a small fraction of weights/channels can concentrate much of the sensitivity, and activation statistics can identify them better than looking at weights in isolation.

AWQ is commonly associated with weight-only INT4, but the method and checkpoint should not be reduced to a marketing label. Support depends on model, quantization scheme, packing and available backend.

14. SmoothQuant: move activation difficulty into weights

Activations can contain outliers that make uniform INT8 difficult. SmoothQuant uses an algebraically equivalent transformation to redistribute magnitude between activations and weights. For a linear layer y = W x, a conceptual form is:

W' = W D
x' = D^-1 x

W' x' = W D D^-1 x = W x

D is a diagonal matrix with positive per-channel factors. If selected well, the distribution of x' is smoothed and some magnitude is transferred into W'. The computation is equivalent in real arithmetic; after transformation, the quantizer can represent both operands with less loss. The SmoothQuant paper proposes this offline migration to make W8A8 viable for language models.

This equality is the algebraic core of the mechanism, not a complete SmoothQuant implementation. The lab verifies the transformation's invariance on a small matrix; it does not calibrate a real model or implement the paper's algorithm.

15. NF4, FP4, INT4 and GGUF: four names that do not mean the same thing

  • INT4: four-bit integer codes, usually accompanied by scales per tensor, channel or group and, depending on the scheme, zero-points.
  • FP4: a four-bit floating-point format. NVFP4, for example, uses E2M1 and block scaling; it is not INT4 under another name.
  • NF4: NormalFloat4, a non-uniform quantization based on quantiles, designed for weights approximately following a normal distribution. It is a component of QLoRA, not the same uniform linear mapping as INT4.
  • GGUF: a file/container format used in the llama.cpp ecosystem that can store weights in several quantization schemes. GGUF does not itself designate one quantization algorithm.

QLoRA adds double quantization: after quantizing weights, it also quantizes the constants/scales from the first quantization to reduce metadata overhead. The paper explains that a FP32 scale for every group of 64 weights adds 0.5 bits per weight on average; reducing scale cost can matter nearly as much as reducing payload.

When evaluating a 4-bit checkpoint, inspect at least: algorithm, dtype/code, group size, symmetric/asymmetric mode, zero-point, scale type and precision, unquantized modules, activation dtype, compute dtype, layout/packing and required backend. Do not swap models simply because both say “4-bit”.

16. Memory sizing: from bits per parameter to actual VRAM

The simplest weight approximation is:

weight_bytes ≈ parameter_count × bits_per_parameter / 8

For a 7-billion-parameter model, excluding scales and special modules:

RepresentationBits/parameterDecimal payloadBinary payload
FP323228 GB26.08 GiB
FP16 / BF161614 GB13.04 GiB
FP8 / INT887 GB6.52 GiB
INT4 raw payload43.5 GB3.26 GiB
INT4 + FP32 scale per 64 weights4.5 estimated3.94 GB3.67 GiB

Decimal GB uses 1,000,000,000 bytes; GiB uses 1,073,741,824 bytes. The 4.5-bit row includes one FP32 scale per 64 weights, without zero-points or padding. It is a metadata example, not a promise that every INT4 checkpoint will occupy exactly that amount.

Total GPU consumption must add weights, KV Cache, temporary activations, execution buffers, workspaces, communication memory, modules kept in FP16/BF16/FP32 and allocator reservations. Also consider whether weights are replicated or sharded across GPUs. A model that fits based on weights alone may still fail when admitting long sequences or high concurrency.

17. Quantized KV Cache: compress attention state, not the model

KV Cache stores Keys and Values for every token retained in the context. An approximate payload formula is:

KV_bytes =
  2 × num_layers × batch_sequences × context_tokens
    × num_kv_heads × head_dim × bytes_per_element

The factor 2 represents Key and Value. Consider 32 layers, 16 sequences, 8,192 tokens per sequence, 8 KV heads and head_dim 128. At two bytes per element, ideal payload is 16 GiB. At one byte, it falls to 8 GiB; at half a byte, to 4 GiB before packing and scales. This excludes metadata and real runtime buffers.

Weight quantization reduces persistent model memory. KV Cache quantization reduces the cost of each active context token and can allow longer contexts or more concurrent sequences. These are different levers. An INT4 weight model can still use FP16/BF16 KV Cache; low-precision weights can also be combined with FP8 KV.

Current vLLM documentation describes FP8 KV Cache with per-tensor and per-attention-head schemes. The per-head scheme currently requires the FlashAttention backend and the LLM Compressor calibration path. Without calibration, default scales of 1.0 are used; with calibration, a dataset is needed. Some sensitive layers, such as certain sliding-window variants, may be excluded using the documented skip-layers option. Do not assume every model and backend supports the same route.

18. Backend and kernel: a format only matters if something can execute it

A compressed representation needs a kernel that understands its layout, scales and accumulation method. The backend determines whether the operation runs as integer GEMM, FP8 Tensor Core, dequantization + higher-precision GEMM, or another path. The same quantization can have very different performance with another group size or matrix dimension.

vLLM documentation reviewed for this chapter lists options including AutoAWQ, BitsAndBytes, GPTQModel, Intel Neural Compressor, LLM Compressor, NVIDIA Model Optimizer, AMD Quark, TorchAO and quantized KV Cache, among others. It also documents several LLM Compressor schemes — FP8 W8A8, INT4 W4A16, INT8 W4A8 and INT8 W8A8 — and the choice of linear backend. Hardware support varies by implementation and changes with releases.

Before deployment, verify:

  • Exact architecture and checkpoint version, not just the model family.
  • GPU, compute capability, driver, CUDA/ROCm and PyTorch/vLLM versions.
  • Quantization method, group size, scales, zero-points and packing declared by the checkpoint.
  • Kernel support for real shapes: hidden size, intermediate size, head count, batch and sequence length.
  • Whether the runtime falls back to a slower path or rejects the model during initialization.

Backend loading is a necessary condition, not proof that acceleration is active. Check logs, selected kernel, memory consumption and execution profile.

19. Validation: tensor error is not model quality

MAE, MSE, RMSE, maximum absolute error, relative L2 and SQNR help measure how far reconstructed values are from the originals. However, a small weight difference can alter an important activation, change logits and modify generated tokens. Local error is not equivalent to functional LLM error.

A solid validation plan keeps three layers separate:

A. Numeric / layer validation

  • Reconstruction error by layer, channel, block and module.
  • Activation and logit drift against the higher-precision baseline.
  • Cosine similarity, relative error, saturation rate and outlier distribution.
  • NaN/Inf, overflow and long-context stability checks.

B. Model quality validation

  • Perplexity on a representative corpus and the correct tokenizer.
  • Product task benchmarks: instruction following, code, maths, extraction, RAG or classification.
  • Deterministic generation with regression prompts, plus sampling tests when the product uses sampling.
  • Language, structured output, tool-calling, safety, refusal and edge-case evaluation.
  • Segmented and extreme-case evaluation; a global average can hide regressions.

C. Serving / performance validation

  • TTFT, TPOT / inter-token latency, token throughput, requests per second and p50/p95/p99 percentiles.
  • Measurement with the same workload, concurrency, prompt/output distribution, context length and warmup.
  • Real GPU memory, utilization, bandwidth, cache hit, queues, errors and backpressure behaviour.
  • Cost per million tokens or request, not only maximum tokens/s from a microbenchmark.

A matrix-multiplication benchmark does not necessarily represent a service with continuous batching, long prefills and concurrent clients. Quantization must be validated against the production profile, not an attractive but disconnected number.

20. A quantization workflow for production

  1. Freeze the baseline: original checkpoint, dtype, model, tokenizer, prompts, tasks, hardware, configuration and metrics.
  2. Identify the limit: weight memory, KV Cache, bandwidth, compute, context, cost or concurrency. Do not quantize just because it is fashionable.
  3. Choose the target: W-only, W/A, KV Cache or a combination. Decide which memory you want to free.
  4. Select format and scheme: FP8/INT8/INT4/NF4, per-tensor/channel/group/block, compute dtype and scale policy.
  5. Select algorithm and calibration: RTN as a baseline; GPTQ/AWQ/SmoothQuant when objective and distribution justify them.
  6. Verify the actual backend: supported kernel, version, hardware, layout and fallbacks.
  7. Evaluate in stages: numerical error, model quality, then service performance.
  8. Canary: deploy limited traffic, compare real distributions, inspect logs/latency and preserve rollback to the prior checkpoint.
  9. Record artifacts: checkpoint hash, recipe, calibration dataset/version, seed, libraries, hardware, metrics and final decision.

21. Serving with vLLM: keep weights and KV Cache separate

Support changes across releases, so commands must be adjusted to the checkpoint and compatibility table for the installed version. The first example is serving a checkpoint that already declares its quantization format:

# Example: checkpoint includes its quantization metadata.
vllm serve <quantized-model-checkpoint>

Do not force a method based on intuition. Some configurations are inferred from model metadata; others require an explicit quantization parameter. The exact method depends on checkpoint family and installed version.

KV Cache is an independent decision. Current documentation includes the option:

vllm serve <model> --kv-cache-dtype fp8

To skip particular sensitive layers, the documentation shows:

vllm serve <model> \
  --kv-cache-dtype fp8 \
  --kv-cache-dtype-skip-layers sliding_window

These examples show documented flags, not a universal recipe for every GPU. Before running them, review the quantized KV Cache section for the installed release, backend compatibility and calibration requirements. Do not expose a serving endpoint to public interfaces without appropriate network, authentication and access controls.

23. Reproduced lab: RTN, scales and numerical error

The included lab implements a mathematical simulator using the Python standard library. It generates a synthetic 32 × 64 weight matrix with channels of different magnitudes and a few deliberate outliers, then compares several linear quantization schemes. The activation set is synthetic as well and contains a few deliberately extreme values.

Lab scope

CPU-only, no GPU, CUDA, PyTorch, Transformers or model downloads. It implements educational symmetric INT8/INT4 and asymmetric INT4 RTN with per-tensor, per-channel and per-group scales. It emulates binary16/BF16 rounding and small linear operations. GPTQ, AWQ, SmoothQuant and FP8 kernels are discussed in the article but are not presented as implemented.

The experiments include:

  • FP16 vs BF16: rounding, dynamic range and overflow.
  • INT4/INT8: weight reconstruction, MSE, RMSE, maximum error, relative L2 and SQNR.
  • Global, per-channel and per-group (16/32 weights) scales, including estimated FP32 scale cost.
  • Synthetic W4A16-style and W8A8-style linear projection to quantify output drift.
  • Absmax vs p99 clipping to show the effect of outliers and saturation.
  • Algebraic channel transform W' = W D and x' = D^-1 x to verify equivalence at working precision.
  • Ideal weight memory arithmetic for a 7B-parameter model and a representative GQA KV Cache.

Per-channel INT4 reduced MSE from 0.157819 to 0.028064 compared with per-tensor on this heterogeneous matrix. Per-group-16 reduced it to 0.014677, but estimated scale cost rose to six bits per weight. This is a concrete trade-off: more granularity improves this reconstruction and consumes more metadata.

In the linear projection, the W4A16-style path achieved RMSE 0.848397 and W8A8-style 0.146636 against the FP32 reference. These are not Transformer quality measurements; they describe drift for one matrix and 24 synthetic vectors.

p99 calibration clipped 16 of 1,536 values and produced RMSE 0.493419, compared with 0.029264 for absmax on this set. The lesson is not “absmax wins”; choosing a threshold without studying the distribution tail can make reconstruction much worse.

Finally, for 7B parameters, ideal payload falls from 14 decimal GB in FP16 to 7 GB in FP8/INT8 and 3.5 GB in INT4 without metadata. The GQA KV Cache example falls ideally from 16 GiB in FP16/BF16 to 8 GiB in FP8. These are representation calculations, not server VRAM measurements.

The ZIP contains six CSV tables, a detailed report and metrics.json with versions, seed, configuration and limitations. The script was run again after generating the evidence; it does not depend on previously written results.

25. Limits and conclusions

Quantization is a problem of representation, statistics, architecture and execution. FP16/BF16 balance range and precision differently. FP8 adds E4M3/E5M2 formats and scaling recipes. INT8/INT4 need scales, zero-points and granularity decisions. GPTQ, AWQ and SmoothQuant try to preserve behaviour better than independent rounding. NF4 and NVFP4 show that even four-bit formats are not all the same.

The right choice starts by measuring what limits the service. If weight memory is the problem, a W4A16 path may be attractive; if compute is the limit and hardware has suitable kernels, W8A8/FP8 may make sense; if the issue is concurrent context state, the better lever may be KV Cache quantization rather than changing weights. Success requires evaluating the exact checkpoint and backend with representative tasks and traffic.

This chapter's lab teaches quantization mechanics and error; it does not quantize a real model or predict its quality. That distinction is deliberate: good engineering requires honest evidence about what was and was not measured.
