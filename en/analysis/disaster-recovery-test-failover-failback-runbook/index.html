A Disaster Recovery Test Failover and Failback Runbook: Isolation, Validation and Controlled Return

An enterprise runbook for test failover and failback: approvals, isolation, dependencies, abort conditions, data reconciliation, cleanup and evidence.

Safety rule

A test failover, a production failover and a failback are different operations. They must not share the same scope or approval by default. This runbook describes an operating method; it is not an instruction to trigger a production switchover.

This is the second stage of the Resilience & Recovery path. The first investigation explains how to design a Disaster Recovery test and measure RTO/RPO. This article turns that design into a controlled operating sequence: who authorizes it, what must be isolated, which dependency starts first, when to abort and how to return to the primary site without losing changes written during an outage.

1. Do not conflate test failover, failover and failback

Button names vary by platform, but the operational objectives are different:

OperationPurposeExpected impactAuthorization
Test failoverExercise recovery in a controlled test environment.The source keeps serving users; the test network stays isolated and receives no real production traffic.Approved exercise change, scope and isolation controls.
Production failoverMove service delivery to the recovery environment.The recovery environment may become authoritative and take production writes and user traffic.Disaster declaration and recovery authorization under the crisis plan.
FailbackReturn service to a recovered site or an agreed alternative location.Requires an authoritative data decision, synchronization of changes and a controlled cutover.Separate change, approved data reconciliation and return window.

A test failover does not, by itself, prove that a production failover is safe: traffic, routes, permissions, external dependencies and load may differ. Likewise, restoring the primary site does not mean it is ready to accept writes. First decide which copy contains the valid changes and how they will be synchronized.

2. Assign responsibilities before opening the window

The exercise lead must have the authority to stop the exercise. Every technical step needs an identifiable owner and verifiable evidence. Avoid having one person authorize, execute and accept the entire exercise without review.

RolePrimary responsibility
Exercise lead / DR coordinatorScope, timing, communications, continue/abort decisions and milestone log.
Service owner / businessPriorities, acceptance criteria, tolerable impact and functional service acceptance.
DR / platformReplication health, recovery-point selection, technical orchestration and cleanup.
Network and securityIsolation, routes, DNS, firewalls, load balancers, certificates and exposure review.
Identity and middlewareDirectory, authentication, DNS, NTP, PKI, secrets and shared services.
Data / DBAConsistency, integrity, recovery point, authorized writes and reconciliation.
Observers / evidence ownersScreenshots, timestamps, logs, incidents, deviations and corrective actions.

The final RACI depends on the organization's governance model. At a minimum, document one accountable operational decision-maker and one service acceptance owner, even when they belong to the same team.

3. Preflight: close the conditions before starting

Do not start when a critical condition depends on an assumption or pending approval.

  • Scope and change: service, components, sites, dependencies, window, owners, communications, PASS/FAIL criteria and exclusions approved.
  • Replication: healthy state, last synchronization, observed lag, errors, selected recovery point and expected RPO recorded.
  • Capacity: quotas, CPU, memory, storage, IP addresses, licenses, IOPS limits and network capacity sufficient at the recovery site.
  • Access: emergency accounts, MFA, certificates, secrets, bastion/jump host and limited temporary permissions tested.
  • Dependencies: identity, DNS, DHCP where applicable, NTP, PKI, storage, databases, middleware, queues and external services inventoried.
  • Security: segmentation, ingress/egress rules, routes, peering, tunnels, NAT, load balancers and public exposure reviewed.
  • Validation: approved synthetic transactions, test data, an available business user and tests that cannot trigger real external side effects defined.
  • Exit: abort criteria, rollback, cleanup, evidence retention and confirmation that production remains under the expected control.

A test labelled “non-disruptive” by a vendor does not replace analysis of the complete environment. Isolation must be verified across the actual routes, firewalls and shared services in the architecture.

4. Isolation: prevent duplicate identities and routes

The test network must be separate from production and from any recovery network serving real traffic. Separation must work in both directions: creating a differently named subnet is not enough when a route, peering, VPN, DNS resolver or firewall rule still connects the environments.

  • Use a dedicated test network with no production route advertisements and no site-to-site connectivity unless it is specifically designed, approved and controlled for the exercise.
  • Verify that test resources do not publish DNS records, VIPs, BGP routes or load-balancer entries that send real users to the exercise environment.
  • Avoid running copied domain controllers or systems with duplicate identities on a shared network. AD/DNS recovery needs an isolation and dependency design of its own.
  • Define how names, certificates, secrets, endpoints and third-party calls resolve inside the test environment. A DNS response pointing back to production breaks logical isolation.
  • Use synthetic transactions and test accounts; block sends, payments, notifications and writes to real external systems.

Microsoft documents an isolated network for test failover and recommends recovering the Active Directory/DNS dependency first when an application needs it. Do not copy AD-specific instructions without reviewing the topology: domain controllers have their own safeguards and requirements.

5. Sequence by dependency, not habit

A typical multi-tier service sequence can be a starting point, but the dependency graph must reflect the actual service:

  1. Recovery plane and network: management connectivity, isolated segmentation, security rules, addressing and test routes.
  2. Identity and foundation services: directory, DNS, NTP, PKI, secrets and services required to authenticate or locate other components.
  3. Data: volumes, storage, databases, queues and consistency checks for the recovered point.
  4. Middleware and application: runtimes, services, APIs, workers, schedulers and internal dependencies.
  5. Ingress and acceptance: test load balancer, certificates, expected name resolution, synthetic transactions and business acceptance.
  6. Closure: metrics, evidence, temporary-resource cleanup and confirmation that the original replication path is healthy.

This is not a universal order. A service may need a secrets store before the database or a broker before certain workers. Model dependencies with explicit ordering, owners and exit criteria; machine boot order is not the same as service recovery order.

6. Run the test failover

  1. Briefing: confirm scope, window, recovery point, owners, coordination channel and start time. Record production health before touching the test environment.
  2. Isolation gate: verify routes, rules, DNS, administrative access and production-traffic blocking. A second operator reviews the evidence before proceeding.
  3. Controlled recovery: use the platform's test-failover operation and the approved recovery point. Do not replace a test with a normal failover or an improvised restore.
  4. Dependencies: recover identity, DNS and foundation services before dependent components. Record failures, retries and timings.
  5. Technical validation: check boot, mounts, services, name resolution, authentication, certificates, firewalls, connections, data consistency and telemetry.
  6. Service validation: run approved synthetic transactions, check agreed functions and obtain functional-owner acceptance. “VM is running” is not an acceptance criterion.
  7. Exercise closure: record observed RTO/RPO, deviations, incidents, decisions and evidence before cleaning up test resources.

When the test environment mirrors production, document which values have been substituted: IP, hostname, DNS, URLs, certificates, accounts, secrets, endpoints, rules and data. Those differences are part of the test result.

7. Failback: data authority is the critical problem

Failback is not “turning the old site back on”. During an outage, new writes may have been accepted at the recovery site. Restarting the source without fencing and reconciliation can create two sources of truth, split-brain or lost transactions.

  1. Re-establish the target: confirm that the return site is recovered, patched to the agreed state, protected and adequately sized. Identify current source and target roles; they may have swapped.
  2. Protect data authority: determine which environment may accept writes. Define a freeze window, fencing, read-only mode or quiesce mechanism to prevent simultaneous changes.
  3. Reprotect / reverse replication: configure the correct replication direction to send valid data from the active environment to the return target. Do not assume the replication engine changes direction automatically.
  4. Check convergence: verify replication state, lag, consistent recovery point, errors, log ordering and integrity criteria. Define the cutover threshold before the window.
  5. Reconcile: resolve writes made during the outage using the approved data procedure. Technical synchronization does not replace functional reconciliation.
  6. Planned cutover: stop or drain writes as designed, confirm the last valid point, switch routes/DNS/load balancers and move traffic only after business and operational authorization.
  7. Post-cutover validation: verify login, critical functions, transactions, data, monitoring, performance and business acceptance. Keep an explicit criterion for returning to the previous environment if validation fails.
  8. Continuous protection: restore replication in the direction appropriate to the new primary and confirm health before closing the change.

Exact steps depend on the product. In Azure Site Recovery, return may require reprotect to reverse replication before failback. In AWS Elastic Disaster Recovery, replication back and traffic redirection are distinct responsibilities. Do not extrapolate one vendor's workflow to another.

8. Abort and rollback conditions

Set thresholds before the exercise. Stop progression and escalate when any of the following occurs:

  • Unexpected connectivity to production, route publication or user traffic to the test environment is detected.
  • Duplicate identities, writes to the wrong system or an unidentified authoritative source are discovered.
  • The recovery point misses the approved RPO, consistency fails or the application does not pass a critical test.
  • Replication degrades, primary-site health is affected or the exercise exceeds the agreed window and impact limits.
  • The authorized decision-maker is unavailable or required evidence is lost, making continuation unjustifiable.

Rollback cannot mean “switch the VMs off”. State which resources are reverted, who controls them, how traffic is restored, what data is retained, how primary health is checked and under what condition replication resumes. In a production failback, the return procedure may require another synchronization; do not improvise a direction reversal.

9. Cleanup and exercise closure

After a test failover, use the product's cleanup workflow and verify its result. Review VMs, disks, NICs, IPs, snapshots, temporary rules, load balancers, DNS records, accounts, secrets, routes and monitoring resources created for the test. Delete only resources identified as temporary for the exercise, never by name similarity alone.

Then confirm production replication remains in the expected state, no test endpoints remain published and temporary resources do not create cost or false alerts. Retain approved evidence, not unnecessary data copies or secrets. The evidence pack must reconstruct what happened, when, who authorized it, the result and what was cleaned up.

10. Evidence and improvement actions

At a minimum, retain:

  • Runbook version, scope, change, participants, approvals and scenario.
  • Replication health and selected recovery point before and after the exercise.
  • Network isolation, routes, firewall, DNS and identity-service evidence.
  • Timestamped milestones, owners, log references and the outcome of each acceptance criterion.
  • Observed RTO/RPO, errors, deviations, incidents and continue/abort decisions.
  • Temporary-resource inventory, cleanup evidence and confirmation that protection returned to a healthy state.
  • Corrective actions with priority, owner, target date and a method to verify closure.

Turn observations into an After-Action Report / Improvement Plan. A problem list without an owner or due date is not a manageable improvement plan. CISA recommends documenting exercise results, improvement areas, owners and timelines in the post-exercise cycle.

11. Offline lab: Recovery Runbook Preflight

The companion lab validates the structure of a JSON test-failover or failback plan. It checks declared controls, mandatory phases, stop conditions, owners, evidence references, dependencies, cycles and ordering. It returns PASS/FAIL and a dependency-derived execution order.

python runbook_preflight.py samples/test-failover.json
python runbook_preflight.py samples/failback.json --json-out report.json --markdown-out report.md
python -m unittest discover -s tests -v
Functional boundary: this is an offline plan linter. It does not physically verify isolation, query replication, validate declared controls, run VMs, restores, failover, failback, traffic or data reconciliation. PASS does not authorize a change or prove recovery works. The examples are synthetic.
