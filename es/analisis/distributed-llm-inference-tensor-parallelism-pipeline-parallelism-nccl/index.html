Distributed LLM Inference: Tensor Parallelism, Pipeline Parallelism y NCCL

Una GPU se queda pequeña. La solución parece sencilla: añadir más. Pero un LLM distribuido no es un modelo que mágicamente se vuelve más rápido al conectarle aceleradores. Hay que decidir qué dimensión se particiona, qué tensores se mantienen replicados, qué datos viajan entre ranks, qué colectivos sincronizan cada capa y qué enlaces físicos transportan esos bytes. En este capítulo vamos desde el álgebra de una Linear hasta la topología multi-node que determina si ocho GPUs colaboran o pasan el tiempo esperando a la red.

La idea central

Distributed inference no consiste en dividir el número de GPUs entre el tamaño del modelo. Consiste en elegir un layout de tensores y una topología de ejecución. Tensor Parallelism divide el cálculo dentro de capas; Pipeline Parallelism divide la profundidad; Data Parallelism replica el modelo para repartir peticiones. Cada estrategia mueve datos diferentes y tiene un coste distinto. La interconexión física es parte del diseño, no un detalle de infraestructura que se resuelve después.

1. Por qué distribuir: capacidad, latencia y throughput son objetivos diferentes

En los capítulos anteriores hemos reducido la precisión de los pesos con quantization y aprendido cómo vLLM administra memoria KV y peticiones mediante Continuous Batching. Aun así, un modelo puede no caber en una GPU, consumir demasiada memoria para mantener suficiente KV Cache o no alcanzar el throughput objetivo. Distribuir la inferencia permite repartir pesos, operaciones o carga entre varios aceleradores.

Conviene separar tres objetivos:

  • Capacity: el modelo o su estado no cabe en una GPU. La prioridad es que cada dispositivo almacene una fracción del modelo y que la inferencia sea posible.
  • Latency: queremos reducir el tiempo de respuesta de una petición. El paralelismo puede acelerar operaciones matriciales, pero introduce comunicación y sincronización. No toda estrategia disminuye el tiempo end-to-end.
  • Throughput: queremos servir más tokens o peticiones por segundo. Podemos ganar throughput solapando trabajos independientes, replicando modelos o manteniendo ocupadas varias etapas.

Una estrategia puede resolver Capacity sin mejorar Latency. Pipeline Parallelism, por ejemplo, puede permitir que un modelo que no cabe en un dispositivo se ejecute en varios, pero una secuencia individual debe atravesar todas las etapas. El beneficio de throughput aparece cuando hay suficientes peticiones independientes que pueden ocupar la pipeline.

El primer criterio sigue siendo sencillo: si el modelo cabe en una GPU y el rendimiento cumple el SLO, no introduzcas distribución solo porque tienes más aceleradores. La complejidad de procesos, red, recuperación de fallos y observabilidad también es coste operativo. La guía actual de vLLM recomienda comenzar con una GPU cuando es suficiente, usar TP dentro de un nodo cuando el modelo requiere varias GPUs y combinar TP/PP cuando hay que extenderse entre nodos. vLLM — Parallelism and Scaling.

2. Los ejes de parallelism: no todos dividen lo mismo

StrategyQué divideQué replicaObjetivo principal
Tensor Parallelism (TP)Dimensiones de pesos y operaciones dentro de una capa.Partes de la activación o resultados intermedios, según layout.Repartir matrices grandes y memoria de pesos.
Pipeline Parallelism (PP)Capas consecutivas del modelo por etapas.El trabajo de cada etapa sobre microbatches diferentes.Repartir profundidad y memoria entre dispositivos.
Data Parallelism (DP)Batch o peticiones entre réplicas.El modelo completo en cada réplica.Escalar el número de peticiones concurrentes.
Context Parallelism (CP)Dimensión de secuencia/contexto.Modelo y parte del estado según implementación.Procesar contextos largos distribuyendo tokens.
Expert Parallelism (EP)Expert networks de un modelo Mixture-of-Experts.Router y partes compartidas según arquitectura.Distribuir expertos activados dinámicamente.

En serving de un LLM dense, TP y PP son los ejes centrales para repartir una sola réplica del modelo. DP suele operar en otra dimensión: múltiples réplicas independientes que reciben peticiones diferentes. CP aparece cuando el contexto es tan largo que conviene distribuir la secuencia. EP es relevante para MoE, donde el routing introduce comunicación All-to-All y tráfico entre expertos.

No confundas Model Parallelism con Data Parallelism. En TP/PP, una sola inferencia necesita colaborar entre ranks para producir el siguiente token. En DP, una petición normalmente se ejecuta en una réplica concreta; no necesita sincronizar los pesos con las otras réplicas durante cada token.

3. Rank, local rank, world size y process groups

En una ejecución distribuida, cada proceso participante recibe un identificador global, el rank. El total de procesos participantes es world size. En sistemas multi-GPU, un proceso suele controlar una GPU, aunque el mapping exacto depende del runtime. El local rank identifica su posición dentro del nodo. No es lo mismo que el índice físico de la GPU ni debe asumirse que rank 0 corresponde siempre a GPU 0.

Un process group define qué ranks colaboran en una operación. Esto importa cuando combinamos TP, PP y DP. En una malla 2D TP×PP, cada pipeline stage puede contener un grupo TP. Los colectives de una capa se lanzan dentro del grupo correcto, mientras que las activaciones pasan por comunicación punto a punto hacia la siguiente etapa.

world_size = TP × PP × DP

global_rank = rank in the entire job
local_rank  = rank within a node
tp_group    = ranks that shard one layer
pp_group    = ranks that own consecutive model stages
dp_group    = independent model replicas

Esta fórmula es una simplificación de una malla rectangular estándar. Context Parallelism y Expert Parallelism añaden dimensiones y grupos adicionales. En sistemas heterogéneos o layouts no uniformes, el mapping debe documentarse explícitamente.

Un error clásico es crear grupos con orden distinto entre procesos. Las operaciones colectivas tienen que invocarse de forma compatible en todos los ranks que participan. NCCL especifica que el count y el datatype deben coincidir entre participantes; un mismatch puede causar hangs, crashes o corrupción de datos. NCCL — Collective Operations.

4. La matemática de una Linear: column-wise y row-wise sharding

Partimos de una capa lineal:

Y = X W

X ∈ R[B,H]
W ∈ R[H,O]
Y ∈ R[B,O]

Con TP=P, hay dos particiones principales. Para simplificar, suponemos que O y H se pueden dividir de forma uniforme por P. Los modelos reales tienen restricciones adicionales por número de heads, head dimension, alignment y kernels.

Column-wise Parallel Linear

Dividimos W por columnas, es decir, por la dimensión de output:

W = concat(W₀, W₁, ..., Wₚ₋₁) along output dimension
Yᵢ = X Wᵢ

Y = concat(Y₀, Y₁, ..., Yₚ₋₁)

Cada rank recibe el input X y calcula una parte de las features de salida. Si el siguiente operador puede consumir el resultado sharded, evitamos reconstruir inmediatamente el tensor completo. Cuando se necesita el output replicado, hay que reunir los shards, por ejemplo con AllGather. La comunicación puede diferirse hasta el punto en el que el layout lo requiera.

Row-wise Parallel Linear

Dividimos W por filas, en la dimensión de input. X se divide de forma compatible:

X = concat(X₀, X₁, ..., Xₚ₋₁) along hidden dimension
W = concat(W₀, W₁, ..., Wₚ₋₁) along input dimension

Yᵢ = Xᵢ Wᵢ
Y = sum(Y₀, Y₁, ..., Yₚ₋₁)

Cada rank calcula una contribución parcial al output. Después hay que reducir y combinar las contribuciones. La forma típica es AllReduce cuando cada rank necesita el resultado completo; una combinación ReduceScatter/AllGather puede ser más adecuada cuando el siguiente operador mantiene una distribución sharded.

PyTorch expone primitives como ColwiseParallel y RowwiseParallel mediante DTensor. La API deja declarar layouts de entrada y salida, y gestiona las operaciones de comunicación necesarias para conectar módulos. PyTorch — Tensor Parallel.

5. Tensor Parallelism dentro de un Transformer

Una Transformer block dense contiene proyecciones de atención y una Feed Forward Network (FFN). Las dimensiones exactas cambian por arquitectura, pero el patrón de sharding más conocido es:

OperatorSharding típicoMotivoComunicación frecuente
Q, K, V projectionsColumn-wiseRepartir heads o grupos de heads entre ranks.Output sharded; puede mantenerse local hasta el siguiente operador.
Attention output projectionRow-wiseCombinar las contribuciones de heads locales.AllReduce o layout equivalente.
MLP gate / up projectionsColumn-wiseRepartir intermediate features.Activaciones sharded.
MLP down projectionRow-wiseSumar las contribuciones de dimensiones intermedias.AllReduce o ReduceScatter.

En una arquitectura con Gated MLP, gate y up projections pueden ejecutarse en paralelo sobre shards locales; después se aplica la activación y el producto elemento a elemento antes de la proyección down. PyTorch documenta este patrón para w1/w3 column-wise y w2 row-wise, de forma que el AllReduce puede colocarse después de la combinación, no necesariamente tras cada Linear individual.

La atención tiene restricciones adicionales. Si hay Hq query heads y TP=P, la partición habitual distribuye heads entre ranks. Hq debe ser compatible con el grado de paralelismo o el runtime debe aplicar una estrategia específica. Grouped Query Attention y Multi-Query Attention reducen el número de KV heads; si el número de KV heads no se divide limpiamente entre ranks, ciertas implementaciones replican grupos o restringen las combinaciones admitidas. No asumas que TP=8 funciona para cualquier checkpoint solo porque haya ocho GPUs.

Los pesos no son el único tensor. También se distribuyen activaciones, heads, logits, embeddings y KV states. La estrategia de sharding se tiene que diseñar en conjunto para evitar Gather/Scatter innecesarios entre módulos. PyTorch DTensor y Megatron Core documentan distintas convenciones de layout; no todos los runtimes tienen exactamente la misma ruta.

6. NCCL collectives: qué datos viajan realmente

NCCL es una biblioteca de comunicación colectiva optimizada para GPUs NVIDIA. Proporciona operaciones donde varios ranks intercambian o reducen buffers. No es un scheduler de inferencia, un orchestrator de nodos ni un sustituto del runtime que crea procesos y asigna modelos. Frameworks como PyTorch y motores como vLLM utilizan una capa de runtime y los collectives de bajo nivel para coordinar los dispositivos.

CollectiveQué haceResultado por rankUso típico
AllReduceReduce buffers de todos los ranks (SUM, MAX, etc.).Todos reciben el resultado completo.Sumar outputs parciales de una operación row-wise.
AllGatherConcatena shards procedentes de todos los ranks.Todos reciben el tensor concatenado.Reconstruir features o secuencias cuando un módulo requiere el tensor completo.
ReduceScatterReduce buffers y distribuye partes iguales del resultado.Cada rank conserva un shard del resultado reducido.Layouts sharded y Sequence Parallelism.
BroadcastUn rank root distribuye el mismo buffer.Todos reciben una copia.Inicialización o distribución de datos/control.
AlltoAllCada rank envía un chunk diferente a cada destino.Cada rank recibe un chunk de todos los orígenes.Expert Parallelism y dispatch de tokens a expertos.
Send / RecvComunicación punto a punto entre ranks.Solo el destino recibe el buffer.Transferencia de activaciones entre pipeline stages.

AllReduce se puede descomponer conceptualmente como ReduceScatter seguido de AllGather. No significa que toda implementación siempre ejecute dos llamadas separadas; NCCL puede elegir una implementación y un algoritmo distinto. También existe una diferencia práctica entre el tamaño del input, el tamaño del output y los bytes que cada rank transmite: no uses el tamaño del tensor global como sinónimo de bytes enviados por rank.

7. Ring All-Reduce: fórmula de volumen y latencia

El Ring AllReduce es una referencia útil para estimar comunicación. Para P ranks y un buffer de N elementos, el algoritmo clásico tiene dos fases:

  • ReduceScatter: P−1 pasos. Cada rank envía un chunk y acumula el chunk que recibe.
  • AllGather: P−1 pasos. Los chunks reducidos circulan hasta que cada rank tiene el resultado completo.

En cada fase, el rank transmite aproximadamente (P−1)/P del buffer. El volumen total enviado por rank es:

bytes_sent_per_rank ≈ 2 × (P − 1) / P × N × element_bytes

ring_time ≈ 2 × (P − 1) × α + bytes_sent_per_rank / BW

α representa una latencia por paso y BW el ancho de banda efectivo disponible para esa comunicación. Es un modelo simplificado, no un predictor exacto de NCCL. No incluye protocolo, headers, múltiples rails, congestión, topología, contención, overhead de kernel, sincronización ni solapamiento con cómputo.

El modelo sí permite ver el trade-off. A medida que P crece, el payload que envía cada rank se acerca a dos buffers, pero el número de pasos y la latencia fija también aumentan. Un TP mayor reduce la memoria ideal de pesos por rank, pero incrementa el coste de coordinación. Además, un AllReduce pequeño puede estar dominado por α y launch overhead; uno grande puede estar dominado por bandwidth.

No presupongas que NCCL siempre usa Ring. La documentación actual enumera algoritmos como Ring, Tree, CollNetChain, CollNetDirect, NVLS, NVLSTree y PAT, con disponibilidad dependiente de versión y plataforma. Si no se fuerza una selección, NCCL decide automáticamente en función del hardware, topología, función colectiva y tamaño del mensaje. NCCL — Environment Variables.

Forzar NCCL_ALGO no es el primer paso de optimización. Primero mide, identifica qué algoritmo y transporte se han seleccionado y crea un baseline. Una variable de entorno que mejora un microbenchmark puede empeorar otras formas de mensaje o el workload real.

8. Sequence Parallelism: cambiar el layout para mover menos activaciones

Sequence Parallelism distribuye la dimensión de secuencia de ciertas activaciones y operaciones element-wise cuando se usa junto con TP. En lugar de replicar completamente una activación entre ranks, se mantiene un shard de secuencia y se utilizan operaciones como ReduceScatter y AllGather para transitar entre layouts.

La distinción es importante: Sequence Parallelism no es Context Parallelism, aunque ambas estrategias dividan una dimensión de tokens. En Sequence Parallelism, el objetivo habitual es reducir memoria de activaciones y la redundancia de ciertas operaciones dentro de una malla TP. Context Parallelism reparte el contexto o la secuencia para escalar atención sobre long-context, con comunicación específica para obtener la información necesaria para el cálculo de atención.

En entrenamiento, Sequence Parallelism puede reducir la memoria de activaciones de LayerNorm y Dropout; en inferencia, las optimizaciones y layouts que se aplican dependen del motor y del modelo. No actives una bandera de sequence parallel sin confirmar que el runtime y el checkpoint admiten la combinación.

También es importante evitar una falsa suma de optimizaciones. Si una ruta introduce AllGather antes de una capa y otra vuelve a hacer AllGather para la siguiente, podemos terminar moviendo más datos de los que ahorramos. El layout debe seguirse desde la salida de una operación hasta la entrada de la siguiente.

9. Pipeline Parallelism: repartir la profundidad del modelo

PP divide las capas en etapas consecutivas. Si un modelo tiene 32 transformer blocks y PP=4, cada etapa puede alojar ocho bloques. Un rank procesa su segmento y envía las activaciones a la siguiente etapa. La última etapa produce el output o logits y el siguiente token vuelve al cliente o al scheduler.

Para una única secuencia, el flujo es secuencial: el token debe atravesar Stage 0, Stage 1, Stage 2 y Stage 3. La latencia de primer resultado incluye el trabajo de todas las etapas más las transferencias entre ellas. PP no convierte una única petición en cuatro peticiones paralelas.

La activación que cruza la frontera suele contener la salida de la etapa anterior. Durante Prefill puede tener forma aproximada [batch, sequence, hidden]; durante Decode, cuando cada secuencia activa produce un token, suele ser [active_sequences, hidden]. Por eso el volumen de P2P depende de tokens activos, hidden size, dtype y layout. No equivale al tamaño de los pesos.

El balance de las etapas es determinante. Una etapa con más capas, un módulo de embedding/LM head más pesado o un kernel menos eficiente se convierte en el bottleneck. Las demás etapas esperan a que esa etapa libere la siguiente microbatch. Las particiones uniformes por número de capas no siempre son uniformes por coste.

10. Pipeline bubble, microbatches y la diferencia entre latencia y throughput

Para una pipeline ideal con P stages equilibradas y M microbatches, la utilización de una programación forward fill/drain sencilla puede aproximarse por:

ideal_utilization ≈ M / (M + P − 1)
bubble_fraction ≈ (P − 1) / (M + P − 1)

La fórmula describe la penalización de llenar y vaciar una pipeline con M trabajos independientes. Aumentar M amortiza el fill/drain, pero no es gratuito: el microbatch puede volverse demasiado pequeño, el overhead de scheduling aumenta y el sistema necesita suficientes peticiones concurrentes.

En entrenamiento existen schedules como GPipe y 1F1B, que deben gestionar activaciones forward y gradientes backward. No hay que trasladar sin más su bubble formula a un servidor autoregresivo. En serving, las secuencias tienen longitudes distintas, los clientes llegan en instantes diferentes, Decode produce iteraciones pequeñas y el scheduler puede incorporar o retirar peticiones dinámicamente. La simulación de este capítulo es FIFO, no un motor de serving real.

La diferencia entre latencia y throughput vuelve a ser clave:

  • Single-request latency: una petición aislada debe recorrer la pipeline completa. Más stages no garantizan menos tiempo hasta el primer token.
  • Steady-state throughput: con suficientes secuencias independientes, varias etapas pueden trabajar simultáneamente sobre microbatches distintos.
  • Tail latency: una etapa lenta, una microbatch irregular o una red congestionada puede afectar a la cola completa.

En un sistema de streaming, los resultados deben analizarse con TTFT y TPOT por petición, no solo con un promedio de throughput agregado.

11. Combinar TP × PP × DP: una malla de ocho GPUs

Supongamos ocho GPUs distribuidas en dos nodos de cuatro GPUs. Hay distintas descomposiciones posibles:

LayoutTPPPInterpretación
TP8 × PP181Una etapa; el grupo TP incluye las ocho GPUs.
TP4 × PP242Dos stages; cada grupo TP permanece dentro de un nodo.
TP2 × PP424Más stages con grupos TP pequeños.
TP1 × PP818Sin collectives TP; muchas fronteras de pipeline.

Los cuatro layouts reparten ocho GPUs, pero no son equivalentes. TP8 introduce collectives que atraviesan el conjunto de ocho dispositivos. TP4×PP2 puede mantener los collectives frecuentes dentro del nodo y pasar activaciones entre nodos en las fronteras de pipeline. TP1×PP8 reduce comunicación intra-layer pero añade siete etapas y siete fronteras. La elección depende del modelo, la latencia de interconexión, el tamaño de activación, el balance por stage, el número de peticiones activas y los SLO.

Una recomendación habitual es mantener TP en el dominio de enlaces rápidos dentro del nodo y utilizar PP para escalar entre nodos. La guía de vLLM muestra como ejemplo dos nodos de ocho GPUs con TP=8 y PP=2. También documenta el edge case de GPUs sin NVLink, como el ejemplo L40S, donde puede ser preferible PP en vez de TP para reducir overhead de comunicación. Es una recomendación contextual, no una regla universal para cualquier generación de GPU ni cualquier modelo. vLLM — Multi-node parallelism.

DP añade otra dimensión. Por ejemplo, cuatro réplicas con TP4 pueden servir peticiones separadas en cuatro grupos de cuatro GPUs. Esto aumenta capacidad de servicio si hay demanda, pero cada réplica necesita su propio conjunto completo de shards. DP no convierte una réplica de 4 GPUs en un modelo que se reparte entre 16 GPUs; combina varias réplicas.

12. La topología física: HBM, NVLink, PCIe y network fabric

Antes de hablar de NCCL, dibuja la máquina física:

  • GPU HBM: la memoria local de cada acelerador. La operación más eficiente suele ser la que evita mover activaciones fuera de la GPU.
  • NVLink / NVSwitch: interconexión de alta velocidad entre GPUs en plataformas que la incorporan. La topología concreta determina qué pares tienen acceso directo y qué caminos comparten recursos.
  • PCIe: bus host-device y, cuando topología/driver lo permiten, comunicación GPU-to-GPU P2P. No todas las parejas tienen la misma ruta.
  • NIC + InfiniBand / RoCE: interconexión entre nodos. GPUDirect RDMA puede permitir que el tráfico vaya desde memoria GPU hacia el adaptador de red sin staging clásico por buffers de CPU, bajo los requisitos de hardware y software.
  • CPU / NUMA: afinidad del proceso, memoria host y NIC respecto al socket. Una mala colocación puede introducir tráfico cruzado por enlaces NUMA.

NCCL favorece P2P cuando CUDA permite acceso directo entre GPUs, habitualmente a través de NVLink o PCIe con una topología y driver compatibles. No basta con que el sistema tenga NVLink anunciado: hay que comprobar los enlaces entre los dispositivos concretos. NVIDIA documenta comandos como nvidia-smi topo -m y nvidia-smi topo -p2p n para inspeccionar la matriz. NCCL — GPU troubleshooting.

La topología también determina la colocación de ranks. Si el TP group necesita un AllReduce por cada bloque, colocar ranks del mismo TP group en GPUs conectadas por el mismo dominio de alta velocidad suele ser preferible a extenderlos accidentalmente por la red multi-node. En cambio, una frontera PP puede tolerar un mensaje P2P entre stages con menor frecuencia, aunque el volumen total y la latencia siguen importando.

13. NCCL, PyTorch Distributed y el runtime: quién hace qué

La ejecución distribuida involucra varias capas:

CapaResponsabilidadEjemplos
Model partitioningDecidir qué pesos, heads, layers o tokens pertenecen a cada rank.Megatron Core, PyTorch TP / DTensor, código del modelo.
Distributed runtimeCrear procesos, asignar ranks, inicializar grupos, arrancar workers y gestionar ciclo de vida.torchrun, multiprocessing, Ray, Slurm, Kubernetes.
Collective communicationEjecutar AllReduce, AllGather, ReduceScatter, AllToAll y P2P.NCCL en GPUs NVIDIA; otros backends según plataforma.
Inference engineScheduler, batching, KV Cache, ejecución de layers y serving API.vLLM, TensorRT-LLM y otros runtimes.
Fabric / hardwareTransportar bytes y ejecutar kernels.NVLink, PCIe, NIC, InfiniBand, RoCE, GPU.

NCCL no crea la malla lógica por sí solo. El framework inicializa los communicators y llama a las operaciones. Los collectives deben ejecutarse en orden compatible entre todos los ranks del grupo. Un rank que no llega, llega tarde o ejecuta otra operación puede bloquear el resto.

En PyTorch, torch.distributed expone ProcessGroup y abstracciones para collectives. El backend NCCL es habitual con GPUs NVIDIA; Gloo se utiliza con frecuencia para CPU y determinados casos. La elección de backend, versiones y transportes depende del entorno. La documentación de PyTorch también muestra cómo TP usa DTensor y layouts para automatizar comunicación.

14. Serving multi-GPU y multi-node con vLLM

Para una única réplica que se distribuye en varias GPUs, vLLM expone tensor_parallel_size y pipeline_parallel_size. La sintaxis actual del CLI incluye:

Una máquina con cuatro GPUs

vllm serve <model> \
  --tensor-parallel-size 4

Los cuatro ranks colaboran dentro del grupo TP. Antes de escoger esta configuración, comprueba que las dimensiones del modelo sean compatibles y que la topología tenga enlaces adecuados.

Dos nodos con ocho GPUs cada uno

vllm serve <model> \
  --tensor-parallel-size 8 \
  --pipeline-parallel-size 2 \
  --distributed-executor-backend ray

Esta distribución coloca típicamente ocho ranks TP por nodo y dos pipeline stages. Ray es un runtime opcional para multi-node; vLLM también documenta una ruta con multiprocessing. Los procesos necesitan poder acceder al mismo modelo o a una ubicación equivalente y los nodos deben tener conectividad privada y consistente.

Pipeline-only dentro de un nodo

vllm serve <model> \
  --tensor-parallel-size 1 \
  --pipeline-parallel-size 4

Puede tener sentido cuando se desea repartir capas sin introducir colectivos TP o cuando la topología no proporciona enlaces GPU-to-GPU adecuados. El balance de etapas y la microbatching deben validarse con el workload real.

La recomendación documentada por vLLM para multi-node es que TP sea el número de GPUs por nodo y PP el número de nodos; también contempla configurar TP sobre el total de GPUs del cluster. El runtime y la estrategia deben validarse con la versión instalada. vLLM — Parallelism and Scaling.

Seguridad del cluster

La documentación de vLLM advierte que el tráfico de control/comunicación del cluster Ray no está cifrado y que un actor con acceso a endpoints puede alcanzar capacidades peligrosas. Mantén el tráfico distribuido en una red privada y controlada. No expongas puertos internos de Ray o workers a redes no confiables; no confundas el endpoint HTTP público del modelo con la red interna de ejecución.

15. Memoria por rank: pesos, KV Cache y buffers

En primera aproximación, el payload de pesos puede dividirse por TP×PP:

ideal_weight_bytes_per_gpu ≈ total_weight_bytes / (TP × PP)

Es una estimación de primer orden, no un cálculo exacto del allocator. Algunos embeddings, norms, output heads, buffers, escalas o tensores pueden mantenerse replicados. El tamaño real también depende del checkpoint, quantization, alignment, workspace y del runtime.

KV Cache necesita una fórmula separada:

KV_bytes ≈
  2 × layers_local × active_sequences × context_tokens
    × local_kv_heads × head_dim × bytes_per_element

El factor 2 representa Key y Value. En PP, cada etapa almacena el KV correspondiente a las capas que ejecuta. En TP, los KV heads pueden distribuirse entre ranks, pero algunos modelos GQA/MQA pueden replicar heads o imponer restricciones. La fórmula exige conocer el layout real, no dividir ciegamente por TP×PP.

Además de pesos y KV, cada GPU necesita memoria para activaciones, workspaces, communication buffers, graph capture, memoria temporal y reservas del allocator. Una configuración puede caber al inicializar y fallar al aumentar max_model_len o max_num_seqs, porque el KV cache y los buffers de runtime ocupan el margen restante.

La log de startup de vLLM suele indicar el tamaño estimado de GPU KV Cache y una aproximación de concurrencia para una longitud de petición determinada. Esa cifra es más útil que el cálculo de pesos por sí solo para entender cuántas secuencias activas caben realmente.

16. Un performance model: compute, communication y synchronization

La latencia de una operación distribuida puede modelarse de forma simplificada como:

T_operation ≈ T_compute + T_communication + T_launch + T_sync

T_communication ≈ latency_cost + payload_bytes / effective_bandwidth

Pero los términos pueden solaparse. Si la implementación permite comunicación concurrente con cómputo, el coste no es necesariamente la suma completa:

T_step ≈ max(T_compute, T_communication) + T_unhidden_overhead

El grado de overlap depende del kernel, streams, dependencias de datos, schedule y capacidad del enlace. Una operación row-parallel que necesita su AllReduce para continuar crea una dependencia; no basta con declarar asynchronous para eliminarla.

En Prefill, el batch de tokens puede ser grande y los GEMMs suelen tener bastante trabajo por comunicación. En Decode, cada secuencia activa suele añadir un token por iteración; para batches pequeños el mensaje colectivo puede ser relativamente pequeño y el launch/latency fijo ganar peso. Cuando aumenta el número de secuencias activas, también aumenta el tamaño de las activaciones que participan en los collectives. Por eso el mismo grado TP puede comportarse distinto durante Prefill y Decode.

El modelo de techo debe separar:

  • Compute peak y utilización real de Tensor Cores.
  • HBM bandwidth local y acceso a pesos.
  • GPU-to-GPU bandwidth y latencia dentro del nodo.
  • Inter-node bandwidth, NIC affinity y congestión de fabric.
  • Scheduler, batch composition, sequence length, KV Cache y CPU overhead.

El objetivo no es maximizar ancho de banda teórico aislado. Es minimizar la parte no solapada de comunicación y mantener las GPUs ocupadas con una distribución equilibrada.

17. Cómo medir de verdad: NCCL Tests, nvbandwidth y serving benchmarks

No midas solo con ping entre nodos. Una inferencia TP depende de comunicación GPU-to-GPU y de collective operations. Un benchmark útil debe probar el tipo y tamaño de mensajes que el motor usa, además del workload de modelo.

Topology discovery

nvidia-smi topo -m
nvidia-smi topo -p2p n
nvidia-smi topo -p2p p

El primer comando enseña la topología de enlaces entre GPUs, CPU, NICs y otros componentes. Las pruebas P2P muestran si las parejas permiten acceso directo por NVLink o PCIe. Una matriz de rutas desigual puede explicar por qué el mismo TP degree cambia de rendimiento al recolocar GPUs.

Bandwidth and collectives

NVIDIA documenta nvbandwidth y nvloom para medir ancho de banda GPU-to-GPU en enlaces NVLink/PCIe y entre nodos en sistemas compatibles. El repositorio oficial NCCL Tests incluye programas como all_reduce_perf y pruebas para otras collectives. Un ejemplo de barrido de tamaños está documentado en el README del proyecto:

mpirun -np 8 -N 8 ./build/all_reduce_perf \
  -b 8M -e 1G -f 2 -g 1

El comando debe adaptarse a los GPUs por proceso, número de nodos y build de NCCL Tests. No lo ejecutes en producción sin reservar recursos; las pruebas pueden consumir gran parte de la interconexión.

Serving benchmark

Después mide vLLM o el engine final con prompts y outputs representativos, batch/concurrency definidos y warmup. Conserva:

  • TTFT, TPOT/inter-token latency y percentiles p50/p95/p99.
  • Input/output tokens por segundo y requests por segundo.
  • Concurrencia activa, queue time, prompt length, output length y distribución de long-context.
  • GPU memory, utilización, HBM, enlaces, KV usage, colas y errores.
  • TP/PP degree, rank mapping, versión de CUDA/driver/NCCL, backend, algoritmo elegido y transport.

Los microbenchmarks ayudan a localizar un problema de transporte. No sustituyen la medición end-to-end de la aplicación. NVIDIA NCCL Tests · NVIDIA nvbandwidth.

18. NCCL logs y observabilidad: detectar qué ruta se está usando

Para una investigación controlada, NCCL puede elevar el nivel de logging:

export NCCL_DEBUG=INFO
export NCCL_DEBUG_SUBSYS=INIT,GRAPH,ENV

Los logs pueden ayudar a identificar inicialización de communicators, topología detectada, variables de entorno, transportes y selección de rutas. En la documentación NVIDIA se muestra el uso de INIT, GRAPH y ENV para revisar afinidad/topología junto con nvidia-smi topo y lscpu.

Una práctica importante: no dejes variables de debugging o tuning en scripts de producción sin necesidad. La documentación NCCL distingue las variables de configuración de sistema de las variables de debugging; algunas deberían eliminarse después de resolver la incidencia, porque pueden degradar rendimiento o provocar otros problemas. NCCL — Environment Variables.

Para investigar una selección de algoritmo, registra versión y topology graph, tamaño del mensaje y tipo de collective. No atribuyas cualquier mejora a NVLink si en realidad cambió el algoritmo o el número de mensajes.

20. Runbook de diagnóstico para un servidor multi-GPU

  1. Freeze the topology: anota nodos, GPU models, driver, CUDA, NCCL, NICs, switch/fabric y cableado. No cambies simultáneamente software y topología.
  2. Map ranks to devices: registra global rank, local rank, GPU UUID, pipeline stage y TP group. Confirma que los ranks de un mismo TP group tienen la ruta física esperada.
  3. Check P2P: ejecuta nvidia-smi topo -m y las matrices P2P. Identifica qué pares cruzan PCIe, NVLink o no tienen acceso directo.
  4. Benchmark the fabric: ejecuta nccl-tests y nvbandwidth con tamaños representativos. Compara resultados por GPU pair, collective y mensaje.
  5. Enable temporary NCCL logs: INFO + INIT/GRAPH/ENV para capturar detección de dispositivos, transportes y selección de rutas.
  6. Validate process groups: mismo world size, ranks válidos, operación colectiva compatible, count/dtype y orden de llamadas.
  7. Run a tiny model: valida una réplica pequeña antes de cargar el checkpoint real. Comprueba forward, decode, stop, error y cierre de workers.
  8. Profile the real workload: Prefill y Decode por separado; TTFT/TPOT, batch, colas, KV, memory, collectives y P2P stage transfers.
  9. Change one dimension: compara TP, PP o placement una variable cada vez. Conserva baseline y rollback.
  10. Remove debug overrides: limpia variables temporales; conserva únicamente ajustes que estén justificados por mediciones reproducibles.

Si un colectivo se bloquea, empieza por el primer error del primer rank. El último proceso que reporta timeout suele ser una víctima, no necesariamente el origen. Una mala sincronización en una capa anterior puede dejar a los demás esperando indefinidamente.

El laboratorio incluido construye un modelo sintético con 32 capas, hidden size 4096 y FFN intermedio 11008. Calcula un payload ideal de pesos y modela la comunicación de un decode iteration con 16 secuencias activas. No descarga pesos ni ejecuta una GPU. Alcance del laboratorio

23. Límites y conclusiones

Distributed inference es una decisión conjunta de arquitectura y topología. TP divide matrices y exige comunicación colectiva frecuente. PP divide capas y mueve activaciones entre etapas. DP replica el modelo y distribuye solicitudes; CP reparte contexto; EP distribuye expertos. Un servidor real puede combinar varias de estas dimensiones.

Más GPUs no significan automáticamente más velocidad. Una partición TP mayor reduce pesos por rank, pero aumenta coordinación; PP reduce capas por etapa, pero crea fill/drain y fronteras; DP aumenta réplicas, pero cada réplica conserva su memoria de modelo; CP y EP cambian el patrón de comunicación. La topología determina qué parte de ese tráfico usa NVLink, PCIe o red inter-node.

La secuencia correcta de ingeniería es medir el cuello de botella, dibujar la topología, decidir layout, probar collectives, validar un modelo pequeño, perfilar Prefill/Decode y cambiar una sola variable por iteración. El laboratorio de este capítulo enseña la matemática y el flujo; no sustituye nccl-tests ni un benchmark real de serving.
