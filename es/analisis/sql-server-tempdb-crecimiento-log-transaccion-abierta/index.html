SQL Server tempdb: diagnosticar el crecimiento del log provocado por una transacción abierta

Un log de tempdb que crece no se resuelve reduciendo el fichero a ciegas. Primero hay que entender por qué SQL Server no puede reutilizar su espacio. Reproducimos el escenario, identificamos la transacción que mantiene activo el log y validamos la recuperación desde SQLCMD y SQL Server Management Studio.

Conclusión principal

La transacción abierta mantuvo registros activos e impidió reutilizar parte del log. SQL Server informó de ACTIVE_TRANSACTION; el fichero pasó de 8 MB a 216 MB y alcanzó el 99,16 % de ocupación. Después del rollback y de ejecutar CHECKPOINT, el uso cayó al 1,78 % y el motivo de espera volvió a NOTHING. El fichero físico siguió midiendo 216 MB: el espacio quedó disponible para reutilizarse, no fue devuelto al sistema operativo.

1. Qué estaba ocurriendo

El síntoma investigado es el crecimiento sostenido de templog.ldf, el fichero de log de tempdb. El tamaño o el porcentaje de ocupación no explican por sí solos la causa: hay que averiguar por qué el motor no puede reutilizar los registros inactivos.

En este laboratorio, una sesión abrió una transacción explícita, insertó filas en una tabla de prueba dentro de tempdb y permaneció en ella durante tres minutos. Mientras tanto, una segunda sesión consultó el uso del log y las DMVs de transacciones. El motivo de espera observado fue ACTIVE_TRANSACTION.

No es un incidente de producción. Es una reproducción controlada para estudiar el mecanismo. Una transacción larga es una causa posible de retención del log, no una explicación universal de cualquier crecimiento de tempdb. La investigación debe partir del valor real de log_reuse_wait_desc.

El crecimiento fijo de 8 MB se configuró deliberadamente para que los eventos fueran visibles en la prueba. No es una recomendación para producción ni debe confundirse con el valor predeterminado de otras instalaciones. Dimensiona tempdb a partir de la carga y de los picos observados.

La tabla dbo.CA_TempdbLogGrowthLab se crea únicamente dentro de tempdb. Los datos de tempdb no son persistentes entre reinicios del motor: la base se vuelve a crear al iniciar SQL Server y no admite backup/restore como una base de usuario.

3. Establecer baseline

Antes de generar carga, registra los ficheros, el consumo actual y el motivo de reutilización del log. Ejecuta la consulta con contexto en tempdb:

USE tempdb;
GO

SELECT name, type_desc, physical_name,
       CAST(size * 8.0 / 1024 AS decimal(12,2)) AS size_mb,
       CASE WHEN is_percent_growth = 1 THEN CONCAT(growth, '%')
            ELSE CONCAT(CAST(growth * 8.0 / 1024 AS decimal(12,2)), ' MB')
       END AS filegrowth
FROM sys.database_files
ORDER BY file_id;

SELECT total_log_size_in_bytes / 1048576.0 AS total_log_mb,
       used_log_space_in_bytes / 1048576.0 AS used_log_mb,
       used_log_space_in_percent
FROM sys.dm_db_log_space_usage;

SELECT name, state_desc, recovery_model_desc, log_reuse_wait_desc
FROM sys.databases
WHERE database_id = DB_ID(N'tempdb');

sys.dm_db_log_space_usage devuelve el tamaño total y el espacio ocupado del log. En SQL Server 2022, las DMVs utilizadas en este artículo requieren VIEW SERVER PERFORMANCE STATE o un rol de servidor que incluya ese permiso, como sysadmin. Comprueba los permisos en la versión y edición de destino.

4. Reproducir una transacción abierta

La carga inserta 12.000 filas con una columna char(7000): 84.000.000 bytes de payload, antes de contar el resto de estructuras y registros. La transacción permanece abierta durante tres minutos para que una segunda sesión pueda diagnosticarla.

USE tempdb;
SET NOCOUNT ON;

IF OBJECT_ID(N'dbo.CA_TempdbLogGrowthLab', N'U') IS NOT NULL
    DROP TABLE dbo.CA_TempdbLogGrowthLab;

CREATE TABLE dbo.CA_TempdbLogGrowthLab
(
    id int IDENTITY(1,1) NOT NULL PRIMARY KEY,
    payload char(7000) NOT NULL
);

BEGIN TRANSACTION CA_TempdbLogGrowthLab;

;WITH n AS
(
    SELECT TOP (12000)
           ROW_NUMBER() OVER (ORDER BY (SELECT NULL)) AS n
    FROM sys.all_objects AS a
    CROSS JOIN sys.all_objects AS b
)
INSERT INTO dbo.CA_TempdbLogGrowthLab (payload)
SELECT REPLICATE('X', 7000)
FROM n;

SELECT @@SPID AS repro_session_id,
       COUNT_BIG(*) AS rows_inserted,
       SUM(DATALENGTH(payload)) AS payload_bytes
FROM dbo.CA_TempdbLogGrowthLab;

-- Mantiene la transacción abierta para el diagnóstico desde otra sesión.
WAITFOR DELAY '00:03:00';

ROLLBACK TRANSACTION CA_TempdbLogGrowthLab;
DROP TABLE dbo.CA_TempdbLogGrowthLab;

Uso exclusivo en laboratorio desechable. Esta carga inserta datos y mantiene una transacción abierta durante tres minutos. No la ejecutes en producción ni en una instancia compartida. El paquete descargable contiene los scripts y estas advertencias.

5. Diagnosticar mientras la transacción sigue abierta

Primero mide el tamaño y la ocupación. Después correlaciona el motivo de espera con la transacción, la sesión, el login, el host y la aplicación:

USE tempdb;
SET NOCOUNT ON;

SELECT total_log_size_in_bytes / 1048576.0 AS total_log_mb,
       used_log_space_in_bytes / 1048576.0 AS used_log_mb,
       used_log_space_in_percent
FROM sys.dm_db_log_space_usage;

SELECT name, state_desc, log_reuse_wait_desc
FROM sys.databases
WHERE database_id = DB_ID(N'tempdb');

SELECT at.transaction_id, at.name AS transaction_name,
       at.transaction_begin_time,
       dt.database_transaction_log_bytes_used / 1048576.0 AS log_used_mb,
       st.session_id, s.login_name, s.host_name, s.program_name
FROM sys.dm_tran_database_transactions AS dt
JOIN sys.dm_tran_session_transactions AS st
  ON st.transaction_id = dt.transaction_id
JOIN sys.dm_tran_active_transactions AS at
  ON at.transaction_id = dt.transaction_id
JOIN sys.dm_exec_sessions AS s
  ON s.session_id = st.session_id
WHERE dt.database_id = DB_ID(N'tempdb')
ORDER BY at.transaction_begin_time;

La combinación de estas consultas responde cuánto log está ocupado, qué impide reutilizarlo, desde cuándo existe la transacción y qué sesión/aplicación debemos investigar. No mates un SPID hasta entender qué trabajo está ejecutando y quién es su propietario funcional.

6. Cuantificar los eventos de autogrowth

El tamaño final no muestra cuántas ampliaciones ocurrieron. En este laboratorio el default trace estaba disponible y se utilizó para contar los eventos históricos. Los identificadores 93 y 92 corresponden a Log File Auto Grow y Data File Auto Grow, respectivamente.

DECLARE @trace nvarchar(4000);
SELECT @trace = path
FROM sys.traces
WHERE is_default = 1;

SELECT EventClass,
       CASE EventClass WHEN 93 THEN 'Log File Auto Grow'
                       WHEN 92 THEN 'Data File Auto Grow' END AS event_name,
       COUNT_BIG(*) AS growth_events,
       SUM(IntegerData) * 8.0 / 1024 AS total_growth_mb,
       MIN(StartTime) AS first_event,
       MAX(StartTime) AS last_event
FROM sys.fn_trace_gettable(@trace, DEFAULT)
WHERE EventClass IN (92,93)
  AND DatabaseName = 'tempdb'
  AND StartTime >= '2026-11-13T20:00:00'
GROUP BY EventClass
ORDER BY EventClass;

El default trace puede no estar habilitado o no conservar ya los eventos de la ventana investigada; valida su disponibilidad antes de usar la consulta. Para instrumentación nueva y persistente, diseña una sesión de Extended Events con filtros y retención adecuados.

7. Resolver y validar: rollback y reutilización

La corrección no consiste en reducir el fichero. Consiste en resolver la transacción que mantiene activo el log, de acuerdo con el propietario de la carga y el impacto funcional. En esta reproducción la sesión que abrió la transacción ejecutó ROLLBACK; después se ejecutó CHECKPOINT en tempdb.

USE tempdb;
CHECKPOINT;

SELECT total_log_size_in_bytes / 1048576.0 AS total_log_mb,
       used_log_space_in_bytes / 1048576.0 AS used_log_mb,
       used_log_space_in_percent
FROM sys.dm_db_log_space_usage;

SELECT name, state_desc, recovery_model_desc, log_reuse_wait_desc
FROM sys.databases
WHERE database_id = DB_ID(N'tempdb');

SELECT COUNT_BIG(*) AS active_tempdb_user_transactions
FROM sys.dm_tran_database_transactions AS dt
JOIN sys.dm_tran_session_transactions AS st
  ON st.transaction_id = dt.transaction_id
WHERE dt.database_id = DB_ID(N'tempdb');

SELECT CASE WHEN OBJECT_ID(N'dbo.CA_TempdbLogGrowthLab', N'U') IS NULL
            THEN 'REMOVED - PASS'
            ELSE 'STILL EXISTS - CHECK' END AS lab_table_status;

Reutilizar espacio de log no equivale a reducir el fichero. El truncamiento lógico libera VLF inactivos para reutilización; un shrink intenta devolver capacidad al sistema de archivos. Son operaciones diferentes. No reduzcas el fichero como respuesta automática a este síntoma.

8. Runbook de producción

  1. Confirmar impacto y capacidad: revisa espacio libre del volumen, tamaño actual, crecimiento y tendencia de ocupación. Comprueba si hay riesgo inmediato de llenar el disco.
  2. Consultar el motivo de espera: lee sys.databases.log_reuse_wait_desc. No asumas que toda retención se debe a una transacción abierta.
  3. Si aparece ACTIVE_TRANSACTION: identifica la transacción con sys.dm_tran_database_transactions, relaciónala con la sesión mediante sys.dm_tran_session_transactions y revisa login, host, programa y hora de inicio.
  4. Entender antes de actuar: coordina con el propietario de la carga. Decide si debe terminar normalmente o revertirse según la lógica de la aplicación y la ventana de servicio. Un KILL puede iniciar un rollback largo y prolongar el consumo de recursos.
  5. Validar la recuperación: mide de nuevo el espacio usado, log_reuse_wait_desc, las transacciones activas y el espacio libre del volumen. Registra las evidencias y el momento de recuperación.
  6. Prevenir recurrencias: dimensiona tempdb para la carga normal y los picos, establece incrementos fijos razonables y monitoriza capacidad y autogrowth. El autogrowth es una salvaguarda, no un plan de capacidad.

ACTIVE_TRANSACTION no demuestra por sí solo que una tabla temporal de usuario sea la responsable. tempdb también contiene objetos internos, worktables, estructuras de sort/hash y row versioning. Correlaciona el motivo de espera y las DMVs antes de atribuir el consumo a una operación concreta.

9. Qué no hacer

  • No reduzcas templog como primera medida. Si la transacción sigue activa, el shrink no corrige la causa. Si el workload vuelve a necesitar espacio, el fichero crecerá otra vez y añadirá trabajo de autogrowth.
  • No mates una sesión sin identificarla. Un SPID no es una causa raíz. Revisa programa, host, login, antigüedad y propietario de la transacción.
  • No confundas tamaño con ocupación. Un fichero de 216 MB puede estar ocupado solo al 1,78 % y ofrecer espacio reutilizable.
  • No copies la configuración del laboratorio. El autogrowth de 8 MB se eligió para observar eventos; producción requiere dimensionamiento basado en la carga y la capacidad de almacenamiento.
  • No generalices el resultado a todos los motivos de espera. Consulta el motivo observado y sigue la ruta de diagnóstico específica. No todas las causas de log reuse se resuelven con rollback.
