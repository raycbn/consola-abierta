Diseñar una prueba de Disaster Recovery: cómo medir la recuperación de un servicio

Método para definir el alcance, medir RTO y RPO, validar dependencias, probar el servicio y cerrar una prueba de Disaster Recovery con evidencias.

La idea principal

Una prueba de Disaster Recovery no demuestra que el servicio se pueda recuperar porque una VM arranque o porque el job de replicación termine en verde. Debe demostrar, dentro de un alcance y unas reglas de seguridad aprobadas, que el servicio mínimo acordado vuelve a funcionar, que el punto de datos recuperado es utilizable y que la evidencia permite comparar el resultado con los objetivos de negocio.

1. Qué demuestra —y qué no— una prueba de DR

Un plan de recuperación describe una capacidad prevista. Una prueba aporta evidencia sobre esa capacidad en un escenario, una fecha y unas condiciones concretas. No son lo mismo. Un runbook puede estar actualizado y seguir fallando por una credencial caducada, un registro DNS que apunta al sitio equivocado, una dependencia que no estaba inventariada o una copia de datos que nunca se ha restaurado.

Conviene separar cuatro afirmaciones que a menudo se mezclan:

  • La copia existe: el backup o la réplica aparece como completada.
  • La infraestructura arranca: los recursos pueden iniciarse en el destino previsto.
  • La aplicación funciona: las dependencias responden y las funciones críticas pasan las comprobaciones técnicas.
  • El servicio se acepta: el responsable funcional confirma que el proceso de negocio mínimo puede continuar.

Una prueba puede validar una de estas capas sin validar las siguientes. El informe debe decir exactamente hasta dónde se llegó. No marques un servicio como recuperado si solo has comprobado que sus máquinas están encendidas.

La guía de contingencia de NIST describe la planificación de recuperación como un conjunto coordinado de planes, procedimientos y medidas técnicas. Su guía de pruebas, formación y ejercicios aborda el diseño, la ejecución y la evaluación de esos eventos. Son referencias fundacionales publicadas en 2010 y 2006; deben leerse como orientación técnica, no como sustituto de los requisitos actuales de la organización o de la regulación aplicable.

2. Define el servicio antes de elegir la prueba

El alcance no debería ser «recuperar el servidor APP01». Debería identificar el servicio que se quiere recuperar, qué capacidad mínima debe ofrecer y qué dependencias tienen que estar disponibles para que esa capacidad exista.

DimensiónPregunta que debe quedar respondidaEvidencia esperada
Servicio¿Qué proceso o funcionalidad vuelve a estar disponible?Catálogo de servicio y criterio de aceptación
Datos¿Qué punto de recuperación es aceptable y consistente?Marca temporal, origen y validación de integridad
Dependencias¿Qué identidad, DNS, red, almacenamiento, base de datos o proveedor hace falta?Mapa de dependencias y orden de arranque
Personas¿Quién activa, ejecuta, valida y acepta?Roles, suplentes y contactos de escalado
Entorno¿Dónde se prueba y qué conexiones están permitidas?Topología aislada y reglas de seguridad
Cierre¿Cómo se limpia el entorno y se vuelve a la situación inicial?Plan de cleanup, failback y reconciliación

Para una aplicación de tres capas, la secuencia puede exigir que la base de datos esté disponible antes del middleware y que el frontend arranque al final. Microsoft documenta precisamente este patrón en sus planes de recuperación de Azure Site Recovery. En un entorno real, el mapa también puede incluir Active Directory, DNS, certificados, secretos, firewalls, balanceadores, colas, almacenamiento, servicios externos y herramientas de monitorización.

La dependencia que no aparece en el inventario tampoco aparecerá mágicamente en el runbook. Antes de la prueba, revisa el mapa con los equipos propietarios de la aplicación y de la plataforma.

3. RTO y RPO: objetivos distintos, mediciones distintas

El Recovery Time Objective (RTO) expresa el tiempo máximo de interrupción que el negocio considera aceptable para un servicio. El Recovery Point Objective (RPO) expresa la pérdida máxima de datos, medida en tiempo, que el negocio está dispuesto a asumir. AWS explica esta diferencia en su pilar de fiabilidad: el RTO no es una media operativa como MTTR, sino un objetivo que se compara con un evento de recuperación concreto.

IndicadorQué mideMedición de referencia
RTO observadoTiempo desde el inicio acordado de la interrupción hasta la restauración del servicio mínimo acordadoservice_restored_at − disruption_started_at
RPO observadoAntigüedad del último punto de datos confirmado como recuperable en el momento de la interrupcióndisruption_started_at − last_recoverable_point_at
Tiempo hasta aceptaciónDemora adicional entre la disponibilidad técnica y la aceptación funcionalbusiness_accepted_at − service_restored_at

Los nombres de los hitos importan. Si en una prueba se empieza a contar cuando se declara el desastre y en otra desde que se detecta la primera interrupción, los resultados no son comparables. Del mismo modo, «servicio restaurado» debe tener una definición verificable: por ejemplo, dependencias disponibles, autenticación correcta, transacción sintética completada y funciones críticas accesibles.

El RPO tampoco debe calcularse a partir de la hora en la que el software dice que terminó un backup, sin más. El punto debe estar identificado y demostrado como recuperable y consistente. Una copia puede existir y aun así fallar al restaurarse, carecer de datos de aplicación o no ser utilizable por el servicio.

Establece objetivos por servicio y criticidad. Un RTO único para toda la plataforma suele ocultar que las aplicaciones tienen dependencias, tolerancias y prioridades diferentes.

4. Elige el nivel de ejercicio según el riesgo

No todas las pruebas necesitan un failover completo. Lo importante es que el tipo de ejercicio responda a una pregunta concreta y que el informe no exagere lo que ha validado.

TipoQué permite comprobarQué no demuestra por sí solo
Tabletop / walkthroughRoles, decisiones, contactos, escalado, comprensión del plan y lagunas del procedimientoQue los sistemas arranquen o que los datos se restauren
Prueba de componenteRestore de una base de datos, recuperación de un volumen, restauración de una VM o validación de una réplicaQue la aplicación completa funcione con todas sus dependencias
Test failover aisladoSecuencia técnica de recuperación y comportamiento del servicio en una red de prueba separadaQue un cambio de producción, DNS global o failback esté validado
Prueba extremo a extremoDependencias, autenticación, datos, transacciones funcionales, observabilidad y aceptación de negocioQue cualquier escenario alternativo o desastre distinto vaya a comportarse igual
Failover controladoLa transición real a la ubicación o plataforma alternativa, con su impacto y coordinaciónQue la vuelta al sitio primario o la reconciliación de datos estén resueltas automáticamente

Microsoft recomienda realizar un test failover antes de un failover completo y validar las aplicaciones y sus dependencias. Para evitar interferir con producción, la documentación de Active Directory y DNS de Azure Site Recovery describe el uso de una red aislada para el ejercicio y advierte de la necesidad de disponer primero de los servicios de identidad y resolución que requiere la aplicación.

La elección del ejercicio debe incluir un criterio de parada. Define qué condición obliga a abortar, quién puede detenerlo, qué recursos se crean y qué proceso los elimina. Si no existe una forma segura de aislar el tráfico o evitar escrituras cruzadas, la prueba no está lista para ejecutarse.

5. Diseña hitos que se puedan medir

Una única marca de «inicio» y otra de «fin» no bastan para explicar dónde se ha consumido el tiempo. Registra hitos con responsables y relojes sincronizados. El siguiente esquema es una estructura de trabajo, no una secuencia obligatoria para todos los servicios:

Figura 1 · Cadena de evidencia de una prueba de recuperación
01 / IMPACTOInterrupción, alcance y T0 acordado
02 / ACTIVACIÓNDecisión, autoridad y coordinación
03 / PLATAFORMADatos, red, identidad y dependencias
04 / SERVICIOAplicación, validación y aceptación
HitoQué registrarQuién lo confirma
Interrupción (T0)Hora de inicio conforme a la definición aprobada y alcance afectadoIncident manager / service owner
ActivaciónDecisión, plan activado, responsables y comunicacionesResponsable de continuidad
Punto de datosIdentificador y timestamp del punto elegido; comprobación de consistenciaData / database owner
DependenciasIdentidad, DNS, red, almacenamiento, base de datos y middleware listosResponsables de plataforma
Servicio disponiblePruebas de salud y funciones técnicas acordadas completadasApplication owner
Validación funcionalTransacciones sintéticas y flujos de negocio mínimos ejecutadosTest lead / business representative
Aceptación y cierreDecisión de aceptación, incidencias, cleanup y acciones de mejoraService owner / exercise controller

Guarda los tiempos en UTC o registra explícitamente el offset. No mezcles la hora del panel del proveedor, el servidor de base de datos y la herramienta de tickets sin normalizar las zonas horarias. Si hay varias regiones o equipos, un reloj desajustado puede parecer una recuperación imposible o un RPO negativo.

6. La evidencia debe permitir reconstruir la prueba

Una captura de pantalla aislada no sustituye a un registro de ejecución. El expediente debería permitir que otra persona entienda qué se probó, con qué versión de procedimiento, bajo qué condiciones, qué resultado se obtuvo y qué quedó fuera.

  • Identificación: servicio, escenario, fecha, alcance y versión de los planes o runbooks.
  • Objetivos: RTO/RPO aprobados, criterio de inicio y condición de servicio restaurado.
  • Entorno: topología de prueba, aislamiento, versiones, puntos de recuperación y cambios aplicados.
  • Marcas temporales: activación, restauración de dependencias, disponibilidad técnica, pruebas y aceptación.
  • Validación: pruebas de datos, autenticación, transacciones y comprobaciones funcionales acordadas.
  • Desviaciones: pasos manuales no documentados, errores, retrasos, dependencias inesperadas y riesgos residuales.
  • Cierre: limpieza, reconciliación, vuelta al estado de partida, responsables y acciones con fecha objetivo.

Referencia cada evidencia mediante un identificador de ticket, log, informe, captura o repositorio autorizado. No incluyas credenciales, datos de clientes ni documentación interna sensible en un paquete público. El laboratorio de este artículo usa referencias ficticias como EV-003; no contiene datos de ningún entorno real.

7. Ejemplo: cumplir RTO no compensa incumplir RPO

El paquete de práctica incluye un caso completamente sintético. Sirve para comprobar el cálculo y la lógica del informe, no para afirmar que se ha realizado una recuperación real.

Dato de ejemploValorResultado
RTO objetivo90 minutosObjetivo aprobado ficticio
RTO observado83 minutosPASS — dentro del objetivo
RPO objetivo15 minutosObjetivo aprobado ficticio
RPO observado18 minutosFAIL — supera el objetivo en 3 minutos
Demora hasta aceptación funcional8 minutos adicionalesSe informa aparte; no se oculta dentro del RTO configurado

El resultado global es FAIL. El servicio mínimo aparece disponible dentro del RTO, pero el punto recuperable está más atrás de lo permitido por el RPO. El equipo debe investigar el desfase de replicación o el punto de restauración, cuantificar el impacto de los datos y decidir si la estrategia cumple la necesidad de negocio. No es correcto promediar los dos objetivos ni etiquetar la prueba como satisfactoria por haber cumplido uno.

8. Cleanup, failback y seguridad del ejercicio

La prueba no termina cuando se muestra la página de login. Antes de ejecutar, documenta la vuelta al estado inicial y los criterios para confirmar que el entorno de prueba se ha eliminado o aislado correctamente.

  • Usa una red de prueba independiente y verifica rutas, peering, VPN y reglas antes de iniciar recursos recuperados.
  • Controla DNS, IPs, identidad, certificados y secretos para impedir que una instancia de prueba escriba en sistemas productivos.
  • Usa cuentas y datos de prueba aprobados; deshabilita integraciones externas que pudieran enviar correos, pagos o notificaciones reales.
  • Registra quién autoriza el inicio, el cambio de fase y la cancelación. Ten a mano el procedimiento de parada.
  • Ejecuta cleanup y valida que no quedan VMs, volúmenes, snapshots, interfaces, reglas temporales ni recursos facturables.
  • Si el ejercicio incluye failback, trata la vuelta como una fase independiente: sincronización, conflictos, fuente autoritativa, DNS y aceptación deben estar definidos.

Un test failover y un failback no son operaciones simétricas. La ubicación alternativa puede recibir escrituras nuevas durante una prueba; antes de volver al origen hay que saber qué datos son autoritativos y cómo se reconcilian. No presupongas que borrar las máquinas temporales equivale a completar la vuelta al estado original.

9. Cierra con un informe de mejora, no solo con un porcentaje

El cierre debe separar los objetivos cumplidos, los incumplidos, las partes no probadas y las limitaciones del ejercicio. Para cada hallazgo registra impacto, causa confirmada o pendiente, acción correctiva, responsable, fecha comprometida y evidencia necesaria para cerrar la acción.

El modelo de After-Action Report / Improvement Plan de CISA es una referencia útil para convertir observaciones del ejercicio en fortalezas, áreas de mejora y acciones asignadas. El valor está en verificar posteriormente que la corrección se ha implantado y que una nueva prueba demuestra su eficacia.

No inventes una periodicidad universal. AWS Well-Architected indica que no existe una frecuencia única válida para todas las estrategias DR salvo requisitos regulatorios explícitos. Define la cadencia en función de criticidad, cambios de arquitectura, crecimiento de datos, modificaciones de dependencias, fallos previos y resultados de las pruebas. Un cambio importante puede exigir una prueba extraordinaria aunque el calendario anual no haya llegado.

10. Laboratorio: Recovery Test Scorecard

El paquete de descarga contiene un analizador offline en Python estándar, datos sintéticos, README y siete pruebas unitarias. Introduce los timestamps acordados y las referencias de evidencias; el programa calcula RTO y RPO, comprueba el orden de hitos y genera un informe JSON y Markdown.

Alcance del laboratorioEl scorecard valida los datos introducidos. No ejecuta restauraciones, failover, replicación, consultas a monitorización ni pruebas funcionales. No demuestra por sí mismo que el punto de recuperación sea válido. Usa datos sintéticos o metadatos aprobados; no exportes información sensible.
python recovery_scorecard.py sample-test.json \\
  --json-out report.json \\
  --markdown-out report.md

Requisitos: Python 3.10 o posterior, sin paquetes de terceros. El código devuelve exit code 0 si se cumplen objetivos y evidencias, 1 si genera un informe con algún fallo y 2 si el input es inválido. El ejemplo incluido da FAIL deliberadamente porque el RPO observado supera el objetivo.
