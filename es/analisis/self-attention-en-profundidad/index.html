Self-Attention en profundidad: matemáticas, gradientes y variantes modernas

Query, Key y Value no son tres nombres decorativos. Son proyecciones aprendidas que construyen una operación diferenciable: calcular compatibilidades, normalizarlas y mezclar información. Vamos a derivarla, recorrer su backward pass y medir qué cambia cuando modificamos sus dimensiones o compartimos las cabezas Key/Value.

La pregunta central

¿Cómo convierte una secuencia de vectores en una nueva representación contextual, y cómo sabe el optimizador qué debe cambiar? El laboratorio implementa el forward pass, deriva manualmente los gradientes de Q/K/V, los contrasta con autograd, comprueba una derivada mediante diferencias finitas y estudia las variantes de atención que afectan a la memoria de inferencia.

1. El mecanismo que vamos a aislar

En el capítulo anterior construimos la anatomía de un decoder-only Transformer y recorrimos el flujo desde los token IDs hasta los logits. Aquí hacemos zoom en el componente que mezcla información entre posiciones: self-attention. No vamos a entrenar otro modelo de lenguaje; vamos a aislar la operación y probar sus propiedades con tensores controlados.

En self-attention, Query, Key y Value se calculan a partir de la misma secuencia de estados ocultos. Una Query se compara con las Keys disponibles; el resultado determina cuánto contribuye cada Value a la salida. Es una descripción funcional, no una traducción semántica literal: una Query no es necesariamente una pregunta lingüística, ni una Key una etiqueta interpretable. Son vectores aprendidos en un espacio de representación.

La operación original de Vaswani et al. (2017) se formula como scaled dot-product attention. Los Transformers actuales añaden decisiones arquitectónicas y de implementación —causalidad, RoPE, GQA, kernels eficientes— que conviene separar para no mezclar tres preguntas distintas: qué calcula la atención, cómo incorpora posición y cómo se ejecuta con menos memoria o movimiento de datos.

2. De X a Q, K y V: las proyecciones aprendidas

Partimos de una entrada que ya contiene representaciones vectoriales. Para un batch con longitud de secuencia T y dimensión de modelo d_model:

X: [B, T, d_model]

El bloque aplica tres proyecciones lineales independientes:

Q = X @ W_Q + b_Q
K = X @ W_K + b_K
V = X @ W_V + b_V

En Multi-Head Attention convencional, cada proyección produce H × d_head características por posición. Si elegimos d_model = 512, H = 8 y d_head = 64, el tensor proyectado puede reorganizarse así:

Q, K, V: [B, T, 512]
reshape: [B, T, 8, 64]
transpose: [B, 8, T, 64]

La última forma separa explícitamente la dimensión de heads. A partir de aquí cada head realiza su atención en paralelo. No significa que haya ocho modelos independientes: todas las heads reciben la misma entrada, sus matrices de proyección se entrenan conjuntamente y sus salidas vuelven a combinarse.

Qué hace cada proyección

  • Query (Q): vector usado para puntuar la compatibilidad entre una posición y las Keys disponibles.
  • Key (K): vector contra el que se compara cada Query para calcular los scores.
  • Value (V): contenido vectorial que se combina usando los pesos obtenidos.

La distinción importante es que Key decide, junto a Query, el peso de una posición; Value aporta el contenido agregado. Cambiar K puede cambiar a quién se atiende sin cambiar directamente el contenido almacenado en V. Cambiar V puede modificar la salida aunque los pesos de atención permanezcan idénticos.

3. Scores: por qué dividimos por la raíz de d_head

Para cada Query calculamos el producto escalar contra todas las Keys. Con Q de forma [B, H, T, d_head] y K de la misma forma:

S = Q @ K.transpose(-2, -1)
S.shape = [B, H, T, T]
S_scaled = S / sqrt(d_head)

El producto escalar mide alineamiento en el espacio aprendido. Sin embargo, su escala depende de la dimensión. Si los componentes de Q y K fueran variables independientes, de media cero y varianza uno, el producto escalar sería la suma de d_head productos: su varianza crecería aproximadamente en proporción a d_head. Al aumentar la dimensión, los logits que entran en softmax tenderían a tener magnitudes mayores.

El factor 1 / sqrt(d_head) normaliza esa escala bajo esa hipótesis de referencia. No garantiza que todos los scores entrenados tengan varianza uno ni elimina los problemas de condicionamiento, pero evita que la dimensión por sí sola empuje sistemáticamente los logits a valores extremos. El paper original explica precisamente la relación entre productos grandes y regiones de softmax con gradientes pequeños.

4. Softmax: de compatibilidades a pesos

Después del producto escalar aplicamos softmax sobre el eje de Keys. Para una posición i, la probabilidad de atención asignada a la posición j es:

P[i,j] = exp(S[i,j]) / sum_k exp(S[i,k])

Cada fila se normaliza por separado y suma uno. No se normaliza la matriz completa: cada Query tiene su propia distribución sobre las posiciones que puede consultar. Los valores son no negativos y comparables dentro de esa fila.

En código, la dimensión correcta importa: con scores de forma [B, H, T_query, T_key], la llamada habitual es softmax(scores, dim=-1). Aplicar softmax en el eje de Query produciría otra operación, no una variación inocua.

En entrenamiento, dropout puede aplicarse a los pesos de atención después del softmax. En inferencia normalmente se usa dropout_p = 0. PyTorch advierte que su API scaled_dot_product_attention aplica el dropout indicado incluso cuando se llama desde un módulo en modo eval: el caller debe pasar explícitamente cero en evaluación.

5. Causal masking y padding: restricciones antes de normalizar

Un decoder autoregresivo no puede consultar tokens futuros. Si la posición i está calculando su representación, únicamente puede usar las posiciones j ≤ i. La máscara causal asigna −infinito a los scores prohibidos antes del softmax:

scores[i, j] = -inf  cuando j > i
weights = softmax(scores, dim=-1)

Como exp(−infinito) = 0, las posiciones futuras reciben peso exactamente cero. Una máscara causal no oculta el pasado: conserva el prefijo completo, incluida la propia posición.

El padding mask resuelve otro problema: evita atender a posiciones de relleno introducidas para igualar longitudes dentro de un batch. En un decoder con padding pueden combinarse ambas restricciones, siempre que se construya correctamente la máscara broadcastable. No confundas los dos conceptos: causalidad expresa el orden de generación; padding expresa qué posiciones de entrada no contienen datos reales.

Ojo con PyTorch

En torch.nn.functional.scaled_dot_product_attention, una máscara booleana con True significa que la posición participa en la atención. En MultiheadAttention, la semántica de key_padding_mask usa True para indicar posiciones que deben enmascararse. Al migrar entre ambas APIs hay que invertir la máscara cuando corresponda. Consulta la documentación de la función que realmente estés usando.

6. Weighted sum y output projection

La matriz de pesos P se aplica a V:

O = P @ V
O.shape = [B, H, T, d_head]

Para cada Query, la salida es una combinación ponderada de los Values permitidos por la máscara. No se elige simplemente la posición con mayor peso; todas las posiciones con peso no nulo contribuyen a la suma. Esta mezcla es diferenciable respecto a P y respecto a V.

En Multi-Head Attention, las salidas de las H heads se concatenan y pasan por otra proyección aprendida:

O_concat = concat(O_1, ..., O_H)
Y = O_concat @ W_O

Si d_head = d_model / H, la concatenación vuelve a tener d_model características. W_O permite que la siguiente capa mezcle información de las distintas subrepresentaciones. La salida suele incorporarse al residual stream del Transformer block, pero esa conexión residual pertenece al bloque completo, no a la operación de atención aislada.

7. Backpropagation: recorrer el camino inverso

Hasta aquí hemos descrito el forward pass. Durante el entrenamiento, una loss aguas abajo produce un gradiente sobre la salida O. A partir de ese gradiente, reverse-mode automatic differentiation aplica la regla de la cadena hasta alcanzar P, S, Q, K y V, y después las matrices W_Q, W_K y W_V.

Vamos a derivar la atención sin máscara por brevedad algebraica; cuando existe máscara causal, las posiciones prohibidas tienen gradiente cero en los scores. Definimos:

S = (Q @ K.T) / sqrt(d_head)
P = softmax(S)
O = P @ V

Sea G = dL/dO el gradiente que llega desde la operación siguiente. Para la multiplicación O = P V, las derivadas matriciales son:

dL/dV = P.T @ G
dL/dP = G @ V.T

Esto separa dos caminos. El gradiente sobre V cambia el contenido que se mezcla. El gradiente sobre P cambia cuánto pesa cada posición, y debe retroceder a través de softmax y del producto QK.T. Por tanto, tanto Query como Key reciben gradiente por el camino de los scores.

8. El gradiente de softmax: por qué importa la distribución

Para una fila p = softmax(s), el Jacobiano de softmax es:

J = diag(p) - p @ p.T

Aplicarlo al vector de gradientes equivale a:

dL/ds_j = p_j * (dL/dp_j - sum_k(p_k * dL/dp_k))

La expresión muestra que las posiciones compiten dentro de la misma fila. El gradiente de un score depende del gradiente que recibe su peso y de la media ponderada por la distribución actual. Cuando softmax se concentra casi por completo en una posición, muchas probabilidades son cercanas a cero y las derivadas locales de esas posiciones pueden volverse pequeñas. Esta es una de las razones por las que la escala de los logits no es un detalle cosmético.

En el mecanismo real, los scores son además el resultado de QK.T / sqrt(d_head). Aplicando la regla de la cadena:

dL/dQ = (dL/dS @ K) / sqrt(d_head)
dL/dK = (dL/dS).T @ Q / sqrt(d_head)

La división por sqrt(d_head) aparece también en el backward pass porque forma parte del forward pass. No desaparece al derivar. Si modificas o eliminas esa escala, cambias tanto la distribución de atención como la magnitud del gradiente que regresa a Q y K.

9. Gradientes de las matrices de proyección

Q, K y V no son parámetros aislados: se obtienen proyectando X. Para una multiplicación lineal Q = X W_Q, el gradiente de W_Q se obtiene combinando las entradas X con el gradiente que llega a Q. Con tensores batched hay que sumar las contribuciones de batch y de posiciones; conceptualmente:

dL/dW_Q = X.T @ (dL/dQ)
dL/dW_K = X.T @ (dL/dK)
dL/dW_V = X.T @ (dL/dV)

Si hay bias, su gradiente suma las contribuciones correspondientes. La misma X alimenta las tres proyecciones, por lo que el gradiente total de X acumula las rutas que atraviesan Q, K y V. Esta es una razón práctica para no describir Query, Key y Value como tres canales independientes: comparten el mismo origen y se optimizan en el contexto de la misma loss.

En el laboratorio empleamos float64 para que los errores numéricos del chequeo de gradientes sean muy pequeños. Derivamos manualmente dQ, dK y dV para una loss cuadrática, los comparamos con torch.autograd.grad y contrastamos además un elemento de W_Q mediante diferencias finitas centrales:

gradient_fd ≈ (loss(W_Q + ε) - loss(W_Q - ε)) / (2 ε)

La diferencia finita no reemplaza autograd: es una comprobación independiente, sensible a la elección de ε y al redondeo. Sirve para detectar errores en la implementación de la derivada, no para entrenar el modelo.

10. Qué cambia al variar el número de heads

En la configuración habitual se mantiene fija la anchura total de atención: H × d_head = d_model. Si d_model = 512:

Con proyecciones fusionadas de d_model a d_model, el recuento de parámetros Q/K/V/O permanece constante al cambiar H si la anchura total se mantiene fija. Lo que cambia es cómo se particiona esa anchura: más heads implican subespacios más estrechos; menos heads implican subespacios más amplios. No existe una regla simple según la cual añadir heads mejore siempre el modelo. También influyen el entrenamiento, los datos, la arquitectura y el presupuesto computacional.

Este razonamiento deja de ser idéntico cuando reducimos el número de cabezas Key/Value: ahí ya no solo reorganizamos la misma anchura, sino que compartimos proyecciones K/V entre varios Query heads.

11. MHA, MQA y GQA: compartir Keys y Values

La atención Multi-Head tradicional asigna a cada Query head su propio Key head y Value head. Multi-Query Attention (MQA) conserva varios Query heads, pero comparte una única cabeza K y V. Grouped-Query Attention (GQA) introduce el punto intermedio: cada grupo de Query heads comparte una pareja K/V.

Si H_q es el número de Query heads y H_kv el número de Key/Value heads, cada grupo contiene H_q / H_kv Query heads. Habitualmente H_q debe ser divisible por H_kv para una distribución uniforme. Cuando H_kv = H_q obtenemos MHA; cuando H_kv = 1 obtenemos MQA; los valores intermedios representan GQA.

La motivación en inferencia autoregresiva es el tamaño de la KV cache. Cada token ya procesado aporta K y V que pueden reutilizarse al generar tokens posteriores. Si almacenamos menos cabezas K/V, reducimos el estado que debemos conservar y leer en cada paso. El paper de Ainslie et al. (2023) estudia GQA como compromiso entre la calidad de MHA y la eficiencia de MQA. No significa que compartir K/V sea gratuito: cambia la parametrización y el modelo debe aprender con esa estructura o adaptarse a ella.

12. El impacto en KV cache: un cálculo que sí escala

La memoria necesaria para almacenar Keys y Values por capa, por secuencia y por token puede estimarse como:

KV bytes = 2 × H_kv × d_head × bytes_per_element
Cache bytes = KV bytes × sequence_length × batch_size × layers

El primer factor 2 representa Key y Value. Para visualizar el efecto, usamos 32 Query heads, d_head = 128, BF16 (2 bytes) y una secuencia de 4.096 tokens. La tabla muestra una sola capa y una sola secuencia; para obtener el total de un modelo se multiplica por batch y número de capas:

DiseñoKV headsBytes por token y capaKV cache por capa
MHA3216 KiB64 MiB
GQA84 KiB16 MiB
GQA42 KiB8 MiB
MQA1512 B2 MiB

En este ejemplo GQA con cuatro KV heads reduce el tamaño teórico de caché al 12,5 % del MHA; MQA lo lleva al 3,125 %. Es una reducción proporcional al número de cabezas KV, manteniendo constantes d_head, longitud, batch y dtype. No es una medición del allocator, del layout paginado, de fragmentación ni de la memoria temporal del kernel.

Esta es la conexión con serving: durante decode, cada nuevo token necesita consultar las Keys y Values acumuladas. En generaciones largas o con mucha concurrencia, el tamaño y la lectura de la KV cache se convierten en una decisión de arquitectura de primer orden. Lo estudiaremos a nivel de Prefill/Decode en el capítulo de inference y a nivel de gestión de bloques con vLLM.

13. RoPE: posición relativa mediante rotaciones

Q, K y V por sí solos no indican el orden de los tokens. Un mecanismo de posición debe incorporar esa información. En el primer capítulo vimos embeddings posicionales aprendidos como opción didáctica; en muchos LLM modernos se emplea Rotary Position Embedding (RoPE).

RoPE divide las dimensiones de cada vector Q y K en pares y rota cada pareja un ángulo que depende de la posición. Las frecuencias varían entre pares. En notación compacta:

q_m = R_m q
k_n = R_n k
(R_m q) · (R_n k) = q · (R_(n-m) k)

La propiedad útil es que el producto entre el Query de la posición m y el Key de la posición n incorpora una dependencia de la diferencia relativa n − m. RoPE aplica rotaciones a Q y K, no a V. El paper RoFormer (Su et al., 2021) desarrolla esta construcción y sus propiedades.

La prueba del laboratorio verifica numéricamente esa identidad de rotación sobre vectores aleatorios en float64. No mide extrapolación a contextos más largos, ni compara perplexity, ni demuestra que cualquier configuración RoPE funcione bien fuera de su entrenamiento. En sistemas reales hay decisiones adicionales: base de frecuencias, escalado de posiciones y extensiones de contexto.

14. Implementación de referencia en PyTorch

La siguiente versión muestra el núcleo del forward pass para tensores con forma [B, H, T, d_head]. Está escrita para hacer visible la operación, no para competir en rendimiento con kernels fusionados:

import math
import torch

def self_attention(q, k, v, causal=True):
    scores = (q @ k.transpose(-2, -1)) / math.sqrt(q.size(-1))

    if causal:
        t_q, t_k = scores.shape[-2:]
        mask = torch.triu(
            torch.ones(t_q, t_k, dtype=torch.bool, device=q.device),
            diagonal=1
        )
        scores = scores.masked_fill(mask, float("-inf"))

    weights = torch.softmax(scores, dim=-1)
    output = weights @ v
    return output, weights

La API optimizada de PyTorch se expone mediante torch.nn.functional.scaled_dot_product_attention. En CUDA puede seleccionar implementaciones especializadas, como FlashAttention-2, Memory-Efficient Attention o el kernel matemático de PyTorch, según el backend y las restricciones de los tensores. En CPU se utiliza la implementación compatible de PyTorch; por eso esta práctica no presenta tiempos de GPU ni afirma estar midiendo FlashAttention.

GQA merece una advertencia adicional: la documentación de PyTorch 2.14 marca enable_gqa como experimental y documenta soporte en determinados kernels CUDA. En este laboratorio CPU hacemos explícita la expansión de cada cabeza K/V compartida a los Query heads de su grupo y contrastamos la salida con SDPA estándar. No etiquetamos esa operación como benchmark del kernel nativo GQA.

FlashAttention resuelve otra dimensión del problema: es un algoritmo exacto y IO-aware que usa tiling para reducir lecturas y escrituras entre HBM y memoria on-chip. No cambia la definición matemática de atención que estamos derivando; cambia cómo se calcula y qué datos intermedios se materializan. El detalle de kernels, memory bandwidth y benchmarking merece su propio análisis.

17. Qué no demuestran estos resultados

Las pruebas se han diseñado para aislar propiedades algebraicas, no para inferir calidad de un LLM. Los vectores Q/K aleatorios no reproducen necesariamente las distribuciones de un modelo entrenado. El experimento de softmax usa una semilla fija; los valores son un ejemplo reproducible, no una ley estadística para todas las redes.

Los cálculos de parámetros y KV cache son estimaciones analíticas con dimensiones declaradas. No se midió asignación real de memoria GPU, fragmentación, throughput, TTFT ni TPOT. El test GQA de CPU expande las KV compartidas; no ejecuta ni mide el kernel CUDA nativo. El test RoPE valida una identidad matemática, no la calidad de generación ni la extrapolación de contexto.

Por último, un mapa de atención no equivale automáticamente a una explicación fiel de una predicción. Jain y Wallace (2019) mostraron límites importantes para tratar los pesos como explicaciones; Wiegreffe y Pinter (2019) discutieron cómo depende la conclusión de qué se entienda por explicación y de cómo se evalúe. La posición prudente es usar los pesos como señales internas que pueden orientar un diagnóstico, nunca como prueba aislada de causalidad o interpretabilidad.

La distinción que conviene recordar

Atención explica cómo se mezcla información en una capa concreta. No describe por sí sola todo el procesamiento de un Transformer, los efectos de residual streams, MLPs, normalizaciones, capas posteriores ni el proceso de decisión completo.

El capítulo 03 dará el siguiente paso: cómo se entrena el modelo para que esas proyecciones y sus demás parámetros aprendan a predecir el siguiente token. Derivaremos Cross Entropy, backpropagation a través de toda la red, AdamW, learning-rate schedules y la diferencia entre reducir una loss y demostrar capacidad de generalización.

Antes de pasar al entrenamiento, el mapa conceptual debe quedar claro: Q y K producen compatibilidades; la escala condiciona los logits; softmax produce pesos; V aporta el contenido; la salida agrega y proyecta; autograd distribuye gradientes por cada ruta. MHA, GQA y MQA modifican cómo se comparten las proyecciones K/V, mientras RoPE incorpora posición mediante rotaciones.
