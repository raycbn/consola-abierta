Windows Server bajo presión: diagnóstico avanzado de CPU, memoria, almacenamiento y red

Un servidor lento no es un diagnóstico. La investigación empieza cuando se correlacionan el impacto en el servicio, la carga, la topología y las señales de cada subsistema. Esta guía desarrolla un método de captura y análisis para distinguir saturación real, contención, latencia y síntomas secundarios.

Principio operativo

No declares un cuello de botella a partir de un contador aislado. Una métrica describe una parte del comportamiento del sistema; la causa requiere correlación temporal, una hipótesis falsable y evidencia del impacto sobre la carga. La pregunta no es «¿qué recurso está alto?», sino «¿qué espera el servicio, durante cuánto tiempo, bajo qué carga y en qué capa se introduce esa espera?».

1. Diagnosticar el servicio, no el gráfico

El síntoma suele llegar en forma de «el servidor va lento», «la aplicación tarda más» o «hay picos de CPU». Ninguna de esas frases define todavía un problema de rendimiento. Antes de abrir PerfMon, concreta el comportamiento degradado y el intervalo en el que ocurre.

Como mínimo, fija estos elementos:

  • Impacto: latencia p50/p95/p99, throughput, errores, timeouts, duración de jobs o incumplimiento de una ventana operativa. Elige una métrica de servicio que represente el problema real.
  • Alcance: un host, un conjunto de nodos, una instancia de aplicación, una ruta de almacenamiento, una VLAN o una región. Compara con un nodo sano cuando exista un equivalente razonable.
  • Ventana temporal: cuándo comenzó, periodicidad, duración, coincidencia con backups, antivirus, snapshots, batch, despliegues, tareas programadas o cambios de configuración.
  • Topología: versión y build del sistema operativo, sockets, NUMA, vCPU, memoria asignada, tipo de almacenamiento, teaming, vSwitch, hipervisor y dependencias aguas arriba y abajo.
  • Baseline: comportamiento conocido bajo una carga comparable. Una métrica solo adquiere significado al compararla con su histórico, con un nodo equivalente o con una expectativa derivada del diseño.

Define primero una hipótesis y qué observación la invalidaría. Si sospechas saturación de CPU, por ejemplo, no basta con encontrar un proceso consumiendo ciclos: debes comprobar si el tiempo de CPU disponible condiciona la latencia de las peticiones y si la cola de ejecución aumenta durante el mismo intervalo. Si el servicio se degrada mientras la CPU permanece ociosa, la hipótesis necesita cambiar.

1.1 Separa saturación, contención y latencia

ConceptoQué significaQué buscar
SaturaciónLa capacidad utilizable de un recurso está ocupada durante el periodo relevante.Uso sostenido, cola creciente, throughput limitado y degradación correlacionada.
ContenciónVarias cargas compiten por un recurso o por una sección crítica.Esperas, colas, cambios de contexto, locks, throttling o vecinos ruidosos.
LatenciaEl tiempo de respuesta de una operación aumenta, aunque el uso agregado no sea elevado.Tiempo por operación, distribución de latencias, esperas y trazas de extremo a extremo.
Capacidad insuficienteEl diseño no dispone de margen para la demanda normal o prevista.Degradación repetible al crecer la carga, sin una anomalía puntual que explique el resultado.

Un host puede mostrar un 25 % de CPU global y, aun así, tener un hilo crítico limitado a un procesador lógico; puede tener memoria disponible baja sin presión efectiva de commit; o puede observar latencia de disco desde la máquina virtual cuando la causa está fuera del sistema operativo invitado. El nivel de agregación de la métrica importa tanto como su valor.

2. Captura: construir una línea temporal que sirva para investigar

Una captura puntual es una fotografía. Para incidentes intermitentes necesitas una secuencia temporal que incluya el estado previo, la degradación y la recuperación. PerfMon y los conjuntos de recopiladores de datos son adecuados para telemetría de contadores durante ventanas prolongadas. Microsoft documenta logman como interfaz para crear, consultar, iniciar y detener estos recopiladores.

2.1 Inventario de contadores en el idioma real del sistema

Los nombres de los contadores están localizados. Los ejemplos siguientes usan los nombres ingleses que aparecen en la documentación, pero no deben copiarse a ciegas en un Windows Server en otro idioma. Consulta los conjuntos disponibles y las rutas exactas del host:

# Ejecutar en una consola elevada si el conjunto está protegido por ACL
Get-Counter -ListSet * |
  Sort-Object CounterSetName |
  Select-Object CounterSetName, Paths

En PowerShell 7, Get-Counter está disponible en Windows. La propia documentación advierte de la localización de los nombres y recomienda enumerar los conjuntos. Verifica también que las instancias existen en esa máquina; no todos los roles, drivers o dispositivos exponen el mismo conjunto de contadores.

2.2 Recopilador de referencia con logman

El siguiente conjunto es una base de investigación, no una plantilla universal. Recoge señales de CPU, memoria, proceso, disco y NIC a intervalos de 15 segundos. Ajusta los contadores a la pregunta que estés intentando responder; añadir todas las instancias y todos los objetos sin criterio aumenta el volumen y complica la lectura.

New-Item -Path 'C:\PerfLogs' -ItemType Directory -Force | Out-Null

$counterPaths = @(
  '\Processor Information(*)\% Processor Time',
  '\Processor Information(*)\% Privileged Time',
  '\Processor Information(*)\% DPC Time',
  '\Processor Information(*)\% Interrupt Time',
  '\System\Processor Queue Length',
  '\System\Context Switches/sec',
  '\Memory\Available MBytes',
  '\Memory\Committed Bytes',
  '\Memory\% Committed Bytes In Use',
  '\Memory\Pages Input/sec',
  '\Process(*)\ID Process',
  '\Process(*)\% Processor Time',
  '\Process(*)\Private Bytes',
  '\Process(*)\Working Set - Private',
  '\LogicalDisk(*)\Avg. Disk sec/Read',
  '\LogicalDisk(*)\Avg. Disk sec/Write',
  '\PhysicalDisk(*)\Avg. Disk sec/Read',
  '\PhysicalDisk(*)\Avg. Disk sec/Write',
  '\PhysicalDisk(*)\Disk Reads/sec',
  '\PhysicalDisk(*)\Disk Writes/sec',
  '\Network Interface(*)\Bytes Total/sec',
  '\Network Interface(*)\Packets Received Errors',
  '\Network Interface(*)\Packets Outbound Errors'
)

logman create counter WS-Perf-Baseline -o 'C:\PerfLogs\WS-Perf-Baseline.blg' -f bincirc -v mmddhhmm -max 1024 -si 00:00:15 -c $counterPaths
logman start WS-Perf-Baseline

# ...reproducir u observar el incidente...

logman stop WS-Perf-Baseline

Comprueba previamente que no existe un recopilador con ese nombre y que el volumen de destino tiene espacio y retención aprobados. El formato circular limita el tamaño configurado, pero no sustituye a una política de custodia. Protege los BLG como evidencias operativas: pueden revelar nombres de procesos, actividad y topología interna. La creación y el control de recopiladores requieren privilegios adecuados.

Quince segundos es un punto de partida razonable para observar tendencias y ventanas largas. Para un spike de pocos segundos, baja el intervalo solo durante una captura acotada y valida el efecto de la instrumentación. No confundas el intervalo de muestreo con la resolución temporal real de todas las métricas. Además, PerfMon resume puntos cuando el volumen de muestras supera lo que el gráfico puede mostrar con fidelidad; revisa la cantidad de muestras y los datos originales antes de interpretar un pico o un mínimo.

2.3 Captura rápida con Get-Counter

Para una comprobación breve y acotada, Get-Counter puede muestrear un conjunto pequeño. El ejemplo muestra un minuto de observación con cinco segundos entre muestras:

Get-Counter -Counter '\Processor(_Total)\% Processor Time', '\Memory\Available MBytes', '\System\Processor Queue Length' -SampleInterval 5 -MaxSamples 12

Sirve para comprobar una hipótesis concreta, no para sustituir un recopilador persistente ni para capturar un problema que aparece fuera de esa ventana. Para tendencias, exporta o registra los datos de forma reproducible y conserva timestamps coherentes con los logs de aplicación, hipervisor y almacenamiento.

3. CPU: utilización agregada, hilos calientes y coste del kernel

Empieza por Processor Information(*)\% Processor Time —o el contador equivalente disponible— y conserva la visibilidad por procesador lógico, además del total. Un agregado puede esconder una distribución muy desigual: un hilo serial puede saturar un logical processor mientras el resto permanece desocupado. En ese caso, la utilización global aparenta tener margen, pero la ruta crítica de la aplicación no puede avanzar más rápido.

3.1 Interpreta proceso y sistema con la misma escala

El contador Process(*)\% Processor Time puede superar el 100 % porque expresa el consumo del proceso en relación con un procesador lógico. En una máquina con 16 procesadores lógicos, un proceso que ocupa cuatro de ellos de forma completa puede aproximarse al 400 %. Para compararlo con el porcentaje total del host, normaliza el valor por el número de procesadores lógicos y comprueba cómo maneja la herramienta los grupos de procesadores.

Incluye Process(*)\ID Process en la captura. Las instancias de proceso pueden tener sufijos como #1 cuando hay varios procesos con el mismo nombre; el sufijo no es una identidad estable. Correlaciona nombre, PID y tiempo de vida, y descarta instancias que hayan terminado o se hayan recreado durante la ventana analizada.

3.2 La cola de CPU no es un umbral mágico

System\Processor Queue Length ayuda a observar trabajo ejecutable que espera CPU, pero no representa todas las esperas de la aplicación. Interprétalo junto al número de procesadores lógicos, la utilización por CPU, la duración de la cola y la latencia del servicio. Una cola puntual puede ser normal; una cola sostenida que coincide con CPU ocupada y degradación de latencia aporta una señal mucho más fuerte.

Si el tiempo de kernel, DPC o interrupciones aumenta, investiga drivers, filtros de almacenamiento y seguridad, NIC, virtualización y dispositivos. El proceso System puede concentrar actividad del kernel que no se atribuye limpiamente a un proceso de usuario. No concluyas «driver defectuoso» solo porque System aparezca arriba: confirma con una traza y revisa qué módulo, pila o tipo de evento consume ciclos.

En una VM, la CPU vista desde el invitado no describe por sí sola la capacidad de ejecución concedida por el hipervisor. Correlaciona la serie temporal con ready/co-stop o las métricas equivalentes de la plataforma, límites de CPU, reservas, sobreasignación y contención del host. Un invitado con poca utilización visible puede seguir sufriendo latencia de planificación externa.

4. Memoria: RAM disponible, commit y presión real

En Windows conviene separar memoria física, memoria comprometida y memoria del kernel. Memory\Available MBytes es una señal de margen físico; Memory\Committed Bytes y Memory\% Committed Bytes In Use describen el compromiso de memoria frente al límite de commit. No son métricas intercambiables. Un valor alto de commit no significa automáticamente que toda esa memoria esté residente en RAM; un valor bajo de memoria disponible tampoco demuestra por sí solo que la aplicación esté paginando de forma perjudicial.

4.1 Correlaciona presión con los procesos

  • Private Bytes: memoria privada comprometida atribuible al proceso. Útil para observar crecimiento, pero no equivale a RAM residente.
  • Working Set - Private: parte privada del conjunto de trabajo residente. Puede cambiar por trimming, presión de memoria o comportamiento normal del gestor de memoria.
  • Available MBytes: margen físico disponible para el sistema y las cargas.
  • Committed Bytes / Commit Limit: compromiso global frente al límite del sistema, que depende de RAM y pagefile.
  • Pool Paged / Pool Nonpaged: asignaciones del kernel. Un crecimiento anómalo sostenido puede orientar hacia un driver, pero PerfMon no identifica por sí solo el pool tag responsable.

El contador Memory\Pages Input/sec es más útil que tratar Pages/sec como un sinónimo de «el pagefile está saturado». Las páginas que entran pueden proceder de archivos mapeados y otros respaldos, no únicamente del archivo de paginación. Los page faults pueden resolverse en memoria sin lectura de disco. Correlaciona entradas de páginas, lecturas, latencia de almacenamiento y el comportamiento del proceso antes de declarar paging excesivo.

4.2 Investiga tendencias, no una fotografía

Busca crecimiento de Private Bytes sin liberación, caída persistente de Available MBytes, aumento de commit, working sets recortados y actividad sostenida de hard faults. Si el sospechoso es memoria del kernel, identifica primero qué pool crece; después escala a herramientas adecuadas para atribuir asignaciones por tag y driver. La memoria no paginada no puede expulsarse al pagefile como la paginada.

En entornos virtualizados, incluye la política de memoria dinámica, ballooning o reclamación del hipervisor cuando aplique. La memoria «asignada» en la configuración de la VM no demuestra que el invitado disponga siempre del mismo margen efectivo bajo contención del host.

5. Almacenamiento: separar volumen, dispositivo y ruta de I/O

Cuando una aplicación se bloquea esperando I/O, el porcentaje de CPU puede caer. Empieza separando el volumen lógico que usa la carga del dispositivo físico o virtual que lo respalda. Observa por lectura y escritura:

  • Avg. Disk sec/Read y Avg. Disk sec/Write: latencia media de finalización por operación durante el intervalo.
  • Disk Reads/sec y Disk Writes/sec: tasa de operaciones, no tamaño ni latencia individual.
  • Disk Bytes/sec: throughput; interprétalo junto al tamaño de I/O y la carga.
  • Avg. Disk Queue Length / Current Disk Queue Length: trabajo pendiente; el significado depende del dispositivo, paralelismo y capa medida.
  • Process(*)\IO Read Operations/sec y IO Write Operations/sec: atribución de actividad de I/O por proceso; no son una medición directa de la latencia que experimenta ese proceso.

No conviertas valores orientativos en SLA universal. La guía de Microsoft presenta referencias de latencia para escenarios generales, pero el criterio real depende del tipo de almacenamiento, la profundidad de cola, el perfil de I/O, el nivel de servicio contratado y el baseline de esa carga. Un pico breve no tiene el mismo significado que una latencia sostenida durante toda la ventana crítica.

Si la latencia aumenta, pregunta qué cambió: IOPS, throughput, tamaño de bloque, patrón aleatorio/secuencial, lectura/escritura, flush, snapshots, backup, antivirus, deduplicación, multipath o contención en el array. En una VM, los contadores del invitado no revelan siempre la cola del datastore, la latencia del vSAN/SAN ni la espera en el host. Correlaciona con las métricas de hipervisor, cabina y ruta multipath, respetando las fronteras de responsabilidad.

DiskSpd es un generador de carga de almacenamiento mantenido por los equipos de ingeniería de Microsoft. Úsalo para caracterizar un diseño o reproducir un patrón en un entorno controlado, no como primera respuesta en un volumen de producción activo: una prueba mal dimensionada puede competir con la carga real y alterar la evidencia que intentas obtener.

6. Red: throughput no equivale a salud de la conexión

Network Interface(*)\Bytes Total/sec permite estimar cuánto tráfico procesa una NIC. Compara ese valor con la capacidad efectiva, no solo con la velocidad nominal anunciada, y diferencia tráfico enviado y recibido. Sin embargo, una interfaz lejos de saturarse puede experimentar drops, retransmisiones, MTU incorrecta, colas, problemas de offload o pérdida en un componente virtual o físico.

Recoge estadísticas de la interfaz antes y después de reproducir el síntoma:

Get-NetAdapterStatistics |
  Format-Table Name, ReceivedBytes, SentBytes,
    ReceivedPacketErrors, OutboundPacketErrors,
    ReceivedDiscardedPackets, OutboundDiscardedPackets -AutoSize

Son contadores acumulativos. La diferencia entre dos lecturas, tomada en una ventana conocida, es más informativa que una lectura aislada. Comprueba si el driver, firmware, teaming, vSwitch, VLAN y la contraparte muestran el mismo patrón. Si la aplicación reporta timeouts, incluye retransmisiones TCP, resets, DNS, latencia de establecimiento y medición desde el otro extremo; no asumas que todo timeout es un problema del servidor local.

6.1 Pktmon para localizar drops dentro de la pila

Pktmon, incluido en Windows Server 2019, 2022 y 2025, permite capturar tráfico y observar pérdidas en varios puntos de la pila de red. Su valor diferencial en entornos virtualizados es que puede mostrar en qué componente se observa o descarta un paquete. Empieza con filtros específicos, reproduce el flujo y limita la ventana de captura:

# Consultar sintaxis de filtros y estado
pktmon filter add help
pktmon list

# Ejemplo: filtrar un puerto concreto (ajusta al flujo investigado)
pktmon filter add -p 443
pktmon start -c

# Reproducir el problema y consultar contadores
pktmon counters

# Detener la captura y convertir el ETL a texto
pktmon stop
pktmon etl2txt PktMon.etl

La sintaxis disponible varía con la versión; consulta pktmon help y la documentación del build antes de ejecutar. No captures todo el tráfico sin necesidad: filtra por IP, puerto, protocolo o componente. Las capturas pueden contener metadatos sensibles y deben manejarse como evidencia restringida. La conversión a PCAPNG facilita el análisis en Wireshark, pero puede perder información específica de los puntos de captura y razones de descarte; conserva el ETL original.

7. Cuándo PerfMon no basta: ETW, WPR y WPA

PerfMon describe tendencias a través de contadores agregados. No ofrece por sí solo una explicación a nivel de kernel, pila de llamadas, thread scheduling o secuencia exacta de eventos. Cuando la pregunta exige saber qué hilo ejecutaba qué código, qué módulo generó el coste o por qué una operación esperó, escala a Event Tracing for Windows (ETW).

Windows Performance Recorder (WPR) recoge trazas ETW mediante perfiles; Windows Performance Analyzer (WPA) abre el ETL y permite analizar eventos, CPU, actividad de disco y otros subsistemas. WPR/WPA forman parte de Windows Performance Toolkit, distribuido con Windows ADK. No es una captura que deba mantenerse abierta indefinidamente: elige un perfil que responda a la hipótesis, define duración y modo de almacenamiento, y limita el volumen.

# Revisar perfiles disponibles en el equipo
wpr -profiles

# Ejemplo de captura CPU en modo memoria
wpr -start CPU

# Reproducir el síntoma durante una ventana acotada
wpr -status

# Guardar el ETL y describir el escenario
wpr -stop C:\PerfLogs\cpu-investigation.etl "CPU contention during request latency"

Comprueba previamente el perfil disponible y el uso de memoria/disco; el comando anterior es ilustrativo. El modo de archivo sin límite puede crecer hasta llenar el volumen. En producción, coordina la captura, define un tamaño y duración máximos, valida el impacto y establece quién custodiará el ETL. WPA requiere una instalación compatible de Windows Performance Toolkit.

Usa PerfMon para responder «cuándo y qué recurso cambió»; WPR/WPA para responder «qué evento, hilo, módulo o pila produjo el coste». No empieces con una traza verbose si todavía no has definido una hipótesis: genera ficheros grandes y dificulta el análisis.

9. Resultados de laboratorio: baseline, CPU, memoria y almacenamiento

Esta sección incorpora mediciones realizadas en un laboratorio aislado el 12 de noviembre de 2026. No son cifras de referencia universales: describen una VM Windows Server 2025 Standard Evaluation (build 26100) con 2 vCPU, 4 GiB de RAM y un disco de datos NVMe virtual de 40 GiB (D:) sobre VMware Workstation 26.0.1. La red se mantuvo en VMnet1 Host-only. DiskSpd 2.3 se ejecutó contra un fichero de prueba de 4 GiB, nunca contra un dispositivo en bruto.

9.1 Línea base en reposo

La captura PerfMon duró 10 min 43,95 s, con intervalo de 5 segundos y 130 muestras válidas. CPU total media: 3,79 % (P95: 4,98 %); memoria disponible media: 2.797 MB; memoria comprometida media: 18,68 %. El disco D: mantuvo la cola en cero, con latencia media de escritura de 0,4 ms (P95: 1,7 ms). Esta es la referencia de reposo de esta VM, no un umbral para otros servidores.

Interpretación de la lectura secuencial

Los 8,3 GiB/s observados en lectura son una medida del conjunto VM/Workstation/VMDK. No demuestran que el NVMe físico alcance esa velocidad: las capas de virtualización y caché del host pueden afectar al resultado. No extrapoles esa cifra a bare metal ni la uses como especificación del dispositivo físico.

9.5 Primera serie de transferencia TCP entre invitados

La primera serie del 13 de noviembre utilizó dos invitados VMware conectados exclusivamente a VMnet1 Host-only (subred 192.168.35.0/24): Ubuntu 24.04.1 como emisor (192.168.35.129, 1 vCPU, 1 GiB) y Windows Server 2025 como receptor (192.168.35.128, 2 vCPU, 4 GiB). El host PCRAY no generó tráfico; no se utilizó NAT ni Bridged. 9.7 Alcance y limitaciones de la evidencia

  • La suite principal de CPU, memoria y almacenamiento completó 15 ejecuciones, sin fallos, y cuenta con una captura PerfMon independiente de 366 muestras a intervalos de cinco segundos.
  • Las mediciones de CPU/memoria/almacenamiento corresponden a una VM Windows Server 2025 concreta (2 vCPU y 4 GiB); la prueba de red utiliza además una VM Ubuntu 24.04.1 con 1 vCPU y 1 GiB.
  • La repetición TCP instrumentada entregó exactamente 768 MiB. La serie PerfMon de red contiene 90 muestras de cinco segundos; no debe interpretarse como resolución por transferencia.
  • Las dos series TCP son ejecuciones distintas y se presentan por separado. Los tiempos del emisor Ubuntu y del receptor Windows utilizan límites de cronometraje diferentes.
  • La red fue VMnet1 Host-only. No se habilitó NAT ni Bridged y el host no actuó como emisor. No se midió una NIC física, bare metal ni SLA de producción.
  • Los resultados dependen del build, idioma, drivers, hipervisor, caché y configuración del laboratorio; no son valores de referencia universales.

Se conservaron BLG/CSV, logs DiskSpd, ETL, correlación xperf, resultados de las tres transferencias y capturas PerfMon. ETW confirma la cola de latencia de escritura, pero no determina si se origina en el driver, la capa de virtualización, caché del host, VMDK o dispositivo físico. La causa raíz de la anomalía de I/O permanece sin confirmar.

10. Runbook operativo de investigación

  1. Registrar impacto: servicio afectado, métricas de latencia/errores, alcance, hora de inicio y condiciones de carga.
  2. Congelar contexto: cambios recientes, tareas concurrentes, eventos de sistema/aplicación, topología, versión/build, configuración de VM y almacenamiento.
  3. Capturar baseline: recopilar contadores mínimos durante una ventana suficiente; incluir antes, durante y después del síntoma.
  4. Correlacionar: alinear timestamps de PerfMon, logs de aplicación, eventos, hipervisor, storage y red; normalizar por capacidad y carga.
  5. Formular hipótesis: indicar evidencia esperada, evidencia que la refutaría y siguiente medición de menor coste.
  6. Escalar con criterio: usar WPR/WPA, Pktmon o herramientas del hipervisor/array solo cuando la pregunta no pueda resolverse con contadores.
  7. Validar la corrección: comparar la misma métrica de servicio y del subsistema antes/después bajo una carga comparable.
  8. Conservar evidencia: guardar BLG/ETL, comandos, intervalo, zona horaria, build, cambios y conclusión, con acceso y retención controlados.
Qué debe contener una conclusión técnica

Una conclusión útil incluye el síntoma medido, la ventana temporal, la evidencia correlacionada, la capa responsable, el mecanismo causal, los descartes relevantes, la mitigación aplicada y el resultado cuantificado. «CPU alta» o «disco lento» son observaciones, no causas raíz.

10.1 Criterios de salida

La investigación no debería cerrarse solo porque el servidor vuelve a responder. Cierra cuando la métrica de servicio recupera el nivel acordado, las métricas del subsistema vuelven a un rango coherente con el baseline, la causa está razonablemente demostrada y no se ha trasladado el cuello de botella a otra capa. Si el problema desapareció sin evidencia suficiente, registra la causa como no confirmada y deja definido qué captura permitirá resolver la recurrencia.
