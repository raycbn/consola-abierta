LLM Inference: Prefill, Decode y KV Cache

El entrenamiento ha terminado. Ahora llega una petición y el modelo tiene que responder. Para entender el coste real de esa operación hay que separar dos fases: procesar el prompt y generar la continuación. En el centro está una estructura de memoria que evita repetir parte del trabajo: la Key/Value Cache.

La pregunta central

Cuando enviamos un prompt, ¿por qué el modelo procesa todos sus tokens juntos, pero después genera uno por uno? ¿Qué cálculos se pueden reutilizar, cuáles no, y cómo se traduce ese estado reutilizado en memoria GPU? Vamos a seguir los tensores y a contrastar el mecanismo con una implementación pequeña.

1. Del entrenamiento a la inferencia

En el capítulo anterior estudiamos cómo un decoder-only Transformer ajusta sus parámetros para aumentar la probabilidad del siguiente token. Durante el entrenamiento se procesan secuencias con teacher forcing: cada posición dispone del prefijo correcto del corpus y la máscara causal impide consultar posiciones futuras. El cálculo de loss y backpropagation actualiza los pesos.

En inferencia, los pesos ya están fijados. Recibimos una secuencia de entrada —el prompt— y queremos producir una continuación. No ejecutamos backward ni actualizamos parámetros. Ejecutamos forward, obtenemos logits para el siguiente token, seleccionamos un token y repetimos el proceso hasta alcanzar un criterio de parada.

La distinción parece sencilla, pero cambia el patrón de cómputo. El prompt puede contener cientos o miles de tokens conocidos antes de empezar a generar. Es posible procesar esas posiciones en paralelo respetando la causalidad. En cambio, el token siguiente depende del token que acabamos de seleccionar: la generación es secuencial a lo largo del tiempo.

El serving de LLMs suele separar esta operación en dos fases conceptuales:

  • Prefill: procesa el prompt completo y prepara el estado de atención que se necesitará después.
  • Decode: incorpora los tokens generados, normalmente uno por iteración, reutilizando el estado anterior.

2. El ciclo autoregresivo, paso a paso

Supongamos que el prompt contiene P tokens. El modelo calcula una distribución para la posición siguiente y seleccionamos el primer token generado. Ese token se añade al contexto. El siguiente forward utiliza el estado anterior y el nuevo token para producir la distribución del segundo token generado.

prompt = [x1, x2, ..., xP]

logits_1 = prefill(prompt)
token_1 = sample_or_select(logits_1)

logits_2 = decode(token_1, cache)
token_2 = sample_or_select(logits_2)

logits_3 = decode(token_2, cache)
token_3 = sample_or_select(logits_3)

Hay un detalle temporal que suele confundir: Prefill ya entrega los logits para seleccionar el primer token de salida. No es necesario volver a pasar ese token por el modelo para obtenerse a sí mismo. La primera llamada de Decode consume el token que acabamos de seleccionar para calcular los logits del token siguiente.

La selección puede ser greedy, sampling con temperatura y top-p/top-k, o un algoritmo más complejo. Esa política transforma logits en un token, pero no cambia la idea esencial de la caché. El contenido de la caché depende del prefijo procesado y del modelo, no de que la elección se haya hecho con greedy o sampling.

El ciclo termina cuando se genera un token EOS, se alcanza el límite de salida, se activa una condición del runtime o se cancela la petición. En batch serving, distintas solicitudes pueden llevar longitudes diferentes; coordinar esas secuencias es una de las responsabilidades de un motor de serving, que estudiaremos más adelante.

3. Prefill: procesar el contexto conocido

En Prefill, el modelo recibe los P tokens del prompt. Cada capa calcula Query, Key y Value a partir de las representaciones ocultas. La atención de cada posición puede consultar posiciones anteriores y la actual, nunca las futuras. Una máscara causal mantiene esa propiedad mientras el framework calcula muchas posiciones en paralelo.

Para una capa de atención, las proyecciones tienen conceptualmente estas dimensiones:

input:  X  [B, P, d_model]
Q:      [B, Hq, P, Dh]
K:      [B, Hkv, P, Dh]
V:      [B, Hkv, P, Dh]

B es el batch size, P la longitud del prompt, Hq el número de query heads, Hkv el número de Key/Value heads y Dh la dimensión por cabeza. En Multi-Head Attention convencional Hq y Hkv coinciden. Con Grouped-Query Attention o Multi-Query Attention, Hkv puede ser menor.

El prompt completo atraviesa las capas. La última posición produce los logits que permiten seleccionar el primer token de salida. Además, cada capa conserva sus tensores K y V para no tener que volver a calcularlos en las siguientes iteraciones.

Prefill no significa que todas las operaciones sean independientes ni que desaparezca la máscara causal. El paralelismo se da sobre posiciones de la secuencia: la matriz de atención mantiene las dependencias permitidas mediante la máscara. El coste de atención densa está relacionado con la longitud del contexto y la implementación concreta del kernel.

4. Decode: un token nuevo, un query nuevo

Una vez elegido el primer token generado, el runtime lo incorpora a la entrada de la siguiente iteración. La capa calcula sus nuevas proyecciones Q, K y V. La Query es nueva y tiene una posición; las claves y valores disponibles abarcan el prefijo anterior más el token actual.

Q_new:       [B, Hq, 1, Dh]
K_all:       [B, Hkv, P + t, Dh]
V_all:       [B, Hkv, P + t, Dh]

scores = Q_new @ transpose(K_all) / sqrt(Dh)
weights = softmax(scores)
context = weights @ V_all

La salida del bloque produce logits para seleccionar el siguiente token. Los K y V de la posición recién procesada se añaden a la caché de su capa. Se repite en cada capa del modelo. La caché, por tanto, no es una única matriz global: es un conjunto de estados K/V, uno por cada bloque de atención.

En Decode el query tiene longitud 1, pero sus claves y valores pueden cubrir miles de posiciones. Cada nuevo token consulta un contexto que crece. La caché evita volver a proyectar y propagar por todas las capas el prefijo que ya se procesó; no convierte la atención en una operación de coste constante con respecto a la longitud del contexto.

Por qué el orden importa

Si ya tenemos K y V del pasado, no necesitamos volver a calcularlos. Pero sí necesitamos una nueva Query para el token actual y tenemos que calcular su atención frente a las claves acumuladas. La KV Cache evita recomputación de estados anteriores; no elimina la lectura del contexto.

5. Qué guarda exactamente la KV Cache

En cada capa de self-attention se proyecta la representación oculta en tres espacios:

  • Query (Q): representa qué información está buscando la posición actual.
  • Key (K): permite calcular la compatibilidad entre el query y cada posición disponible.
  • Value (V): contiene la información que se combina según los pesos de atención.

En forma simplificada, la atención calcula similitudes QKᵀ, las escala, aplica softmax y usa el resultado para ponderar V. Los K y V de las posiciones anteriores no cambian cuando añadimos un token nuevo en un Transformer causal estándar con pesos fijos: esas posiciones solo podían depender de su propio prefijo, que ya conocemos.

Por eso se pueden almacenar. En cambio:

  • No se guarda una copia de los pesos del modelo por token; los pesos son compartidos por todas las posiciones.
  • No se guarda Query para reutilizarla en el futuro: las queries corresponden a posiciones concretas y la siguiente posición generará una query distinta.
  • No se almacena simplemente el texto del prompt: se almacenan proyecciones tensoriales por capa, cabeza y posición.
  • La caché no contiene por sí sola toda la activación de la red ni el estado completo del proceso de generación.

La caché está vinculada a la identidad y configuración del modelo, a la secuencia de tokens que la produjo y a opciones como RoPE/positional encoding, dtype, arquitectura y atención. Reutilizarla con un prefijo distinto, un modelo incompatible o posiciones mal alineadas no es válido.

6. Por qué la caché evita tanto trabajo

Consideremos un prompt de P tokens y D entradas de Decode. Sin caché, una implementación de referencia puede volver a ejecutar el modelo sobre todo el prefijo para cada nuevo token. El número de posiciones procesadas a través del modelo sería:

(P + 1) + (P + 2) + ... + (P + D)

Con Prefill y caché incremental, el modelo procesa las P posiciones iniciales una vez y después una posición por cada entrada de Decode:

P + D

Para P=32 y D=32, el recálculo completo pasa por 1.552 posiciones acumuladas, frente a 64 en la ruta incremental. La reducción en el recuento de posiciones es del 95,88% en este ejemplo estructural. No significa una reducción equivalente de FLOPs o latencia: cada nuevo query sigue comparándose con un contexto K/V creciente, y el coste de atención, memoria y kernels depende de la arquitectura.

La oportunidad de la caché es especialmente evidente en generación token a token: sin ella, la proyección de posiciones antiguas se repite en cada paso. Con ella, la proyección histórica se conserva y solo se incorpora la nueva posición.

7. Cuánto espacio consume: la fórmula de memoria

La contrapartida es que almacenar K y V cuesta memoria. Para una arquitectura de atención densa homogénea, la estimación del almacenamiento es:

KV_bytes =
  2 × L × B × T × Hkv × Dh × bytes_per_element

Donde:

  • 2: Key y Value.
  • L: número de capas con caché de atención.
  • B: batch size o número de secuencias que mantienen su propio estado.
  • T: posiciones almacenadas en el contexto.
  • Hkv: número de Key/Value heads.
  • Dh: dimensión de cada cabeza.
  • bytes_per_element: tamaño del tipo numérico almacenado (2 para FP16/BF16, 4 para FP32).

Ejemplo ilustrativo: 32 capas, batch 1, 8 KV heads, head_dim 128 y dos bytes por elemento. Cada token necesita 128 KiB de K/V. Para 16.384 tokens, el almacenamiento suma 2 GiB, sin incluir pesos, activaciones, buffers temporales, metadatos ni fragmentación del allocator.

El tamaño crece linealmente con T y B. Duplicar el contexto o el batch duplica el espacio de caché, manteniendo lo demás constante. Aumentar capas, KV heads o dimensión por cabeza también lo incrementa.

La fórmula es una base de dimensionamiento, no una cifra universal. MQA/GQA reducen Hkv frente a Hq; una ventana deslizante puede limitar T en determinadas capas; modelos híbridos pueden combinar distintos tipos de atención; y un runtime puede almacenar bloques, padding o estructuras auxiliares. Por eso hay que consultar la arquitectura y el formato reales antes de reservar memoria.

La caché suele vivir en la memoria del acelerador porque el Decode necesita acceder a ella repetidamente. Algunos runtimes permiten offload a CPU u otras estrategias de almacenamiento: reducen presión de VRAM, pero introducen transferencias y trade-offs de latencia/throughput.

8. Compute-bound en Prefill y memory-bound en Decode

En muchos workloads, Prefill procesa una cantidad significativa de tokens simultáneamente. Hay más trabajo matricial disponible y el acelerador puede aprovechar mejor el paralelismo. Por eso se describe habitualmente como una fase más compute-bound.

Decode procesa muy pocos tokens nuevos por secuencia e itera sobre el modelo en pasos dependientes. Para cada token, los pesos del modelo deben participar en el forward y las claves/valores de un contexto creciente deben leerse. En batch pequeño, la operación puede quedar limitada por mover datos desde memoria más que por el pico teórico de operaciones aritméticas: de ahí el término memory-bound.

Es una caracterización típica, no una ley universal. El batch, longitud del contexto, número de solicitudes concurrentes, tipo de acelerador, kernels, cuantización, speculative decoding y prefix caching pueden cambiar el cuello de botella. Un prompt corto con un prefijo ya cacheado puede comportarse de otra forma; speculative decoding también puede cambiar el trabajo por iteración.

La distinción ayuda a entender por qué una mejora en el kernel de atención puede beneficiar a una fase de manera distinta a la otra, y por qué “tokens por segundo” por sí solo no explica la experiencia del usuario. La latencia del primer token y la latencia entre tokens son dimensiones diferentes.

9. Variantes de caché y decisiones de ingeniería

Dynamic Cache y Static Cache

Una Dynamic Cache amplía sus tensores a medida que llegan tokens. Es flexible para secuencias de longitud variable, pero el crecimiento dinámico puede implicar asignaciones y costes de gestión. Una Static Cache reserva una capacidad conocida de antemano; puede facilitar compilación y ejecución con formas estables, pero reserva espacio incluso cuando una secuencia todavía es corta. La elección depende de runtime, patrón de tráfico y limitaciones de memoria.

GQA y MQA

En Multi-Query Attention, varias query heads comparten una sola pareja de K/V heads. Grouped-Query Attention agrupa varias query heads por cada KV head. Al reducir Hkv, cae la memoria de cache y el volumen de K/V que se debe almacenar y leer. No es una optimización gratuita: cambia el diseño de atención y el compromiso entre capacidad de representación y coste.

Sliding window y arquitecturas híbridas

Algunas capas solo atienden a una ventana local. En esos casos no siempre hace falta conservar todas las posiciones antiguas en esas capas: la longitud efectiva de cache puede limitarse. Otros modelos mezclan capas globales y locales, por lo que la memoria no se estima correctamente multiplicando una única configuración homogénea sin revisar el patrón de atención capa a capa.

Prefix caching no es lo mismo que la cache de una solicitud

La KV Cache ordinaria evita recomputar el prefijo dentro de una generación. Prefix caching intenta reutilizar estados de un prefijo compartido entre solicitudes distintas. Por ejemplo, varias peticiones pueden comenzar con el mismo contexto de sistema o con un documento común. Un motor puede identificar bloques de tokens coincidentes y compartir el estado ya calculado, siempre que la identidad del modelo, los tokens y la configuración permitan esa reutilización. Es una capa de serving adicional, no una propiedad automática de toda caché por petición.

Offload, cuantización y paginación

Offload mueve parte de la cache fuera de VRAM, intercambiando memoria por transferencias. La cuantización reduce bytes por elemento, pero introduce decisiones de escala, precisión y error que requieren validación. La asignación paginada administra bloques de KV para reducir fragmentación y facilitar la admisión de solicitudes de longitudes distintas. Son técnicas complementarias, no sinónimos de KV Cache. Profundizaremos en el motor y su planificación en el capítulo dedicado a vLLM.

10. Cómo medir una inferencia real

Antes de comparar motores o configuraciones hay que definir qué latencia se está midiendo y bajo qué carga. Entre las métricas habituales:

  • TTFT (Time To First Token): tiempo desde que llega la petición hasta que el sistema puede emitir el primer token. Incluye colas y Prefill en la medición end-to-end, según el punto exacto de instrumentación.
  • TPOT (Time Per Output Token): tiempo medio por token generado después del primero, conforme a la convención de medición utilizada.
  • ITL (Inter-Token Latency): tiempo entre tokens consecutivos, útil para estudiar fluidez y variabilidad.
  • Throughput: tokens por segundo, que debe especificar si cuenta tokens de entrada, de salida o ambos y si se mide por request o de forma agregada.
  • Concurrencia y percentiles: solicitudes activas, distribución de longitudes, p50/p95/p99 y tasa de errores.

Una prueba reproducible debe fijar modelo y revisión, tokenizer, hardware, dtype, longitud de entrada/salida, batch/concurrencia, warm-up, duración, política de sampling y definición exacta de cada métrica. También conviene reportar colas y timeouts; medir solo una llamada aislada no representa el comportamiento de un servicio bajo carga.

En el capítulo 08 profundizaremos en benchmarking: TTFT, TPOT, throughput, percentiles, saturación y coste por request. Aquí basta con distinguir que Prefill condiciona el inicio y Decode la cadencia de salida, aunque la carga real puede mezclar ambas fases entre muchas solicitudes.

11. Laboratorio reproducido: caché incremental frente a recálculo

He construido un decoder-only Transformer pequeño en PyTorch con tres capas, cuatro attention heads y dimensión de modelo 64. El modelo tiene pesos aleatorios: su función no es generar lenguaje convincente, sino aislar el flujo de tensores y comprobar que la ruta incremental es equivalente a volver a ejecutar el prefijo completo.

Modelo3 decoder blocks · 4 heads · d_model 64 · head_dim 16

El laboratorio ejecuta Prefill una vez y recoge el estado K/V de cada capa. Después incorpora una secuencia conocida de 12 tokens. En cada paso compara los logits del Decode incremental con los logits de la última posición de un forward completo sobre el prefijo acumulado.

También comprueba la longitud y forma de las cachés, cuenta las posiciones que pasan por el modelo en ambos esquemas y compara los bytes ocupados por los tensores con la fórmula de memoria. No mide latencia relativa entre ambas rutas: el forward completo se usa como referencia numérica, no como benchmark de rendimiento.

13. Errores frecuentes al implementar Decode

  • Recalcular todo el prefijo: funciona como baseline, pero desperdicia proyecciones y activaciones que ya se calcularon.
  • Olvidar añadir K/V: una caché que no se actualiza hace que el modelo ignore tokens generados recientemente.
  • Desalinear posiciones: con RoPE o embeddings posicionales, el nuevo token debe recibir su posición absoluta o relativa correcta; empezar cada llamada en posición cero altera el resultado.
  • Aplicar una máscara causal incorrecta: en un query de longitud uno y un K/V de longitud larga, una máscara no cuadrada puede usar una alineación inesperada. En el laboratorio se atiende a todas las entradas del cache, porque todas son pasado o presente, nunca futuro.
  • Confundir Hq y Hkv: GQA/MQA pueden tener menos KV heads que query heads. La shape de cache no debe asumir siempre que son iguales.
  • Mezclar solicitudes incompatibles: reutilizar un cache con otro modelo, tokenización, prefijo o configuración de posiciones puede invalidar el estado.
  • Dimensionar solo por pesos: en contextos largos y batch alto, la KV Cache puede ser una parte dominante de la memoria de serving.
  • Comparar métricas no equivalentes: TTFT, TPOT, throughput agregado y latencia por request no son intercambiables.

14. Qué demuestra y qué no demuestra el laboratorio

El experimento demuestra que, para este modelo didáctico y dentro de la tolerancia numérica fijada, el cálculo de Prefill y Decode incremental reproduce los logits obtenidos al recalcular cada prefijo completo. Comprueba además la estructura y el dimensionamiento de la caché.

No demuestra aceleración de GPU, menor latencia de un motor real, calidad de generación, throughput de producción, escalabilidad, comportamiento con GQA/MQA, precisión de caches cuantizadas ni ventaja estadística sobre diferentes arquitecturas. Los pesos son aleatorios y no se ha entrenado el modelo.

Conclusión verificable

La KV Cache conserva las claves y valores calculados por cada capa para las posiciones ya procesadas. Decode añade el K/V de la nueva posición y calcula una nueva Query contra el contexto acumulado. En el laboratorio, esta ruta coincide con el recálculo completo dentro de 2 × 10⁻⁵ y evita volver a procesar las posiciones antiguas. El coste que aparece a cambio es memoria proporcional al contexto, batch, capas y número de KV heads.

15. Qué viene después

Ya tenemos el recorrido de la inferencia base: Prefill calcula el estado del prompt; Decode añade tokens de uno en uno; la KV Cache evita recalcular las proyecciones históricas, pero consume memoria y sigue requiriendo leer el contexto.

El capítulo 05 entrará en el motor de serving: vLLM, PagedAttention, Continuous Batching y gestión de memoria GPU. Pasaremos de una caché por secuencia a entender cómo un runtime administra muchas secuencias concurrentes sin desperdiciar memoria con reservas rígidas.
