Benchmarking de LLMs: TTFT, TPOT, throughput y metodología reproducible

Un servidor anuncia 180 tokens por segundo. ¿Es rápido? La cifra no responde a la pregunta. ¿Son tokens de entrada o de salida? ¿De una petición o agregados entre todas? ¿Con qué prompt, longitud de generación, concurrencia, cache, latencia de cola y tasa de error? ¿Se ha medido la respuesta del usuario o solo el kernel? En este capítulo construimos una metodología para medir un sistema LLM como sistema: desde el primer trabajo hasta el último token, bajo cargas conocidas, con límites estadísticos y evidencias que puedan repetirse.

La tesis del capítulo

No existe un único número llamado «rendimiento del LLM». El resultado depende de modelo, hardware, runtime, prompt, output, distribución de llegadas, concurrencia, política de cache, streaming, definición temporal y criterio de éxito. Un benchmark válido publica esa configuración y conserva las muestras por petición. Sin workload y sin fronteras de medición, un tokens/s aislado es telemetría incompleta, no una comparación técnica.

1. Qué pregunta responde un benchmark de LLM

Un benchmark no empieza ejecutando una herramienta. Empieza definiendo la decisión. No es lo mismo seleccionar un modelo para un asistente interactivo que dimensionar una API de generación masiva, un servicio RAG, extracción estructurada o un backend de agentes que encadena varias llamadas.

Hay cuatro preguntas distintas:

  • Experiencia: ¿cuánto espera el usuario hasta el primer contenido y qué ritmo mantiene después?
  • Capacidad: ¿cuántas peticiones, input tokens y output tokens completa el sistema con una mezcla de tráfico determinada?
  • Fiabilidad: ¿qué fracción termina correctamente y cumple los límites definidos como SLO?
  • Economía: ¿cuánto cuesta entregar trabajo válido, bajo el SLO acordado?

Una pregunta comprobable sería: «¿cuál es la mayor tasa de llegada que mantiene TTFT p95 por debajo de 800 ms, TPOT p95 por debajo de 60 ms, errores por debajo del 0,5 % y calidad aceptable para nuestro conjunto de evaluación?». «¿Qué modelo es más rápido?» no especifica el uso ni la frontera de medición.

También hay que separar performance de quality. Un servidor puede producir tokens muy deprisa y generar respuestas incorrectas, incompletas o inseguras. La evaluación de calidad requiere otro conjunto de pruebas (exactitud, task success, groundedness, tool success) y debe acompañar a la evaluación de rendimiento. Cambiar cuantización, limitar contexto o modificar sampling puede alterar calidad; la comparación debe registrar esos cambios.

2. Tres planos de medición: cliente, servidor y hardware

PlanoQué observaQué respondeQué no demuestra por sí solo
Cliente / black-boxSchedule, envío HTTP, stream recibido, finalización, errores.La experiencia end-to-end del consumidor de la API.Qué componente interno generó la latencia.
Servidor / runtimeQueue time, prefill, decode, scheduler, batches, KV Cache.Qué hace el motor y dónde espera.La latencia exacta que percibe el cliente fuera del servidor.
Hardware / sistemaGPU utilisation, HBM, SM, PCIe/NVLink, NIC, CPU, memoria y energía.Qué recurso puede estar saturado.La utilidad de la respuesta ni la experiencia del usuario.

El benchmark principal del servicio debe medirse desde el cliente. El runtime y el hardware explican el resultado. Es posible tener buen TTFT del lado del servidor y un TTFT peor en el cliente por cola del generador, serialización, gateway, transporte, TLS, red o buffering del stream.

Guarda métricas por petición del cliente y, cuando sea posible, correlación con trazas internas mediante request ID. No sumes componentes si se solapan o si sus relojes no están sincronizados. Dos valores llamados «TTFT» pueden empezar y terminar en instantes diferentes.

3. TTFT, ITL, TPOT y E2E: poner cada reloj en su sitio

Time To First Token (TTFT)

En un benchmark streaming del cliente, TTFT es el tiempo desde el envío real de la petición hasta la recepción del primer evento que contiene contenido generado:

TTFT_client = first_content_received_at - request_sent_at

Incluye transmisión, gateway, cola del servidor, preparación/tokenización, Prefill, primer paso de Decode y retorno del primer fragmento. No equivale al tiempo de ejecución de un kernel ni al Prefill aislado.

Concreta qué significa «first token». Algunas APIs envían primero cabeceras HTTP, eventos de estado, metadatos, rol assistant o chunks vacíos. Eso no siempre es contenido visible. Registra la primera recepción de contenido no vacío y documenta el parser del stream. En respuestas no streaming el cliente no puede observar TTFT de forma fiable: solo conoce el tiempo de respuesta completa.

Inter-Token Latency (ITL)

ITL representa el intervalo entre eventos consecutivos de contenido en un stream:

ITL_i = content_event[i].received_at - content_event[i-1].received_at

En sistemas que emiten exactamente un token por chunk, el intervalo se aproxima al tiempo entre tokens entregados. Pero un chunk puede contener varios tokens; speculative decoding, buffering o coalescing cambian la relación entre evento y token.

Time Per Output Token (TPOT)

En la convención usada por el benchmark de serving de vLLM, TPOT se calcula por petición:

TPOT_request = (E2E - TTFT) / (output_tokens - 1)

Se define solo cuando hay más de un token generado. Es una media amortizada del intervalo posterior al primer token, no la latencia de cada token individual. Calcula primero TPOT por petición y después resume su distribución; no restes medias globales ni dividas por un output length promedio.

Ejemplo conceptual: TTFT = 100 ms, E2E = 180 ms y output = 5 tokens. El periodo tras el primer token es 80 ms y TPOT = 80/(5−1) = 20 ms. Si el cliente observa dos gaps de 40 ms porque el segundo evento transporta tres tokens, ITL de eventos es 40 ms y TPOT amortizado es 20 ms. Ambas métricas contestan preguntas distintas.

End-to-End latency (E2E)

En este artículo E2E es el tiempo desde el envío real hasta que el cliente considera completa la respuesta:

E2E_client = response_completed_at - request_sent_at

Documenta si el final se considera al recibir el último chunk de contenido, el evento terminal, el cierre del stream o el body completo. No mezcles finalización lógica y cierre TCP sin indicarlo.

Time To First Byte (TTFB), Time To First Output (TTFO), server TTFT o model execution time aparecen en distintas herramientas. No supongas que son sinónimos. Publica fórmula y frontera temporal. El CLI de vLLM diferencia TTFT, ITL y TPOT, y explica por qué ITL y TPOT divergen cuando un chunk lleva varios tokens. Véase vLLM Benchmark CLI.

4. Throughput: tokens/s no es una métrica única

Throughput mide trabajo completado por unidad de tiempo. En LLM serving hay que identificar qué tokens y qué intervalo se cuentan:

request_throughput = successful_requests / measurement_window_seconds
output_token_throughput = generated_output_tokens / measurement_window_seconds
input_token_throughput = accepted_input_tokens / measurement_window_seconds
total_token_throughput = (input_tokens + output_tokens) / measurement_window_seconds

Request/s mide peticiones completadas. Output tokens/s mide tokens generados por todo el sistema. Input tokens/s refleja trabajo de Prefill. Total tokens/s combina ambos, pero puede ocultar cuánto corresponde a Prefill y cuánto a Decode. Anota si incluyes tokens de peticiones fallidas, canceladas o rechazadas. El laboratorio cuenta solo tokens de peticiones exitosas para throughput y conserva las fallidas para calcular errores.

El ritmo de generación de un usuario no es el throughput agregado del servidor. El inverso de ITL o TPOT aproxima una tasa por secuencia bajo condiciones concretas. Output tokens/s agrega tokens de muchas secuencias activas. Un servidor puede producir 2.000 output tokens/s mientras cada usuario recibe 25 tokens/s. No hay contradicción.

El measurement window debe ser explícito. En un ensayo de duración fija puede ir desde el comienzo de la fase medida hasta el fin del drain (cuando terminan las peticiones admitidas). En el laboratorio se usa la primera llegada planificada hasta la última finalización: incluye drain, excluye warmup. Otras herramientas pueden usar ventanas diferentes.

El mismo output tokens/s puede provenir de muchas respuestas cortas o de pocas largas. Publica request/s, input tokens/s, output tokens/s y distribución de longitudes.

5. Descomponer la latencia: cliente, servidor, Prefill y Decode

planned arrival
  └─ client queue / rate limiter
      └─ actual HTTP send
          └─ network / gateway / ingress
              └─ server scheduler queue
                  └─ Prefill
                      └─ first Decode / first content
                          └─ incremental Decode + stream delivery
                              └─ terminal event / completion

El cliente puede tardar en enviar la petición porque ha alcanzado su límite de concurrencia. Esa espera es client queue, no latencia del servidor. La cola interna aparece después del envío y antes de que una secuencia entre en ejecución. Prefill procesa el prompt; Decode produce los siguientes tokens.

vLLM diferencia el tiempo de cola del benchmark cliente respecto al scheduler queue del servidor. Con métricas por petición activadas, los valores server-side ayudan a aproximar qué porción del TTFT pertenece al scheduler y al runtime. El TTFT del cliente sigue incluyendo transporte y overhead adicional. La instrumentación por petición puede añadir overhead; úsala como diagnóstico y publica si estaba activada.

La descomposición solo es aditiva si los intervalos no se solapan y sus relojes son comparables. Si client TTFT ya incluye server queue y prefill, sumarlos otra vez produce una latencia ficticia. Para correlacionar cliente y servidor hacen falta relojes sincronizados o spans correlacionados.

6. Diseñar el workload: la distribución importa más que la media

Un ensayo con prompts aleatorios de 128 tokens y outputs de 32 puede servir para comparar una microconfiguración, pero no representa por defecto un asistente real con historial, documentos RAG, instrucciones de sistema, tool calls y respuestas largas.

Documenta cinco dimensiones:

  • Input: distribución de prompt tokens (p50/p90/p99), system prompt, historial, retrieval context, documentos largos y proporción de prefijos repetidos.
  • Output: distribución de output tokens, stop sequences, max_tokens, respuestas cortas/largas y truncadas.
  • Request mix: chat, clasificación, extracción JSON, summarisation, RAG, tool calling, reasoning, multimodal o streaming, con proporciones declaradas.
  • Model contract: checkpoint y revision/commit exactos, tokenizer, chat template, sampling y versión API.
  • Cache contract: prefix caching, KV reuse, cache cold/warm, prompt reuse y política de reset.

La longitud del contexto es una variable estructural. Prompts largos elevan Prefill y ocupan más KV Cache; muchas secuencias largas reducen la concurrencia efectiva por presión de memoria. Output length prolonga la ocupación de cada petición. Construye perfiles separados: short chat, long-context RAG, long generation, mixed production traffic y stress test.

No uses una media como sustituto de una distribución. Dos workloads con media de 1.000 input tokens pueden diferir radicalmente: uno concentra casi todas las peticiones cerca de 1.000; otro mezcla 100 con 10.000. Colas, KV y tail latency serán distintos.

Los random prompts aíslan longitudes, pero no necesariamente semántica, tokenización ni prefijos compartidos. Si utilizas un dataset, registra origen, licencia, hash, tokenización, anonimización, filtrado de datos sensibles y transformaciones.

7. Open-loop, closed-loop y coordinated omission

Closed-loop: concurrency-controlled

Un cliente closed-loop envía una petición, espera a completarla y después envía la siguiente. Si la latencia se duplica, ese cliente reduce automáticamente su tasa de llegada. El generador deja de ofrecer carga justo cuando el sistema se degrada. Es útil para modelar usuarios activos que esperan respuesta, pero puede ocultar qué pasa cuando las llegadas externas continúan.

Open-loop: arrival-rate-controlled

En open-loop se planifican llegadas a una tasa objetivo independientemente de la finalización de las anteriores. Si el sistema no sostiene el ritmo, crecen colas, retrasos del generador, rechazos o timeouts. Es útil para estudiar APIs con llegadas externas independientes.

Open-loop no significa mandar tráfico ilimitado ni ignorar backpressure. Debe existir rate scheduler, límites de recursos y políticas explícitas de sobrecarga. Registra llegadas planificadas y envíos reales: si el cliente no mantiene la tasa, el benchmark no ha mantenido el offered rate.

Coordinated omission

La coordinated omission aparece cuando el generador deja de crear muestras durante un periodo de lentitud. Al medir solo las peticiones que logra enviar, omite precisamente el intervalo en el que se habría acumulado trabajo. El p99 parece mejor porque faltan solicitudes. Un esquema de llegadas independiente de las finalizaciones reduce ese sesgo si el generador puede sostener el ritmo y reporta sus propias colas.

Perfiles frecuentes:

  • Constant rate: intervalo determinista, facilita comparar configuraciones.
  • Poisson-like: llegadas estocásticas independientes para modelar cierto tráfico agregado.
  • Gamma / burstiness: permite variar agrupación y variabilidad.
  • Bursts: ráfagas deliberadas para probar admission control, colas, autoscaling y recuperación.
  • Concurrency cap: máximo de requests en vuelo, que puede crear espera en cliente.

Una tasa fija de cinco solicitudes por segundo no describe lo mismo que cinco clientes concurrentes: si las peticiones duran más, los clientes closed-loop completan menos solicitudes por segundo. Registra arrival rate, concurrencia, distribución temporal y backpressure. vLLM y NVIDIA AIPerf permiten controlar request rate, concurrencia y patrones de llegada; valida los flags en la versión instalada.

8. Concurrencia, saturación y goodput: encontrar la zona operable

Con poca carga, aumentar concurrencia suele mejorar throughput: más secuencias llenan batches y mantienen ocupada la GPU. Llega un punto en que los recursos se saturan. A partir de ahí el throughput crece poco mientras colas y p95/p99 aumentan con rapidez. Ese cambio de pendiente es la saturation knee.

La métrica de salida no debería ser «el máximo tokens/s observado», sino la máxima carga de entrada que mantiene el SLO y el error budget. En este artículo usamos una definición operativa de goodput:

goodput_requests_per_second =
  successful requests that satisfy all latency SLOs
  / measurement_window_seconds

Una petición cumple si satisface todas las condiciones acordadas: por ejemplo, TTFT ≤ 800 ms, TPOT ≤ 60 ms y E2E ≤ 8 s. El límite de errores se calcula sobre solicitudes recibidas o planificadas según la política declarada. Son thresholds ilustrativos, no recomendaciones universales.

Se puede definir goodput por tokens o tareas completadas, pero debe declararse denominador y criterio. Goodput no es sinónimo de output tokens/s. Una respuesta larga que incumple TTFT puede elevar throughput y a la vez reducir utilidad operativa.

La relación de Little, L = λW, conecta peticiones medias en el sistema (L), tasa media de llegada (λ) y tiempo medio (W) en un sistema estable. Ayuda a razonar sobre colas, pero no sustituye los percentiles ni aplica sin cuidado cuando el régimen cambia o la cola crece sin estabilizarse.

9. Percentiles y estadística: por qué p99 necesita muestras

La media resume el centro, pero no la cola. Un p50 agradable puede convivir con un p99 que produce timeouts. Publica p50, p90, p95 y p99 de TTFT, ITL/TPOT y E2E, junto con errores, requests/s y output tokens/s. El máximo es útil para depurar, pero sensible a una observación anómala.

Un p99 muestral no es automáticamente una estimación precisa del percentil real. Con cien peticiones, el 1 % más lento representa aproximadamente una muestra; con mil, unas diez. Deben conservarse observaciones crudas, tamaño de muestra, interpolación y repeticiones. Para decisiones rigurosas, añade intervalos de confianza o bootstrap y describe el método.

No existe un número mágico universal de solicitudes para validar p99. Depende de variabilidad, distancia al SLO y confianza buscada. MLPerf muestra que las estimaciones de cola en un benchmark formal pueden necesitar muestras enormes según sus reglas estadísticas; esas reglas no son un mínimo universal para todo servicio.

No promedies p99 de máquinas, procesos o runs para producir un p99 global: los cuantiles no son aditivos. Si tienes histogramas compatibles, agrega buckets y calcula el quantile sobre el histograma agregado; o reúne muestras por petición bajo una misma definición. Prometheus documenta histogramas y histogram_quantile().

Repite ejecuciones independientes. Informa de variación entre runs, no solo una ejecución favorable. Si el efecto observado es menor que el ruido, no es base sólida para un cambio de arquitectura.

10. Protocolo reproducible: el benchmark necesita un manifiesto

GrupoCampos a registrar
ModeloNombre, revisión/hash, tokenizer revision, chat template, cuantización, dtype, contexto y límites.
HardwareGPU SKU/cantidad, memoria, topología, CPU, RAM, NIC, driver, firmware y power mode.
SoftwareOS/kernel, runtime, commit, Python, PyTorch, CUDA, NCCL, driver y librerías.
ServingTP/PP/DP, max model length, max sequences, scheduler, batching, prefix cache, KV dtype y chunked prefill.
RequestDataset/hash/licencia, input/output length, stop, sampling, streaming, tool calls y distribución.
Load generatorVersión, request rate, patrón de llegada, concurrencia, timeout, retries, warmup y número de requests.
MeasurementFrontera temporal, reloj, percentil, agregación, ventana, drain, errores y métricas cliente/servidor.
OperaciónEstado térmico, co-tenancy, background load, red, cache state, fecha, hora y número de run.

Secuencia:

  1. Freeze: inmoviliza revisiones de modelo, runtime, hardware y dataset; calcula hashes.
  2. Warmup: inicializa kernels, graph capture, caches y conexiones. No mezcles warmup con muestras headline.
  3. Settle: deja alcanzar el estado estudiado; registra autoscaling y cambios de cache.
  4. Measure: genera carga al patrón/tasa declarados y captura stream, errores y métricas server-side.
  5. Drain: termina peticiones admitidas; cuenta timeouts, rechazos e incompletas.
  6. Repeat: ejecuta varias repeticiones independientes y cambia una variable por vez.
  7. Publish: conserva CSV/JSON crudos, manifest, logs, scripts y limitaciones.

Warm cache y cold cache son escenarios válidos, pero no deben mezclarse. Para prefix caching, diseña una prueba con prefijos compartidos y otra sin ellos. La documentación de vLLM advierte que repetir benchmarks con inputs similares puede aumentar el prefix cache hit ratio y mejorar artificialmente el resultado; describe resets de cache y sweeps que limpian caches entre repeticiones. La política de cache forma parte del workload.

Un manifiesto mínimo:

{
  "model": "model-name",
  "model_revision": "commit-or-sha256",
  "runtime": "vllm-x.y.z",
  "hardware": ["gpu-sku x 4"],
  "precision": "bf16",
  "parallelism": {"tensor": 4, "pipeline": 1},
  "cache": {"prefix": false, "state": "cold-per-run"},
  "workload": {"dataset_sha256": "...", "arrival": "poisson", "request_rate": 5},
  "measurement": {"warmup_requests": 50, "measured_requests": 1000, "streaming": true}
}

Los valores son ilustrativos, no una configuración recomendada. Un benchmark real debe completar campos verificables.

11. Benchmarking práctico con vLLM

vLLM ofrece comandos separados para medir serving por API y throughput offline. No son equivalentes: bench serve observa el endpoint desde un cliente; bench throughput se centra en generación dentro del proceso y no reproduce por sí solo la ruta de red, gateway y API que ve el usuario.

Levantar un servidor

vllm serve MODEL_ID --enable-per-request-metrics

Usa un modelo al que tengas acceso y cuyos términos permitan la prueba. Fija revisión y configuración. La instrumentación por petición facilita el diagnóstico, pero conviene realizar también una medición headline con el mínimo overhead posible.

Generar carga mediante el endpoint

vllm bench serve \
  --backend openai \
  --endpoint /v1/completions \
  --model MODEL_ID \
  --dataset-name random \
  --random-input-len 1024 \
  --random-output-len 256 \
  --num-prompts 200 \
  --request-rate 5 \
  --max-concurrency 32 \
  --save-result \
  --save-detailed \
  --result-dir ./results

El dataset random fija longitudes y sirve para probar el motor de forma controlada. No equivale a una conversación real: no modela distribución semántica, prefijos compartidos ni necesariamente tokenizer/chat template real. El backend, endpoint y flags pueden cambiar: ejecuta vllm bench serve --help en la versión instalada y conserva ese output.

Para explorar capacidad, barre request rates o límites de concurrencia sin cambiar simultáneamente modelo y configuración. Los comandos de sweep de vLLM ayudan a observar el trade-off entre carga, throughput y latencia SLO. Consulta vLLM Benchmark Sweeps.

Guarda resultados raw por petición, longitud de tokens, request IDs, TTFT/ITL/TPOT/E2E, request rate, max concurrency, client queue y peticiones completadas. En una ejecución diagnóstica separada puedes habilitar server queue, prefill/decode y métricas KV.

Un benchmark offline responde «¿cuánto throughput genera el modelo bajo el backend?»; no responde «¿qué experimenta un usuario a través del gateway bajo carga?». Para lo segundo necesitas medir la ruta que usa el cliente.

12. AIPerf y MLPerf: herramientas frente a estándar

NVIDIA AIPerf

AIPerf es la herramienta de benchmarking GenAI de NVIDIA. Su documentación describe TTFT, ITL, output token throughput y total token throughput. Incluye modos controlados por request rate o concurrency y patrones como constant, Poisson/Gamma o bursts. Es útil para endpoints compatibles; registra versión porque flags, formatos y perfiles evolucionan.

MLPerf Inference

MLPerf Inference de MLCommons es un benchmark estandarizado con modelos, datasets, escenarios, reglas y políticas de reporting. Sus escenarios incluyen SingleStream, MultiStream, Offline y Server; Server modela llegadas online con restricciones de latencia definidas por el benchmark. La comparación oficial está sujeta a reglas, no a cualquier ejecución local.

MLPerf responde a «cómo se comporta una submission bajo una especificación estandarizada». Un benchmark propio responde a «cómo se comporta mi servicio con mi tráfico y mis SLO». Ambos aportan valor, pero no son sustitutos. Dataset, escenario, harness, reglas y validación son parte del resultado.

La tabla headline debe medir desde el cliente. Un panel de diagnóstico complementa esa vista, no la reemplaza. La documentación de vLLM publica, entre otras, las siguientes métricas:

Correlaciona latencias con GPU utilisation, SM, HBM bandwidth/usage, memoria, KV cache occupancy, clocks, thermal throttling, CPU, RAM, PCIe/NVLink y NIC. Una GPU al 100 % no es automáticamente la causa; debe correlacionarse con colas y fases. Una GPU al 30 % puede indicar limitación de memoria, CPU, sincronización o batch pequeño.

Registra admission rejections, HTTP status, cancellations, timeouts, retries, context rejections, preemptions y cache hits/misses. Si hay retries, cuenta la petición lógica y cada intento para no inflar throughput ni esconder fallos.

Las convenciones GenAI de OpenTelemetry incluyen nombres orientados a TTFT y tiempo por token de salida. En la documentación revisada aparecen en estado de desarrollo; trátalas como convenciones en evolución y fija la revisión adoptada. No las presentes como un contrato universal estable.

14. Prometheus e histogramas: calcular percentiles agregados

Para histogramas clásicos de Prometheus, una consulta típica para aproximar el p99 E2E agregando instancias sería:

histogram_quantile(
  0.99,
  sum by (le) (
    rate(vllm:e2e_request_latency_seconds_bucket[5m])
  )
)

Adapta nombre de métrica, labels y ventana a la versión. La operación correcta agrega buckets compatibles antes de calcular el quantile. Si calculas p99 por worker y luego promedias esos p99, no obtienes el p99 de fleet. Los histogramas conservan resolución solo en sus buckets: elige límites que cubran el rango operativo y el tail de interés.

No conviertas request_id, prompt text, usuario o token en labels; disparan cardinalidad y pueden exponer datos. Usa métricas agregadas para tendencias y traces/logs muestreados para peticiones individuales. Define retención y redacción de datos sensibles.

La pregunta no es solo «qué métrica empeoró», sino «en qué frontera empieza el retraso». Un p99 malo de TTFT puede proceder de una minoría de prompts muy largos; la media de input tokens no lo revelará. TPOT puede cambiar por mezcla de batches, longitudes, cuantización o concurrencia.

16. Long context, prefix cache y continuous batching

Aumentar input length eleva el trabajo de Prefill y el tamaño de KV Cache. La capacidad de admitir nuevas secuencias puede caer aunque el throughput de una fase suba. Un prefix cache hit también puede beneficiar mucho más a un prompt largo que a uno corto.

Continuous batching permite incorporar nuevas secuencias cuando otras terminan; no es el mismo experimento que un static batch cerrado. Registra running/waiting requests, preemption, KV block pressure, prefix cache hits y secuencias activas.

  • Cache cold: prefijos no reutilizados, cache reseteada de forma declarada.
  • Prefix warm: instrucciones/prefijos repetidos con cache activa.
  • Long prompt: input tokens altos y output fijo, para aislar Prefill.
  • Long decode: prompt fijo y output largo, para estudiar generación y ocupación.
  • Mixed: distribución de producción con longitudes variables.

Especifica max_model_len, max_num_seqs, KV dtype, block size, chunked prefill, speculative decoding y políticas de scheduler/cache que alteren el resultado.

17. Coste por petición y por millón de tokens

Rendimiento y coste se comparan bajo el mismo contrato de trabajo. Una aproximación al coste directo de compute es:

compute_cost =
  gpu_hour_rate × gpu_count × measured_runtime_seconds / 3600
cost_per_1M_output_tokens =
  compute_cost × 1,000,000 / successful_output_tokens

No es el coste total. Excluye capacidad infrautilizada, amortización, electricidad, CPU, RAM, almacenamiento, red, balanceadores, observabilidad, licencias, soporte y operación. Autoscaling, billing granular o GPUs compartidas necesitan atribución adicional.

Separa coste por millón de output tokens y de total tokens. Añade coste por petición y, mejor, coste por tarea correcta dentro del SLO. Un sistema barato que produce respuestas inválidas o incumple latencia puede ser peor que uno más caro.

El laboratorio acepta --gpu-hour-cost y --gpu-count como valores del operador; no consulta precios ni incorpora costes ocultos. El fixture sintético no representa coste por token de un LLM.

18. Laboratorio reproducido: analizar trazas propias con Python estándar

Este capítulo no simula kernels ni ejecuta un LLM pequeño. Implementa un analizador de trazas observadas desde el cliente. Puedes aprender con datos sintéticos y alimentar el mismo programa con CSV exportados de un benchmark real.

Alcance y coste

Python estándar, CPU-only, sin PyTorch, Transformers, vLLM, CUDA, GPU, API externa, modelo ni servicio de pago. Coste: 0 €. Los registros predeterminados son sintéticos para validar fórmulas; no son benchmarks de modelo, motor, GPU ni red.

Ejecutar

Expand-Archive .\llm-benchmarking-08-lab.zip -DestinationPath .\llm-benchmarking-08
cd .\llm-benchmarking-08
.\run.ps1

O directamente: python .\src\run_lab.py.

El fixture usa una semilla fija y dos escenarios (steady y bursty), cada uno con 48 solicitudes sintéticas. Incluye errores deliberados, longitudes variables y eventos que a veces transportan varios tokens en un chunk.

Importar CSV reales

python .\src\run_lab.py --requests C:\bench\requests.csv --events C:\bench\token-events.csv --output .\reports-real --slo-ttft-ms 500 --slo-tpot-ms 80 --slo-e2e-ms 5000

El CSV de peticiones requiere request_id, scenario, scheduled_ms, sent_ms, first_token_ms, completed_ms, prompt_tokens, output_tokens y status. Los timestamps deben compartir un reloj monotónico y estar en milisegundos. first_token_ms puede quedar vacío en fallos antes del primer contenido. Los campos server_queue_ms, server_prefill_ms y server_decode_ms son opcionales y permanecen separados del plano cliente.

El CSV de stream requiere request_id, chunk_index, received_ms y tokens_in_chunk. Los índices son consecutivos; el primer evento coincide con first_token_ms y la suma de tokens por chunk coincide con output_tokens. ITL calcula intervalos entre eventos, no inventa tiempos dentro de chunks multi-token.

Salidas

  • request-metrics.csv: métricas por solicitud.
  • itl-samples.csv: gaps entre eventos consecutivos.
  • metrics.json: métricas globales y por escenario.
  • lab-report.md: resumen y límites de interpretación.
  • data/manifest.json: procedencia del fixture y seed.

Calcula TTFT, TPOT, ITL, E2E, client queue, campos opcionales server-side, request throughput, input/output/total token throughput, concurrencia máxima, error rate y goodput. Los percentiles usan interpolación lineal R-7. No se generan intervalos de confianza de p99.

Resultados de verificación

Con Python 3.12.10, la ejecución terminó con 20/20 comprobaciones PASS. El fixture contiene 96 requests, 92 exitosas y 4 timeouts; ventana sintética de 32,953 segundos, output throughput de 70,645 tokens/s y concurrencia máxima de 11.

Estos números verifican el analizador, no el rendimiento de un LLM. Proceden de una traza generada localmente; no hay modelo, servidor de inferencia, GPU o API detrás. El valor práctico es que el formato de importación y las fórmulas pueden usarse para analizar observaciones reales sin cambiar el núcleo del programa.

El coste opcional usa una tarifa GPU-hora introducida por el operador y calcula solo coste directo durante la ventana; no incluye amortización, infraestructura ni tiempo ocioso.

19. Runbook: antes, durante y después

Antes

  1. Define decisión, quality gate, SLO y métrica principal.
  2. Fija modelo, tokenizer, chat template, runtime y hardware.
  3. Construye dataset representativo y documenta privacidad/licencia.
  4. Valida que el generador sostiene el rate sin ser bottleneck.
  5. Define warmup, cache mode, request rate, concurrency, timeout y repeticiones.

Durante

  1. Registra schedule y send reales, request ID y resultado.
  2. Mide TTFT, ITL, TPOT y E2E en el cliente.
  3. Recoge métricas server-side y GPU con versión.
  4. Incluye errores, rechazos, cancels y timeouts.
  5. Guarda cache, colas, batches y distribución de tokens.

Después

  1. Espera al drain y cierra la ventana.
  2. Comprueba integridad de eventos, tokens y timestamps.
  3. Calcula percentiles por petición; no promedies percentiles de workers.
  4. Repite y compara variabilidad.
  5. Presenta saturation frontier y máximo goodput dentro del SLO.
  6. Publica datos crudos, manifest, scripts, resultados y límites.

20. Conclusiones y cierre de LLM Engineering

Un benchmark LLM solo tiene sentido cuando carga, frontera temporal y criterio de éxito están definidos. TTFT mide espera hasta el primer contenido; ITL, gaps entre eventos; TPOT, tiempo de generación amortizado; E2E, ciclo completo. Request/s, input tokens/s, output tokens/s y total tokens/s describen capacidades diferentes. Los percentiles revelan colas; goodput conecta capacidad y SLO.

Open-loop y closed-loop representan modelos de llegada diferentes. Distribución de longitudes, prefix cache, continuous batching y long context cambian la carga. Las métricas server-side y GPU explican síntomas, pero la experiencia principal se mide desde el cliente. El coste solo es comparable si se divide por trabajo válido y se declara lo que queda fuera.

Un resultado reproducible conserva versiones, manifiesto, trazas y código. Un p99 sin tamaño de muestra, un output TPS sin ventana o un benchmark que omite fallos no debe usarse para dimensionar un servicio. Primero define el workload; después mide; finalmente explica la evidencia.
